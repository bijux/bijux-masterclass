## 0. Orientation

Module 01 taught the contract (graph → scheduler → workers) and task economics. Module 02 taught how analytics fail at scale (shuffles, skew, metadata coherence, sizing). This module is the production layer:

1) **Control plane**: how you drive execution (collections vs futures),  
2) **Survivability**: memory, spilling, failure modes, retries/cancellation,  
3) **Evidence**: diagnostics that convert “it’s slow” into a root cause,  
4) **Deployment**: patterns that actually run on HPC/Kubernetes/multi-tenant systems,  
5) **Engineering**: tests, idempotence, and decision boundaries.

The goal: you can take an arbitrary distributed workload and:
- choose the correct runtime model,
- make memory behavior predictable,
- diagnose failures quickly with hard evidence,
- deploy reproducibly,
- know when *not* to use Dask.

# Core 1 — Distributed Runtime: Client, Workers, Futures, Orchestration

## 1.1 Architecture: what actually runs where

**Client** (your Python process) builds graphs / submits tasks.  
**Scheduler** holds global state: task graph, dependencies, worker locations, priorities.  
**Workers** execute tasks, store task results, exchange data peer-to-peer.  

The “distributed” API is not optional once you care about production diagnostics and failure handling. The futures interface extends `concurrent.futures` concepts to the cluster. :contentReference[oaicite:0]{index=0}

### Minimal cluster you can reason about

```python
from dask.distributed import Client, LocalCluster

cluster = LocalCluster(
    n_workers=4,
    threads_per_worker=1,     # predictable CPU isolation
    processes=True,           # process isolation is the default production stance
    memory_limit="4GiB",
    dashboard_address=":8787",
)
client = Client(cluster)
client
````

**Why `threads_per_worker=1` as the default stance?**
Because it avoids hidden GIL contention in Python UDFs and makes per-worker memory behavior easier to debug. If you later prove your workload releases the GIL (pure NumPy, some BLAS paths, pure I/O), then *increase threads intentionally*—not by habit.

## 1.2 Threads vs processes: the correct decision rule

**Do not** reduce this to “NumPy releases GIL.” The real question:

### A) Are your tasks CPU-bound Python?

* Python loops, row-wise `.apply`, parsing, regex-heavy transforms, object-heavy work → **processes** (threads will contend).

### B) Are your tasks mostly I/O-bound?

* network reads, object store fetch, database calls → threads can help (latency hiding), but measure.

### C) Are your tasks “vectorized” numeric?

* big NumPy/BLAS operations → threads can help *if* you control BLAS thread oversubscription.

  * If MKL/OpenBLAS uses many threads inside each task and you also run multiple tasks per worker → you can oversubscribe and slow down.

**Production default**: `processes=True, threads_per_worker=1` unless you can justify otherwise with measurements.

## 1.3 Collections vs futures: not binary — it’s “declarative vs imperative”

**Collections (DataFrame/Array/Bag)**:

* declarative graph construction,
* graph-level optimizations (fusion, projection, pushdown),
* best when your workload matches the collection semantics.

**Futures**:

* imperative orchestration,
* streaming / online pipelines,
* external tools, irregular DAGs, per-file workflows, dynamic task generation,
* explicit error handling, cancellation, backpressure.

They are *composable*. Internally, collections ultimately become tasks executed by workers; you can persist a collection, then orchestrate “side pipelines” with futures.

### Rule of thumb

* If you’re doing tabular analytics and you’re writing hundreds of `client.submit` calls → you’re likely discarding dataframe optimizations and reinventing a worse scheduler.
* If you’re running heterogeneous steps (download → validate → external tool → parse → write) → futures are the correct control plane.

## 1.4 Futures: the production patterns (submit / map / as_completed)

### 1.4.1 Basic submission + gathering

```python
from dask.distributed import wait

def heavy(x: int) -> int:
    return x * x

futs = [client.submit(heavy, i, pure=True) for i in range(100)]
wait(futs)                      # barrier
results = client.gather(futs)   # bring to client
```

**`pure=True`** enables task deduplication for deterministic functions (same inputs → same outputs). If your function is not deterministic, set `pure=False`.

### 1.4.2 Streaming results with backpressure

```python
from dask.distributed import as_completed

acs = as_completed(futs, with_results=True)
for fut, res in acs:
    # process result incrementally
    pass
```

This is how you avoid “submit a million tasks, then die” patterns: you stream results, checkpoint, and maintain bounded in-flight work.

### 1.4.3 Cancellation and failure-aware gathering

Dask provides cancellation in the client/future API surface (e.g., `Client.cancel`, `Future.cancel`). ([Dask][1])

Pattern:

```python
from dask.distributed import CancelledError

fut = client.submit(heavy, 10)
# ... decide you no longer want it
client.cancel(fut)

try:
    fut.result()
except CancelledError:
    pass
```

For “best-effort” workflows, gather with controlled error behavior (pattern varies by API; the key idea is to not let one bad shard kill the entire run).

## 1.5 Mixing collections + futures correctly (the “two-plane” architecture)

### Scenario motif: ETL + aggregation + external scoring

* Use DataFrame for ETL + groupby.
* Use futures for per-partition model scoring (or external tool calls).
* Keep boundaries explicit (`persist` or `to_delayed`).

```python
import pandas as pd
import numpy as np
import dask.dataframe as dd

pdf = pd.DataFrame({
    "user": np.random.randint(0, 200_000, size=5_000_000),
    "x": np.random.randn(5_000_000),
    "y": np.random.randn(5_000_000),
})
ddf = dd.from_pandas(pdf, npartitions=200)

stage = ddf[["user", "x"]][ddf["x"] > 0]          # project+filter
stage = stage.repartition(partition_size="128MiB")
stage = stage.persist()                            # stable stage boundary

# Declarative aggregation
agg = stage.groupby("user").x.mean()

# Imperative: score partitions (toy example)
def score_partition(pdf: pd.DataFrame) -> pd.DataFrame:
    pdf = pdf.copy()
    pdf["score"] = pdf["x"] * 0.1
    return pdf

# Convert collection to delayed partitions, then to futures
parts = stage.to_delayed()
score_futs = [client.submit(score_partition, p) for p in parts]

# Stream completion instead of gathering everything at once
from dask.distributed import as_completed
for fut, scored in as_completed(score_futs, with_results=True):
    # write scored partition somewhere idempotent
    pass
```

**Why this is production-grade**:

* ETL work is optimized by dataframe planning.
* A real boundary (`persist`) prevents recomputation across branches.
* Futures let you stream and checkpoint.

## 1.6 Serialization: production reality, not a footnote

Distributed execution requires serialization for:

* task arguments,
* task results,
* inter-worker transfers.

Dask uses a serialization system with multiple serializers and custom handling for common scientific Python types; this is a major source of latency and memory amplification if you pass large Python objects or object-dtype frames.

**Rules that prevent 80% of production serialization pain**:

1. Avoid `object` dtype at scale (strings are fine if properly typed; mixed Python objects are not).
2. Do not ship giant Python dict/list payloads as task arguments; ship references (paths, keys), load on worker.
3. Prefer columnar formats (Parquet/Arrow-backed flows) rather than Python object graphs.
4. Keep task inputs modest; keep task outputs modest; write big outputs to storage from workers.

## 1.7 Worker plugins: lifecycle hooks you will eventually need

Worker plugins exist to run code on worker start/close (e.g., initialize libraries, set env vars, warm caches, register metrics hooks). This is a standard production extension mechanism. ([Dask][2])

Minimal pattern:

```python
from distributed.diagnostics.plugin import WorkerPlugin

class InitPlugin(WorkerPlugin):
    def setup(self, worker):
        # e.g., set thread env vars, initialize GPU context, etc.
        pass

client.register_worker_plugin(InitPlugin(), name="init-plugin")
```

Use plugins when:

* you need deterministic worker initialization,
* you must install per-worker state,
* you want structured lifecycle instrumentation.

# Core 2 — Memory, Spilling, Survival Engineering

## 2.1 The only correct mental model: *managed vs unmanaged* (and why spilling won’t save you)

**Managed memory**: task results stored in the worker data store (tracked and spillable).
**Unmanaged memory**: everything else (temporary allocations, Python overhead, library buffers, leaks, “recent” allocations).

Spilling primarily affects the worker’s managed data store. Internally this uses a spill-to-disk mapping; when spilling is disabled it behaves like a normal in-memory dict. ([Dask Distributed][3])

**Consequence**: if you blow up unmanaged memory (e.g., building huge Python lists, object-heavy transformations), spilling won’t rescue you. The worker may pause or be terminated even if managed memory is small.

## 2.2 Memory thresholds are configuration, not folklore

Dask exposes explicit config keys controlling worker memory behavior, including target/spill/pause/terminate thresholds. The authoritative keys and defaults are documented in the distributed configuration reference and memory docs.

### The knobs you must know

* `distributed.worker.memory.target`
* `distributed.worker.memory.spill`
* `distributed.worker.memory.pause`
* `distributed.worker.memory.terminate`

**Interpretation**:

* *target/spill* govern when the worker begins reducing managed memory pressure (spilling).
* *pause* throttles task execution to stop making the situation worse.
* *terminate* kills the worker process to protect the node.

**Important**: pausing/termination are not a “clean linear pipeline”; they’re threshold-driven reactions under noisy measurement (especially for unmanaged memory).

## 2.3 A minimal, explicit memory configuration (YAML)

Put this in `~/.config/dask/distributed.yaml` (or ship it with your deployment):

```yaml
distributed:
  worker:
    memory:
      target: 0.60
      spill: 0.70
      pause: 0.80
      terminate: 0.95
```

These keys are the canonical surface area. Tune them intentionally based on:

* node RAM,
* workload amplification (shuffle/groupby/join),
* spill disk performance and capacity.

(Use the docs as the source of truth for the config names and semantics. )

## 2.4 The failure modes you actually see in production (and what causes them)

### A) Shuffle buffer blow-ups

Symptoms:

* memory climbs during shuffle,
* spilling engages but doesn’t stabilize,
* one or a few workers approach termination.

Cause:

* shuffle temporarily buffers many incoming fragments,
* skew concentrates data,
* partitions too small → too many fragments.

Fix:

* reduce width before shuffle,
* reduce partitions (coalesce),
* mitigate skew (salting / pre-aggregation),
* increase worker memory or reduce concurrency.

### B) Serialization bloat

Symptoms:

* high network bytes,
* CPU not saturated,
* workers show rising unmanaged memory,
* tasks labeled as “transfer” dominate.

Cause:

* huge Python object graphs,
* object dtype frames,
* passing large objects through task arguments.

Fix:

* pass references (paths/keys), load on worker,
* convert to efficient dtypes,
* avoid Python containers as payload.

### C) Runaway graphs and recomputation

Symptoms:

* repeated upstream stages executed multiple times,
* memory churn,
* wall time dominated by repeated work.

Cause:

* branching without `persist`,
* massive graphs with little fusion.

Fix:

* persist stage boundaries,
* reduce graph size (bigger partitions / fewer layers).

## 2.5 Survival patterns (these are non-negotiable in production)

1. **Idempotent outputs**: tasks may run more than once (retry, worker loss).
2. **Write from workers, not the client**: client-side gathering of huge results is a common death.
3. **Bounded in-flight work**: stream with `as_completed`, don’t submit unbounded task counts.
4. **Keep partitions sane**: if you can’t explain your partition sizing, you’re guessing.
5. **Avoid object dtype** unless you can defend it with measurements.

# Core 3 — Diagnostics: Read the Dashboard Like an Engineer

Dask’s dashboard is not “nice to have”; it is the primary evidence source for performance and failures. The distributed docs describe what diagnostics exist and how to use them. ([Dask Distributed][4])

## 3.1 What each panel answers (the operational questions)

### Task Stream

Answers:

* Are tasks too small (scheduler-bound)?
* Is there a long tail (skew/stragglers)?
* Are there phases (map → shuffle → reduce) and where is time going?

### Shuffle

Answers:

* How many bytes moved?
* Is shuffle dominating runtime?
* Are there stragglers / blocked transfers?

### Workers / Memory

Answers:

* Is memory pressure the bottleneck?
* Is unmanaged memory rising (leak / big temporaries)?
* Are workers pausing or restarting?

### Graph / Graph Size

Answers:

* Is the graph enormous?
* Are there too many layers?
* Are we recomputing upstream work?

### Profile

Answers:

* Inside-task hotspots (Python vs NumPy vs I/O).
* Which functions dominate CPU time.

## 3.2 Programmatic diagnostics (for CI artifacts and incident reports)

### 3.2.1 Shareable performance report

```python
from dask.distributed import performance_report

with performance_report(filename="dask-report.html"):
    result = ddf.groupby("user").x.mean().compute()
```

This produces an artifact that mirrors dashboard evidence and can be archived.

### 3.2.2 Extract task stream and logs programmatically

The Client API provides methods like `get_task_stream` and `get_worker_logs`. ([Dask Distributed][5])

```python
ts = client.get_task_stream(count=2000)   # recent history
logs = client.get_worker_logs(n=200)      # tail worker logs
```

## 3.3 Incident walk-through (worked, with “before/after” evidence)

### Incident: “Groupby hangs at 99%, workers near memory limit”

**Pipeline**:

* read wide dataset,
* groupby key with skew,
* aggregate.

**Dashboard evidence (before)**:

* Task Stream: most tasks finish quickly; a small set run 30–60× longer (long tail).
* Shuffle panel: very high bytes moved; progress stalls near completion.
* Workers: one worker shows memory near pause/terminate; unmanaged memory spikes.

**Root causes**:

1. skew: hot key(s) concentrate data → straggler partitions,
2. width: unnecessary columns traverse shuffle,
3. fragmentation: too many small partitions → too many shuffle fragments.

**Fix** (apply in this order):

```python
# 1) narrow
narrow = ddf[["key", "value"]]

# 2) filter early (if semantically valid)
narrow = narrow[narrow["value"] > 0]

# 3) pre-aggregate within partitions (reduces shuffle payload)
def part(pdf):
    return pdf.groupby("key", sort=False)["value"].sum().reset_index()

import pandas as pd
meta = pd.DataFrame({"key": pd.Series([], dtype="int64"),
                     "value": pd.Series([], dtype="float64")})

partial = narrow.map_partitions(part, meta=meta)

# 4) if skew persists: salt hot keys (two-phase aggregation)
# (Use salting only when evidence shows long-tail stragglers.)
```

**Dashboard evidence (after)**:

* Shuffle bytes reduced (projection + pre-aggregation).
* Long tail shrinks (less straggler dominance; salting if needed).
* Memory peaks lower; fewer pauses; throughput improves.

This “before/after” loop is the production diagnostic workflow: **observe → hypothesize → change one major thing → re-measure**.

# Core 4 — Deployment: Local → HPC → Kubernetes → Gateway

## 4.1 LocalCluster (development parity)

LocalCluster gives you the same scheduler/workers model and dashboard. It is the correct “single-node production simulator.”

```python
from dask.distributed import Client, LocalCluster

cluster = LocalCluster(n_workers=8, threads_per_worker=1, processes=True, memory_limit="3GiB")
client = Client(cluster)
```

## 4.2 HPC / SLURM with dask-jobqueue (the minimal working template)

`dask-jobqueue` provides `SLURMCluster` and adaptive scaling. The jobqueue docs show the adaptive pattern (`cluster.adapt(minimum_jobs=..., maximum_jobs=...)`). ([Jobqueue][6])

```python
from dask_jobqueue import SLURMCluster
from dask.distributed import Client

cluster = SLURMCluster(
    queue="normal",
    account="YOUR_ACCOUNT",
    cores=4,
    processes=4,               # 1 thread each is a common HPC stance
    memory="16GiB",
    walltime="02:00:00",
    local_directory="/scratch/$USER/dask-spill",   # fast local disk for spill
)

# Scale explicitly (deterministic)
cluster.scale(jobs=10)

# Or adapt (cost control) — use bounds
cluster.adapt(minimum_jobs=2, maximum_jobs=50)     # shown in jobqueue docs :contentReference[oaicite:10]{index=10}

client = Client(cluster)
client
```

### Adaptive scaling safety rules (HPC reality)

* Always set a **non-zero minimum** for steady-state workloads (avoids cold-start churn).
* Avoid aggressive scale-down during long shuffles (you want stable worker sets while exchanging data).
* Use adapt for bursty workloads; prefer static scaling for heavy shuffle-dominated runs.

## 4.3 Kubernetes with dask-kubernetes Operator (KubeCluster)

The operator-based `KubeCluster` pattern is documented; you generate a spec via `make_cluster_spec`, modify it, then create the cluster. ([Dask Kubernetes Operator][7])

```python
from dask_kubernetes.operator import KubeCluster, make_cluster_spec
from dask.distributed import Client

spec = make_cluster_spec(name="prod", n_workers=2)

# Example: node selection
spec["spec"]["worker"]["spec"]["nodeSelector"] = {"disktype": "ssd"}

cluster = KubeCluster(custom_cluster_spec=spec)
cluster.scale(20)

client = Client(cluster)
client
```

## 4.4 Multi-tenant: Dask Gateway (standard 2025 pattern)

Gateway provides a control plane for users to request clusters with quotas/auth. The client API includes `cluster_options`, `submit/connect`, `scale_cluster`, and `adapt_cluster`. ([Dask Gateway][8])

### Minimal user-side pattern

```python
from dask_gateway import GatewayCluster
from dask.distributed import Client

cluster = GatewayCluster()   # uses configured gateway defaults
cluster.adapt(minimum=2, maximum=30)   # adaptive scaling documented :contentReference[oaicite:13]{index=13}

client = Client(cluster)
client
```

### Why Gateway matters

* separation of concerns: users run code; admins enforce quotas/security,
* consistent cluster provisioning across teams.

# Core 5 — Engineering Practice: Contracts, Testing, When Not to Use Dask

## 5.1 Contracts you must enforce

### A) Determinism / idempotence at I/O edges

* Tasks can be retried.
* Workers can die mid-run.
* Your pipeline must not corrupt outputs if a task runs twice.

**Pattern**: write to a unique temporary path, then atomically rename/commit.

### B) Schema and dtype contracts (especially around UDFs)

* enforce `meta` for `map_partitions`,
* forbid “sometimes a column exists” logic.

### C) Resource contracts

* enforce partition sizing,
* enforce max task payload sizes,
* enforce memory thresholds via config.

## 5.2 Testing strategy that works in real codebases

1. **Unit test partition functions** on pandas objects (fast, deterministic).
2. **Integration test** a minimal distributed run:

   * LocalCluster with 2 workers,
   * small synthetic dataset,
   * assert outputs + assert no schema drift,
   * produce a `performance_report` artifact in CI for regressions.

## 5.3 When *not* to use Dask (decision matrix)

Use Dask when:

* you can express work as partitioned tasks with limited global coordination,
* data is bigger than RAM or you need cluster execution,
* you need Python ecosystem integration.

Prefer alternatives when:

* you need extremely low-latency interactive queries on single-node data → DuckDB/Polars.
* you need SQL-first warehouse workflows → Spark/Trino/DB engines.
* you need actor-style distributed systems and online serving patterns → Ray.
* your workload is single-machine and fits RAM → pandas/NumPy is simpler and often faster.

**Rule**: if your pipeline is “shuffle-after-shuffle” and dominated by all-to-all exchanges, Dask can do it—but you are operating in the hardest regime. Consider whether the problem formulation can change.

## Appendix B — Diagnostic Decision Tree

1. **Is Task Stream dominated by tiny tasks (< ~50ms)?**

   * Yes → scheduler-bound → increase partition size, fuse operations, batch work.
   * No → go next.

2. **Is Shuffle panel dominating wall time / bytes huge?**

   * Yes → network/memory-bound shuffle regime:

     * project/filter before shuffle,
     * pre-aggregate,
     * mitigate skew,
     * reduce fragmentation (fewer larger partitions).
   * No → go next.

3. **Are workers pausing / unmanaged memory rising?**

   * Yes → unmanaged pressure:

     * remove object dtype / Python containers,
     * reduce per-task temporaries,
     * avoid massive in-memory gathers,
     * profile inside tasks.
   * No → go next.

4. **CPU low but network high?**

   * serialization/transfer overhead:

     * shrink payloads,
     * pass references not objects,
     * reduce partition count fragmentation.

5. **One worker always last?**

   * skew/straggler:

     * detect hot keys,
     * salt,
     * change key or reformulate query.
