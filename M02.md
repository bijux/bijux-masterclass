## 0. Orientation

Module 01 gave you the runtime contract: **lazy graphs, fixed per-task overhead, stage boundaries**.  
Module 02 is the analytics reality: the moment you do “relational things” at scale, you pay for **global coordination**.

### 0.1 The two dominant failure modes in scalable analytics

**(1) Shuffle pain** — global redistribution dominates runtime and peak memory.  
**(2) Metadata pain** — dtype/schema drift breaks correctness or forces conservative execution.

The goal of this module is operational: design pipelines that are:
- **shuffle-thrifty** (few shuffles, minimal bytes moved, balanced keys),
- **metadata-stable** (explicit schema contracts for UDF boundaries),
- **memory-safe** (no uncontrolled shuffle buffer amplification),
- **shape-disciplined** (no repartition ping-pong).

### 0.2 A “global work checklist” (run this in your head before running code)

Whenever you write one of: `groupby`, `merge/join`, `set_index`, `sort_values`:

1) **Width**: which columns will be moved? drop unused columns now.  
2) **Rows**: can you filter or pre-aggregate before the global step?  
3) **Key quality**: skew? cardinality? does the key naturally balance?  
4) **Partition geometry**: are partitions tiny/fragmented? too many participants?  
5) **Stage boundary**: will you reuse the post-shuffle result? `persist()`?

This checklist aligns to the cost model from Module 01:
> time ≈ compute + I/O + shuffle/network + (task_count × overhead)

# Core 1 — Shuffles: The Dominant Runtime and Memory Event

## 1.1 Operational definition (what a shuffle *is* in the runtime)

A shuffle is a **many-to-many exchange** to repartition data by a key:

- each input partition is split into buckets by destination,
- buckets are serialized and transferred,
- destination partitions concatenate received buckets,
- downstream tasks run on the new partitioning.

### Shuffle diagram (cement the mental model)

```mermaid
flowchart LR
  subgraph Inputs
    P1[Partition 1] --> B11[(bucket→A)]
    P1 --> B12[(bucket→B)]
    P2[Partition 2] --> B21[(bucket→A)]
    P2 --> B22[(bucket→B)]
    P3[Partition 3] --> B31[(bucket→A)]
    P3 --> B32[(bucket→B)]
  end

  subgraph Network_Exchange
    B11 --> OA[Out A]
    B21 --> OA
    B31 --> OA
    B12 --> OB[Out B]
    B22 --> OB
    B32 --> OB
  end
````

Why it dominates:

* **bytes moved** → wall time + CPU for (de)serialization,
* **buffering** → peak memory amplification,
* **coordination** → lots of tasks + dependencies,
* **skew sensitivity** → stragglers (one destination receives “everything”),
* **fragmentation** → many tiny transfers when partitions are too small.

**Mental model:** before the shuffle, you often have locality-preserving parallel work; during the shuffle, the cluster behaves like a distributed exchange engine. Treat shuffles as regime changes, not routine steps.

## 1.2 Recognize shuffle triggers immediately

In Dask DataFrame, these commonly force shuffles unless data is already aligned:

* `groupby(key).agg(...)`
* `merge/join` on non-aligned keys
* `set_index(key)`
* global sorts (`sort_values`, some global top-k patterns)

If you cannot point to the line that triggers the shuffle, you are debugging blind.

## 1.3 Shuffle cost control (four levers, strict priority order)

The priority order is not stylistic—it minimizes the bytes and tasks that enter the global exchange.

### Lever A — Reduce width (project early)

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({
    "k": np.random.randint(0, 200_000, 5_000_000),
    "v": np.random.randn(5_000_000),
    "junk1": np.random.randn(5_000_000),
    "junk2": np.random.randn(5_000_000),
})
ddf = dd.from_pandas(pdf, npartitions=200)

wide   = ddf.groupby("k").sum()                  # shuffles v + junk1 + junk2
narrow = ddf[["k", "v"]].groupby("k").v.sum()    # shuffles only v

# Run with dashboard open; compare Shuffle bytes + peak memory.
# wide.compute()
# narrow.compute()
```

**Mechanism:** every extra column multiplies network bytes and buffer memory during shuffle.

### Lever B — Reduce rows (filter early)

```python
import dask.dataframe as dd

filtered = ddf[ddf["v"] > 0]
out = filtered[["k", "v"]].groupby("k").v.sum()
# out.compute()
```

**Mechanism:** fewer rows → fewer bytes split into buckets → fewer bytes exchanged.

### Lever C — Pre-aggregate locally (compress before global combine)

This is exactness-preserving for mergeable aggregations and often yields order-of-magnitude reductions in shuffle payload.

```python
import pandas as pd

def local_group_sum(pdf: pd.DataFrame) -> pd.DataFrame:
    # sort=False avoids unnecessary sorting inside partitions
    return pdf.groupby("k", sort=False)["v"].sum().reset_index()

# Meta is an explicit schema contract for the UDF boundary.
meta = pd.DataFrame({
    "k": pd.Series([], dtype="int64"),
    "v": pd.Series([], dtype="float64"),
})

partial = ddf[["k", "v"]].map_partitions(local_group_sum, meta=meta)
final = partial.groupby("k").v.sum()

# final.compute()
```

**When it helps most:** when keys repeat heavily within partitions (raw rows compress to fewer groups before shuffle).
**Note:** you can also declare `meta` via `make_meta`; both are valid. (Core 3 expands this.)

### Lever D — Choose keys deliberately (avoid self-inflicted skew)

Keys determine:

* skew (hot keys),
* cardinality (number of groups/state),
* output balance.

If the key is structurally skewed, you must mitigate skew (Core 2) or accept long-tail stragglers.

# Core 2 — GroupBy and Aggregations Under Skew (Correctness + Throughput)

## 2.1 Two categories of aggregation (do not confuse them)

### Category 1 — mergeable (decomposable) aggregations

These can be computed as:

* partial state per partition,
* associative combine of partial states,
* finalization.

Examples:

* `sum`, `count`, `min`, `max`
* `mean` via `(sum, count)`
* many stats via moments (numerical stability is its own topic)

These enable tree-reduction behavior and make pre-aggregation (Core 1 Lever C) valid.

### Category 2 — non-mergeable or expensive-to-merge aggregations

Exact metrics that conceptually require “seeing all values” are harder:

* **Exact median / quantiles** are the canonical example: exactness typically requires global coordination over raw-ish data; approximations can be scalable but are not the same contract.

**Engineering rule:** if the aggregation is not mergeable, it is a scalability risk. Either:

* accept approximate methods (explicitly), or
* restructure the question, or
* isolate “hard keys” into special-case paths.

## 2.2 What skew is and why the job “hangs at 99%”

**Skew:** a small fraction of keys owns a large fraction of rows.

Operational consequences:

* a few destination partitions receive huge buckets,
* a few workers become overloaded (stragglers),
* memory concentrates on those workers,
* progress appears stuck near completion because the tail dominates.

## 2.3 Detect skew cheaply (measure; do not guess)

```python
sample = ddf[["k"]].sample(frac=0.001, random_state=0).compute()
print(sample["k"].value_counts().head(10))
```

Look for:

* top key frequency massively above typical,
* head/tail imbalance.

## 2.4 Mitigation ladder (apply in order; stop when solved)

### Step 1 — Narrow + filter + local pre-aggregation

This often fixes mild/moderate skew by shrinking payload and intermediate state.

### Step 2 — Salting (split hot keys across buckets), then re-reduce

Use only when dashboard shows stragglers driven by hot keys.

**Correct salting is per-partition and schema-stable.**

```python
import numpy as np
import pandas as pd

def add_salt(pdf: pd.DataFrame, salt_n: int, seed: int) -> pd.DataFrame:
    pdf = pdf.copy()
    # Fixed seed -> reproducible results. For non-deterministic salting,
    # derive a per-partition seed (e.g., seed + partition_id).
    rng = np.random.default_rng(seed)
    pdf["salt"] = rng.integers(0, salt_n, size=len(pdf), endpoint=False)
    return pdf

meta = ddf._meta.assign(salt=np.int64())
salted = ddf.map_partitions(add_salt, meta=meta, salt_n=16, seed=42)

# Stage 1: distribute hot keys across (k, salt)
partial = salted.groupby(["k", "salt"]).v.sum().reset_index()

# Stage 2: combine salts back to k
final = partial.groupby("k").v.sum()

# final.compute()
```

Trade-offs:

* extra intermediate rows,
* extra aggregation stage,
* better tail latency under severe skew.

### Step 3 — Change the question (often the only honest solution)

If one key dominates, no framework makes it cheap. Options:

* aggregate on coarser keys (cohorts),
* approximate metrics,
* split hot keys into a dedicated processing path.

## 2.5 Avoid accidental global work (two high-frequency traps)

### Trap A — implicit sorts

Sorting is global coordination when it affects partition alignment. Avoid it unless required.

Within partition-level pandas groupby, use `sort=False` when order is irrelevant:

```python
partial = ddf.map_partitions(
    lambda pdf: pdf.groupby("k", sort=False)["v"].sum().reset_index(),
    meta={"k": "i8", "v": "f8"},
)
```

### Trap B — fragmented partitions before shuffle

More partitions means:

* more exchange endpoints,
* more overhead,
* more tiny transfers.

Increase partitions only when:

* partitions are too large for peak memory amplification, or
* tasks are actually chunky and you need more concurrency.

# Core 3 — `map_partitions` as the Production Knife: Metadata Coherence

## 3.1 The contract (why production failures happen)

`map_partitions` is the main extension point: “run pandas code per partition.”
But distributed concatenation requires this invariant:

> Every partition must produce the **same columns**, **same order**, and **compatible dtypes**.

Violations appear as:

* concat failures,
* unexpected dtype upcasts,
* downstream join/groupby errors that only show up at scale (e.g., empty partitions).

**Rule:** If a UDF changes schema/dtypes, declare `meta` explicitly.

## 3.2 `meta=` done correctly (schema as a contract)

```python
import pandas as pd
from dask.dataframe.utils import make_meta

def enrich(pdf: pd.DataFrame) -> pd.DataFrame:
    pdf = pdf.copy()
    pdf["v2"] = pdf["v"] * pdf["v"]
    pdf["flag"] = pdf["v"] > 0
    return pdf[["k", "v2", "flag"]]

meta = make_meta({"k": "i8", "v2": "f8", "flag": "bool"})
ddf2 = ddf.map_partitions(enrich, meta=meta)

# bounded validation
# ddf2.head()
```

`make_meta` is preferable when you want schema declared in one place and reused across multiple UDFs.

## 3.3 Schema drift anti-patterns (and how to make them impossible)

### Anti-pattern: conditional column creation

```python
def bad(pdf):
    pdf = pdf.copy()
    if len(pdf) and pdf["v"].mean() > 0:
        pdf["new"] = 1
    return pdf
```

Fix: always create the column; fill defaults; keep dtypes stable.

```python
def good(pdf):
    pdf = pdf.copy()
    pdf["new"] = 0
    if len(pdf) and pdf["v"].mean() > 0:
        pdf["new"] = 1
    return pdf
```

### Anti-pattern: object dtype creep

Returning lists/dicts inside DataFrame columns forces `object` dtype and destroys predictable memory/serialization costs. If the data is nested, keep it in Bag longer or normalize it explicitly.

## 3.4 Vectorize inside partitions; avoid row-wise apply

Row-wise `.apply(axis=1)` is Python iteration.

Bad:

```python
bad = ddf.map_partitions(
    lambda pdf: pdf.apply(lambda r: r["v"] * 2 if r["v"] > 0 else 0, axis=1),
    meta=("out", "f8"),
)
```

Good:

```python
good = ddf.map_partitions(
    lambda pdf: (pdf["v"].where(pdf["v"] > 0, 0) * 2),
    meta=("out", "f8"),
)
```

# Core 4 — Array + Bag Pipelines (When DataFrames Are the Wrong Tool)

This core is deliberately shorter: it exists to prevent category errors.

### 4.1 Array: chunking controls task count; blockwise ops avoid shuffles

Array pipelines often avoid DataFrame-style shuffles because many operations are blockwise and fuse. Your dominant risk becomes **chunk-induced task explosion** (Module 01 overhead term).

```python
import dask.array as da

shape = (100_000, 1024)

x_small = da.random.random(shape, chunks=(500, 1024))      # too many tasks
x_large = da.random.random(shape, chunks=(10_000, 1024))   # healthier

m_small = x_small.mean(axis=0)
m_large = x_large.mean(axis=0)

# Compare task counts + runtime in dashboard
# m_small.compute()
# m_large.compute()
```

### 4.2 Bag: defer schema, reduce volume, then convert

Bag is the correct front-end for irregular records. It postpones schema enforcement until you’ve filtered and extracted stable fields—meaning you defer expensive “relational” costs until the data is smaller.

```python
import json
import dask.bag as db

raw = db.read_text("logs/*.jsonl").map(json.loads)
clean = raw.filter(lambda r: r.get("status") == "success")

flat = clean.map(lambda r: {
    "user": r.get("user_id"),
    "ts": r.get("timestamp"),
    "v": float(r.get("metric", 0.0)),
})
```

### 4.3 Mixed topology: bag → dataframe → parquet (where shuffles enter)

Shuffles usually enter at first serious `groupby/join/set_index`. Win by ensuring the dataset is **narrow and filtered** before that line.

# Core 5 — Partition/Chunk Sizing: The Practical Performance Lever

## 5.1 The rule-of-thumb (and the non-negotiable caveat)

“~50–200MB per partition” is an empirical starting point to:

* amortize scheduler overhead (avoid microtasks),
* survive memory amplification during shuffles/joins.

But you must tune by:

* worker memory limit,
* dtype (`object` inflates),
* shuffle buffer behavior,
* network/disk performance.

## 5.2 Measure partition size (bytes, not rows)

```python
p0 = ddf.partitions[0].compute()
mib = p0.memory_usage(deep=True).sum() / 1_048_576
print("partition0 (MiB):", round(mib, 2))
```

## 5.3 Coalesce vs repartition: pick the right mechanism

Coalesce (reduce partition count) when overhead dominates:

```python
ddf2 = ddf.repartition(npartitions=200)
```

Repartition by size for memory safety and uniformity:

```python
ddf2 = ddf.repartition(partition_size="128MiB")
```

**Rule:** repartitioning is work; do it once with intent, not repeatedly “just in case.”

## 5.4 Pipeline shape discipline (the real multiplier)

Bad:

* shuffle wide → repartition → shuffle again → write tiny files

Good:

* read narrow + filter → repartition once → (persist if reused) → one major shuffle → write controlled files

## Appendix B — Patterns and Anti-patterns

### Patterns (default behaviors)

* Narrow before shuffle (project + filter).
* Pre-aggregate locally for mergeable aggregations.
* Treat salting as a skew-specific tool, not a default.
* Declare `meta` for schema-affecting UDFs.
* Size partitions by bytes; avoid fragmentation before shuffles.
* One deliberate shuffle per pipeline when possible.

### Anti-patterns (assume these are bugs)

* Shuffling wide frames because it’s convenient.
* Groupby on skewed keys without mitigation.
* `map_partitions` with conditional schema or implicit dtype inference.
* Row-wise apply as a default technique.
* Repartition ping-pong between stages.
