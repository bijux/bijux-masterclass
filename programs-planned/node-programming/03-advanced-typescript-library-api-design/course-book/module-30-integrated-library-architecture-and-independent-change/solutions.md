# Module 30 Reasoned Solutions

## A. Contract map

A strong map separates runtime factories/classes, erased interfaces/helpers, internal decoders, built declaration files, package subpaths, JSON text, unknown values, validated outputs, issues, and CLI process behavior. Each fact has one authority.

## B. Assertions

Assertions inside tuple accumulation or key-indexed internal storage can be justified by exact traversal/registration invariants. Assertions from unknown input to inferred output cannot. Remove any assertion whose proof sentence names only “TypeScript limitation” without a runtime fact.

## C. Declarations

Consumers should understand schema construction, inference, result narrowing, optional fields, callbacks, errors, and subpaths. Internal contexts, mutable accumulators, symbols, and source paths should be absent.

## D. Package

The built fixture—not source imports—proves exports. Root, JSON, and testing paths should resolve; undeclared internals should not. Import should define values only.

## E. Bounds

Resource limits are runtime contracts and require boundary tests. Issue objects carry paths/codes/messages only, avoiding arbitrary input retention.

## F. Laboratory

The independent audit should find at least one unnecessary generic, one missing runtime check, one declaration leak, one package-boundary risk, and one compatibility ambiguity, then repair them without adding broad assertions.

## G. Impact map

The new combinator affects every named layer. A map that lists only `combinators.ts` and tests is incomplete.

## H. Implementation

The runtime selects one variant by an own string discriminator. The static output is `Infer<V[keyof V]>`. Construction validates non-empty maps and variant consistency as far as the public representation permits. Unknown tags produce a discriminator-path issue. Existing `union` remains unchanged.

## I. Restraint

Async validation changes lifecycle and cancellation; universal exactness and path types are expensive and domain-sensitive; JSON Schema is a separate interchange standard; class instances are unnecessary for validated data; plugins create versioning and authority requirements. Omitting them keeps Course 3 coherent.

## J. Reconstruction standard

A complete story links structural shape to generic relationship, type derivation, variance, declarations, exports, runtime validation, compatibility, and independent change. Each layer must be truthful on its own and aligned with the others.

## I. Surface agreement

The table should show one implementation authority for each behavior and evidence at every consumer-visible layer. A declaration-only helper with no runtime export is a defect. A runtime export omitted from `exports` is private even if tests can reach its file. An optional type whose parser rejects absence is dishonest. A migration with no old-data fixture is an unsupported claim.

## J. Impact order

Begin with a written contract and construction-time invariants. Implement runtime selection and duplicate rejection next, then derive the output type from the same variant map. Export only after runtime and type tests agree. Inspect declarations, add package tests, document diagnostics, and finish with compatibility analysis. This order prevents a polished public type from legitimizing incomplete runtime behavior.

## K. Consumers

Application consumers prove ordinary inference and runtime execution. Testing consumers prove the supported subpath. Wrappers reveal whether public generic relationships are composable without internal imports. The unsupported deep import should fail because private files are not a compatibility promise.

## L. Verification ownership

A package-consumer fixture catches wrong declaration targets. Runtime schema tests catch optionality drift. Adversarial union tests enforce diagnostic bounds. Versioned fixture and migration tests catch lost tags. No single test suite can cover all four because the defects occur at different phases.

## M. Defense

The explanation should identify JSON syntax parsing, unknown runtime value, version union parsing, own-property validation, optional behavior, migration, canonical rendering, file replacement, declaration projection, and package resolution. Assertions are acceptable only inside a bounded implementation where a preceding invariant establishes the relation. Limits and exports are product decisions, not incidental defaults.

## N. Transfer

A successful independent architecture uses the same reasoning without copying SchemaKit's domain. It should name its runtime authority, derived static relationships, supported paths, emitted artifacts, compatibility fixtures, and future-change policy. That is the point at which advanced TypeScript becomes library engineering rather than isolated type manipulation.

## O. Rehearsal

A release table should identify exact built artifacts and commands. Type checking source is not a substitute for installing the package shape. Old fixtures test data compatibility; process execution tests CLI status and output; unsupported imports prove encapsulation; declaration inspection catches leaked names; consumer fixtures prove real resolution. Failures should point to one owning layer rather than being waived as tooling noise.

## P. Defense

Runtime trust belongs to schema decoding from `unknown`. `Infer<S>` derives the output relation. The hardest assertion usually connects generic runtime construction to a mapped output; it must be local and supported by one-to-one traversal. Internal decoder files remain private. V1 project data remains readable and migratable. Removing an export or rejecting V1 requires a major release. Issue, depth, length, and union-detail limits bound adversarial diagnostics.
