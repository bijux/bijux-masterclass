## 1. Why Generics Are Metaprogramming at All

From a surface-syntax perspective:

```rust
fn id<T>(x: T) -> T { x }
fn map<T, U, F: Fn(T) -> U>(f: F, xs: Vec<T>) -> Vec<U> { /* ... */ }
```

this looks like “just abstraction”. Where is the “meta”?

Two key points:

1. **Type parameters are meta-variables.**

   * Ordinary functions abstract over **values**.
   * Polymorphic functions abstract over **types**.

   In a core calculus, parametric polymorphism introduces **type-level lambdas**:

   ```text
   Λα. λ(x : α). x
   ```

   This is exactly “code that is parameterised by types”.

2. **The compiler must interpret these type-level programs.**

   * At the **type phase**, it checks that a polymorphic definition is well-typed for *all* instantiations of its type variables.
   * Later, it **instantiates** those type variables at concrete types and chooses an **implementation strategy** (erasure, monomorphization, dictionary passing).

This is **static metaprogramming at the type level**:

* **R:** types and typing derivations as structured objects (type graphs, constraints).
* **T:** generate or rewrite code for each type instantiation.
* **S:** all of this is enforced **before runtime**.

Parametric polymorphism is the lowest-risk, best-disciplined form of static meta you can have: it is **meta over types** with deliberately restricted power.

---

## 2. Three Notions of Polymorphism

We distinguish three classical forms.

1. **Parametric polymorphism** (“generics” in the narrow sense):

   ```text
   id : ∀α. α → α
   map : ∀α β. (α → β) → List α → List β
   ```

   Behaviour must be **uniform in α, β**. The function cannot branch on which type is used.

2. **Ad-hoc polymorphism** (overloading, typeclasses, traits):

   ```text
   (+) : Int → Int → Int
   (+) : Float → Float → Float
   ```

   Or:

   ```rust
   trait Add<Rhs = Self> { type Output; fn add(self, rhs: Rhs) -> Self::Output; }
   ```

   Different instances **can behave differently** per type.

3. **Subtype polymorphism** (OO style):

   ```java
   void draw(Shape s) { s.draw(); }
   ```

   Dynamic dispatch chooses behaviour based on the **runtime class** of the argument.

This core focuses on **(1) parametric polymorphism**: the form that most directly gives **free theorems** and **representation independence**.

Ad-hoc polymorphism (M04C17–18) and subtyping (adjacent OO material) are different metaprogramming stories.

## 3. R–T–S and the Compiler Pipeline for Generics

### 3.1 Representations (R)

For parametric polymorphism, the primary representations are:

* **Type syntax / graphs**: `∀α. τ`, constraints, type variables, schemes.
* **Typing derivations / constraints**: logical evidence that a polymorphic definition is valid.
* **IR with type annotations**: HIR/MIR/typed AST with polymorphic constructs.

We distinguish two transformation layers:

* `T_type`: transforms *typing judgments* and type annotations; no change to runtime IR yet.
* `T_code`: later transforms on IR/code to realise polymorphism.

### 3.2 Type-Phase Transform (`T_type`)

At the type checking phase:

1. **Generalisation** (defining polymorphic functions):

   From a monomorphic derivation:

   ```text
   Γ ⊢ e : τ
   ```

   to a polymorphic scheme:

   ```text
   Γ ⊢ e : ∀α₁ … αₙ. τ
   ```

   where `αᵢ` are the type variables not fixed by Γ.

2. **Instantiation** (using polymorphic functions):

   Given:

   ```text
   Γ ⊢ f : ∀α. σ   and   τ is a type
   ```

   we obtain an instance:

   ```text
   Γ ⊢ f[τ] : σ[α := τ]
   ```

This is **meta-level logic over types**. It satisfies **R** and **S** and indirectly contributes to **T** by changing the set of programs that are accepted and how they are typed.

### 3.3 Code-Phase Transform (`T_code`)

After types are known, the compiler must decide **how to implement** polymorphism. Typical strategies:

* **Erasure:** compile one copy of the code, drop type parameters, specialise only where needed via casts.
* **Monomorphization:** generate a copy of the function per concrete type instantiation.
* **Dictionary passing / interfaces:** pass runtime evidence (method tables, vtables, dictionaries) to a single generic body.

This is explicit **code transformation** (T) on IR:

* `T_code(IR)` → `IR'` with no polymorphism, ready for optimisation and codegen.

We will study this in detail in **M04C19**; here we only need the conceptual separation:

> **Generics as meta** = `T_type` + `T_code` over type-annotated IR, both executed **before runtime**.

## 4. Canonical Parametric Polymorphism (Idealised Core)

We fix a simple core calculus:

* Types:

  ```text
  τ ::= α           -- type variable
      | Int | Bool | …    -- base types
      | τ → τ             -- functions
      | ∀α. τ             -- universal types
  ```

* Terms:

  ```text
  e ::= x
      | λ(x : τ). e
      | e₁ e₂
      | Λα. e              -- type abstraction
      | e[τ]               -- type application
      | …                  -- constants
  ```

Typing rules (schematically):

* Type abstraction:

  ```text
  Γ ⊢ e : τ
  --------------------------
  Γ ⊢ Λα. e : ∀α. τ
  ```

* Type application:

  ```text
  Γ ⊢ e : ∀α. τ
  ------------------------
  Γ ⊢ e[σ] : τ[α := σ]
  ```

In this ideal system:

* Terms **cannot inspect types at runtime**.
* There is no reflection, no runtime type tests, no overloading; only parametric polymorphism.

This is the setting where **parametricity** and **free theorems** are mathematically clean.

Real languages only approximate this; we’ll address that explicitly later.

## 5. Parametricity and Theorems for Free

**Parametricity** (Reynolds): roughly, polymorphic functions behave **uniformly** across all instantiations of their type variables. They cannot “cheat” and treat some types specially, because they cannot observe which type was chosen.

The payoff: from a type alone, we can derive **semantic laws** that any implementation must satisfy.

### 5.1 Simple Examples

1. The identity type:

   ```text
   id : ∀α. α → α
   ```

   In a pure, parametric setting:

   * `id` cannot construct new values of type `α`.
   * It cannot inspect or branch on the structure of `α`.
   * Therefore, **up to observational equivalence**, the only possible implementation is:

     ```text
     id = Λα. λ(x : α). x
     ```

   It may differ by inlining or constant factors, but you cannot have an `id` that behaves differently on `Int` vs `Bool` without breaking parametricity.

2. Map:

   ```text
   map : ∀α β. (α → β) → List α → List β
   ```

   **Free theorem (fusion):**

   For all `f : α → β`, `g : β → γ`, `xs : List α`:

   ```text
   map g (map f xs) ≡ map (g ∘ f) xs
   ```

   Why?

   * `map` cannot inspect elements of type `α` or `β` beyond applying the supplied function.
   * It cannot drop or duplicate elements “selectively” based on their types.
   * Therefore the only thing it can do is traverse the structure of `xs`, applying its function argument in one pass; any deviation is observable by choosing suitable `f`, `g`.

### 5.2 Where Free Theorems Break

If the language allows non-parametric operations, the same types **do not** guarantee these laws:

* Runtime type inspection (reflection, RTTI).
* Global mutable state dependent on types.
* Partial evaluation or specialisation triggered by types.

Example:

```java
<T> T id(T x) {
    System.out.println(x.getClass().getName());
    return x;
}
```

Type:

```text
id : ∀α. α → α         -- in a Java-ish surface syntax
```

But `id` is **not parametric** in the strong sense: it behaves differently depending on `α` (`String`, `User`, …). The “free theorem” that `id` is observationally indistinguishable from the identity fails.

> **Key point:**
> The type *suggests* parametricity; the language semantics may violate it. Parametricity is an *additional discipline*, not guaranteed by syntax alone in mainstream languages.

## 6. Representation Independence

The practical engineering payoff:

> If you expose a type `α` abstractly and only allow clients to interact via **parametric operations**, then clients cannot distinguish between different representations of `α`.

Example (informal, ML-style):

```ocaml
module type COUNTER = sig
  type t
  val zero : t
  val inc  : t -> t
  val to_int : t -> int
end
```

Client code sees only `type t` and functions whose types are **parametric in `t`** (no cheating operations on a specific representation).

You can implement:

* `t = int` with `zero = 0`, `inc = (+1)`, or
* `t = int * int` with some more complex scheme,

and as long as you satisfy the **type signatures** and **parametric behaviour**, clients cannot tell which representation you chose.

This is **representation independence**: you can change the internal representation of abstractions without affecting well-typed client code.

From a metaprogramming perspective:

* Parametric interfaces create **meta-invariants over families of programs**.
* These invariants are enforced **by the type checker**, not by ad-hoc convention.

## 7. Erasure vs Reification (Preview of M04C19)

Generics need an **implementation strategy**:

1. **Erased generics:**

   * Types are used at compile time only; at runtime they vanish.
   * Often implemented by compiling all type parameters to a uniform representation (e.g. `Object` / `void*` / tagged value).
   * Example: Java generics (type erasure), many ML-family languages.

   Consequences:

   * **Pros:** smaller binaries, no code bloat, simple codegen.
   * **Cons:** limited runtime type testing, boxing, casts, fewer optimisation opportunities.

2. **Reified / monomorphized generics:**

   * Each instantiation `f<int>`, `f<User>` may get its own version of the code.
   * Types are kept around in IR; specialisation is explicit.

   Consequences:

   * **Pros:** better inlining, no boxing, more optimised code.
   * **Cons:** code size, compile-time cost (M04C19, M10C49).

This choice is **not** visible in the ideal parametric calculus, but it hugely affects:

* which **non-parametric tricks** are possible (runtime type tests),
* how much generics can be abused as a **type-level computation mechanism**.

We revisit this in depth in **M04C19**.

## 8. Parametricity in Real Languages: Reality Check

The ideal picture (System F + purity) is clean; real languages are messier.

### 8.1 Java / C# / Kotlin / Scala

* **Erased generics** (Java, partially Kotlin):

  * `List<T>` compiled to `List<Object>` with casts.
  * Reflection and `instanceof` let you observe runtime types to some extent.
  * Bridge methods, wildcards, raw types further blur parametricity.

* **Reified generics** (some cases: Kotlin reified type params, C# with `typeof(T)`, constraints):

  * You can write methods like `bool IsDefault<T>(T x)` that behave differently depending on whether `T` is a struct/class, or inspect `typeof(T)`.

These features **break pure parametricity**. Types suggest uniformity, but the implementation can branch on `T`.

### 8.2 Rust

* Generics + traits are **nominally parametric**:

  ```rust
  fn id<T>(x: T) -> T { x }
  ```

  behaves uniformly in `T`.

* But:

  * `Any` (`downcast_ref::<T>`) and reflection-ish crates let you inspect type IDs.
  * Specialisation and auto-traits can behave differently for different `T`.

Rust is closer to the ideal than Java, but still not pure. Parametricity is a **good mental model**, not an iron law.

### 8.3 C++ Templates

Although templates are often marketed as “C++ generics”, they are fundamentally different:

* Templates are **instantiated** very early into concrete types; they support:

  * partial specialisation,
  * `if constexpr`, SFINAE tricks,
  * arbitrary constant and type-level computation.

* There is no **semantic guarantee** of uniformity:

  ```cpp
  template<typename T>
  void f(T x) {
      if constexpr (std::is_integral_v<T>) { /* int path */ }
      else { /* non-int path */ }
  }
  ```

This is not parametric polymorphism in the classical sense; it is a **compile-time ad-hoc / type-level programming system** (borderline Module 05). Parametricity free theorems **do not** hold in general.

## 9. WSM/Tier View: When Generics Stay “Controlled”

Recall the **WSM/Tier** idea from M01C05:

* **Tier-0/1:** plain code, simple abstractions, low systemic risk.
* **Tier-2:** structured, well-disciplined meta (e.g. hygienic macros, plain generics).
* **Tier-3/4:** highly expressive meta, significant complexity and global impact.

Parametric polymorphism is designed to live at **Tier-1/2**:

* Meta-power is bounded: you can only be **uniform** in type parameters.
* Effects are **local**: generics rarely affect global code shape in surprising ways.
* Tooling is strong: error messages and reasoning are type-directed, not expansion-driven.

Generics become Tier-3/4 when you:

1. **Abuse them as a type-level programming language**:

   * C++ template metaprogramming, deep Rust trait machinery, heavy type-level hacks in Haskell/Scala.
   * You start encoding invariants and behaviours in types that require serious proof-engineering to understand.

2. **Layer constraint systems without discipline**:

   * Deeply nested bounds and where-clauses.
   * Higher-kinded types, associated types, functional dependencies—all crammed into “just generics”.

3. **Exploit reflection and specialisation aggressively**:

   * Branch behaviour on runtime type information (`Any`, `Typeable`, RTTI).
   * Use specialisation to create non-uniform behaviour per type.

For M04C16, the **good practice message** is:

> Treat parametric generics as **constrained, nearly-Tier-1 meta**.
> Once you start doing elaborate type-level tricks, you’ve left this core and entered Module 05 territory (with corresponding Tier-3/4 risks).

## 12. M04C16 Glossary (Compact Reference)

* **Parametric polymorphism**
  Polymorphism where functions are abstracted uniformly over type variables; behaviour cannot depend on the particular types chosen.

* **Ad-hoc polymorphism**
  Polymorphism where behaviour can vary per type (overloading, typeclasses, traits).

* **Subtype polymorphism**
  Polymorphism induced by subtyping or inheritance, where a function accepts a base type and dispatches on dynamic subtype.

* **Universal type / type scheme** (`∀α. τ`)
  A type that quantifies over type variables; the core of parametric polymorphism.

* **Parametricity**
  Property that polymorphic functions act uniformly across all instantiations of their type variables; no type-dependent branching. Yields **free theorems**.

* **Free theorem**
  A semantic property derivable from a polymorphic type alone (e.g. fusion laws for `map`), assuming parametricity.

* **Representation independence**
  Invariance of client-visible behaviour under changes to the internal representation of an abstract type, provided interactions go through a parametric interface.

* **Erased generics**
  Implementation strategy where type parameters are used only at compile time and erased at runtime (e.g. Java generics).

* **Reified / monomorphized generics**
  Strategy where the compiler produces specialised versions per type instantiation, keeping type information in IR.

* **`T_type` vs `T_code`**
  `T_type`: type-phase transform (generalisation/instantiation).
  `T_code`: code/IR-phase transform (erasure, monomorphization, dictionary passing).

* **Tier-1/2 generics (WSM)**
  Use of parametric polymorphism as low-risk meta: uniform in types, minimal constraints, no heavy type-level tricks.

* **Tier-3/4 generics (WSM)**
  Use of generics as a powerful type-level programming substrate (templates as a language, deep trait machinery, heavy reflection), with associated complexity and systemic risk.

## 13. Python Sidebar: “Generics” and Parametric Style

Python does not have **static** parametric polymorphism in the same sense, but there are analogous ideas.

### 13.1 Duck Typing as “Implicit Parametricity”

Python functions are often **implicitly polymorphic**:

```python
def head(xs):
    return xs[0]
```

* Works for any `xs` supporting `__getitem__` with index `0`.
* There is no static `∀α` quantifier or guarantee of uniformity.
* Parametricity is a **design discipline**, not enforced by the language.

From the M04C16 viewpoint:

* There is **no type-phase `T_type`**; type variables live only in your head or in annotations.
* There is **no code-phase `T_code`** specialising by type; Python is dynamically typed.

This is **dynamic polymorphism**, not static meta.

### 13.2 `typing` and Generic Classes

Python’s `typing` module allows:

```python
from typing import TypeVar, Generic, List

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value

def id_box(x: Box[T]) -> Box[T]:
    return x
```

Here:

* Static type checkers (mypy, pyright) treat this as if it were parametric polymorphism.
* At runtime:

  * `T` is erased;
  * `Box[int]` is the same class as `Box[str]`;
  * type parameters exist only in metadata for tools.

From the R–T–S perspective:

* **R:** type hints form a static type graph in tooling, but CPython itself does not enforce them.
* **T:** no code generation based on `T` (erasure-like).
* **S:** tools can treat type checking as a pre-runtime phase, but the language semantics itself does not.

> Practically:
> Python’s generics are **“parametric style”** enforced by tools, not **true parametric polymorphism** in the runtime semantics.

### 13.3 Single-Dispatch and Multiple Dispatch

`functools.singledispatch`:

```python
from functools import singledispatch

@singledispatch
def to_text(x):
    return str(x)

@to_text.register
def _(x: int):
    return f"int({x})"
```

* Dispatch is based on **runtime type** of `x`.
* Behaviour is **ad-hoc**, not parametric.
* Conceptually this belongs in **M04C17 (ad-hoc polymorphism)**, not M04C16.

From a WSM/Tier view:

* Python’s “generics” are **Tier-0/1 discipline** layered on a dynamic language.
* Serious meta-power comes from **reflection, decorators, and dynamic dispatch**, not from static parametric polymorphism.

## 14. C++ Sidebar: Templates – Parametric vs Type-Level Programming

C++ templates combine:

* genuine **parametric usage** in some patterns, and
* very expressive **type-level programming** in others.

### 14.1 Simple Parametric Template

```cpp
template<typename T>
T max_value(T a, T b) {
    return a < b ? b : a;
}
```

Assuming:

* `T` supports `<`,
* No specialisation exists,

this is close to a parametric function:

* It does not inspect any **runtime representation** of `T`.
* Behaviour is **uniform** modulo what `<` does for each `T`.

But C++ gives you no semantic guarantee of parametricity:

* You can specialise:

  ```cpp
  template<>
  const char* max_value<const char*>(const char*, const char*);
  ```

* Or add `if constexpr` branches on traits.

Then behaviour becomes **type-dependent** and free theorems break.

### 14.2 Template Metaprogramming (Beyond M04C16)

Classic TMP:

```cpp
template<int N>
struct Fib {
    static constexpr int value = Fib<N - 1>::value + Fib<N - 2>::value;
};

template<>
struct Fib<0> { static constexpr int value = 0; };

template<>
struct Fib<1> { static constexpr int value = 1; };
```

Here:

* Templates are used as **a compile-time computation language**.
* There is no parametricity in the M04C16 sense; behaviour is completely driven by type/constant patterns.
* This belongs squarely in **Module 05 (type-level programming) and Module 06 (staging/constexpr)**.

WSM/Tier classification:

* Simple, uniform templates over `T` can be **Tier-2** meta.
* Template metaprogramming of this form is **Tier-4**: Turing-complete, hard to debug, and can cause compile-time blow-ups.

### 14.3 Interaction with Erasure/Reification

C++ templates are strongly **reified** and monomorphized:

* Each instantiation `max_value<int>`, `max_value<double>` typically generates distinct code.
* This gives performance and optimisation benefits.
* It also enables non-parametric tricks: you can specialise per type and branch on type traits.

Contrast with Java-style erasure (no specialisation) and ML-style parametric polymorphism (no specialisation + uniform runtime representation). The more reified and specialisable your templates, the less automatically parametric they are.

From M04C16’s perspective:

* C++ templates provide **both** parametric and non-parametric patterns.
* It is the **library and language design discipline** that determines whether a given template API behaves as controlled, Tier-2 parametric meta or as a high-Tier type-level DSL.
