## 1. Traits / Concepts / Typeclasses: Interfaces Over Types

### 1.1 Intuition

Abstractly:

> A **trait / concept / typeclass** is an *interface over types*:
> a named collection of operations and laws parameterised by one or more type variables, plus a mechanism to declare *instances* for particular types.

Schematic syntax:

```text
class C α₁ … αₙ where
  op₁ : σ₁
  …
  opₖ : σₖ
```

Instances:

```text
instance C τ₁ … τₙ where
  op₁ = e₁
  …
  opₖ = eₖ
```

Polymorphic functions with constraints:

```text
f : ∀α. C α ⇒ α → α → Bool
```

Key points:

* The **interface** lives at the type level (conditions on `α`).
* Instances live at the value level (concrete functions).
* Functions can quantify over types **subject to** the interface being available.

### 1.2 Relation to parametric and ad-hoc polymorphism

Recall Module 4:

* **Parametric polymorphism** (M04C16):

  ```text
  id : ∀α. α → α
  ```

  – one uniform implementation for all `α`.

* **Ad-hoc polymorphism** (M04C17):
  – multiple per-type implementations; resolution is compile-time search + choice.

Traits/typeclasses:

* Combine **parametric quantification** (`∀α`) with **type-based dispatch** (`C α`).
* Provide a disciplined variant of ad-hoc polymorphism, constrained by an interface.

Heuristically:

> Traits/typeclasses = parametric polymorphism + constraint-directed ad-hoc polymorphism.

## 2. R–T–S Model and Typing Judgments

### 2.1 Representation (R)

We model the static representation as:

1. **Class / trait declarations**

   ```text
   class C α₁ … αₙ where
     op₁ : σ₁
     …
     opₖ : σₖ
   ```

   Possibly with:

   * *laws* (equations, §3),
   * *associated types* (`type F α …`, §5).

2. **Instance declarations**

   ```text
   instance C τ₁ … τₙ where
     op₁ = e₁
     …
     opₖ = eₖ
   ```

   Or with preconditions:

   ```text
   instance D τ ⇒ C (List τ) where …
   ```

3. **Constraint environment**

   Typing judgments now carry *constraints*:

   ```text
   Γ; Δ ⊢ e : τ
   ```

   where, for example:

   * Γ is the usual term environment;
   * Δ is a finite set of constraints such as `C Int`, `D [Bool]`, `Iterator it`.

4. **Implicit dictionary shape**

   For each `C` we can imagine a *dictionary type*:

   ```text
   dictC α₁ … αₙ ≈ { op₁ : σ₁; …; opₖ : σₖ }
   ```

   and each instance corresponds to a specific *dictionary value* of that type.

### 2.2 Transform (T): Constraint Solving + Dictionary Passing

Source-level example:

```text
f : ∀α. C α ⇒ α → α
f x = op₁ x
```

Conceptual desugaring:

1. **Constraint collection**: obtain Δ containing `C α`.

2. **Instance resolution** (cf. M04C17) to determine which instance provides `C τ` when needed.

3. **Dictionary translation**:

   ```text
   f : ∀α. dictC α → α → α
   f d x = d.op₁ x
   ```

4. **Dictionary construction and passing** at call sites, based on resolved instances.

Thus:

> Class/trait constraints are eliminated by a static transform into explicit dictionary parameters in a simpler core language.

### 2.3 Static dimension (S) and pipeline placement

In the phase-clean pipeline (M10C47):

```text
parse → expand → resolve/bind → type + solve_constraints → lower → optimise → codegen
```

Traits/typeclasses sit at:

* **type + solve_constraints**:

  * they need resolved types and instance environment;
  * they must complete *before* lower/optimise/codegen.

Conceptually:

* **R**: declarations, instances, associated types, constraint set Δ.
* **T**: constraint solving + dictionary-passing rewrite (and potentially monomorphization, M04C19).
* **S**: entirely static.

Real compilers often keep some trait metadata in IR for optimisation and diagnostics, but **semantically** the core calculus needs only functions + records.

## 3. Laws, Representation Independence, and Meta-Interfaces

### 3.1 Laws as semantic contracts

Many interfaces are intended to satisfy algebraic laws. Example: a `Monoid`-like interface:

```text
class Monoid α where
  mempty : α
  (<>)   : α → α → α
```

Typical laws:

```text
∀x.       mempty <> x = x
∀x.       x <> mempty = x
∀x y z.   (x <> y) <> z = x <> (y <> z)
```

These are **not** enforced by the type system in typical languages, but they matter:

* They justify **generic theorems** and refactorings.
* They justify **optimisations** that change structure but preserve semantics.

### 3.2 Lawless instances as “type-correct but wrong”

A “method-bundle” instance can be type-correct and semantically wrong.

Example: a pathological monoid on integers:

```text
instance Monoid Int where
  mempty = 0
  x <> y = x            -- ignores y
```

This satisfies the types, but:

* `mempty <> x = 0 <> x = 0` — violates the left identity law,
* generic code expecting the monoid laws (e.g. a balanced `fold`) is no longer sound.

From the type system’s perspective, the instance is fine. From the **meta-interface** perspective, it is broken; you cannot use monoid theorems safely.

Lesson:

> Laws are part of the semantic contract of the interface. If you ignore them, traits/typeclasses collapse back into “bags of methods” and you lose meta-reasoning.

### 3.3 Representation independence with traits

Combine:

* parametricity (M04C16),
* abstract types,
* and **lawful** trait instances.

Set-up:

* A module exposes an abstract type `T` and a trait-based interface:

  ```text
  module M (T, publicOps, publicMonoid) where
    type T      -- abstract
    publicOps   : …
    instance Monoid T where
      mempty = …
      (<>)  = …
  ```

* Clients only see `T` through the `Monoid T` and other exported operations; they cannot see the concrete representation.

If:

* the module maintains **parametricity** (no cheating with unsafe casts / reflection),
* and the `Monoid T` instance satisfies the monoid laws,

then:

> Clients cannot distinguish between different internal representations of `T` that implement the same laws; the trait + laws give you **representation independence**.

You can:

* change `T` from a list-based representation to a balanced tree,
* adjust the `Monoid T` instance accordingly,
* and all client code remains correct, *by construction*.

Traits/typeclasses as **meta-interfaces**:

* summarise the observable behaviour of a family of representations;
* allow you to reason about whole modules and rewrites without knowing the internal data structures.

## 4. Dictionary Passing: Desugaring to a Core Calculus

### 4.1 Source fragment

Schematic code:

```text
class Eq α where
  (==) : α → α → Bool

instance Eq Int where
  (==) = eqInt

equal : ∀α. Eq α ⇒ α → α → Bool
equal x y = x == y
```

Call:

```text
r = equal 3 4
```

### 4.2 Core translation

Define dictionary type:

```text
type dictEq α = { eq : α → α → Bool }
```

Instance as dictionary value:

```text
dictEqInt : dictEq Int
dictEqInt = { eq = eqInt }
```

Translate constrained function:

```text
equal : ∀α. dictEq α → α → α → Bool
equal d x y = d.eq x y
```

Elaborate call:

```text
r = equal @Int dictEqInt 3 4
```

Downstream choices (M04C19):

* **Monomorphize**: generate a specialised version of `equal` for `Int`, potentially inline the dictionary.
* **Shared generics**: keep a single generic `equal` and pass `dictEqInt` at runtime.

Conceptually, this translation:

* removes constraints from the core,
* reduces trait/typeclass usage to ordinary functions + records,
* isolates all meta-work at the static phase.

Real compilers may not literally implement dictionary records, but this model is the right **semantic IR** for reasoning.

## 5. Associated Types / Type Members: Type-Level Functions (Preview)

Many systems extend traits/typeclasses with **associated types** (type members).

Schematic:

```text
class Iterator it where
  type Item it
  next : it → Maybe (Item it)
```

Examples:

```text
instance Iterator IntListIter where
  type Item IntListIter = Int
  next = …

instance Iterator (TreeIter α) where
  type Item (TreeIter α) = α
  next = …
```

Here, `Item` behaves as:

```text
Item : Type → Type
```

– a **type-level function** from implementor type `it` to element type.

R–T–S impact:

* **R**: class declaration now includes type members; constraints include equalities like `Item it ~ τ`.
* **T**: constraint solving must handle both trait membership (`Iterator it`) and type equality / family reduction (`Item (TreeIter α) ~ α`).
* **S**: still static, but you now have a simple type-level language inside the trait system.

This is exactly the bridge to **M05C22**:

> As soon as you let associated types appear in equalities and constraints, you have **type-level functions**. You have entered the first layer of type-level programming, not “just” nicer traits.

Used moderately, associated types cleanly express relationships between types in an interface. Used aggressively, they become a general type-level toolbox and push you toward Tier-3/4.

## 6. Coherence, Overlaps, Orphans

Trait/typeclass systems inherit and amplify the resolution issues from M04C17.

### 6.1 Coherence (revisited)

We want:

* For each pair `(C, τ)` (class + type arguments), at most one **semantically active** instance in any well-typed program.
* The resolution algorithm always chooses that instance for all obligations `C τ`.

Violations:

* Multiple different `C τ` instances reachable through different imports or modules.
* Overlapping instances where a local heuristic (e.g. “last defined wins”) picks one.

Coherence is a **global** contract between:

* the set of instances,
* and the resolution algorithm.

### 6.2 Overlapping instances and “more specific”

Abstract example:

```text
class Show α where
  show : α → Text

instance Show [α]    where …
instance Show [Char] where …
```

For `τ = [Char]`:

* both instance heads apply:

  * `C [α]` with `α = Char`,
  * `C [Char]` directly.

Intuitively, `Show [Char]` is **more specific** than `Show [α]`:

* every type that matches `Show [Char]` also matches `Show [α]`,
* but not vice versa.

A system that allows overlapping instances needs a well-founded notion of “more specific” (e.g. instance-head pattern inclusion) and a rule:

* “If exactly one instance is strictly more specific than all others, choose it; otherwise, fail.”

Anything weaker and you’re in “whatever happens to win” territory: Tier-3/4.

### 6.3 Orphan instances and trade-offs

An **orphan instance** is an instance defined in a module that defines *neither*:

* the class/trait, nor
* the implementing type.

Example:

* class `Ord` is defined in library `A`,
* list type `[α]` is defined in library `B`,
* you define `instance Ord [α]` in `C`, which owns neither.

If another module `D` also defines `Ord [α]`, you have:

* two incompatible candidates for `Ord [α]`,
* behaviour depending on:

  * which module is imported,
  * or link order,
  * or build configuration.

This destroys global coherence.

**Orphan rules** restrict this:

* You may only define instances when you own at least one of:

  * the class/trait,
  * or the type.

Effect:

* You sacrifice some extensibility:

  * you can’t retroactively attach arbitrary foreign traits to foreign types anywhere.
* You gain predictability:

  * the `(C, τ)` pair has one legitimate implementation “owner”.

This is an explicit WSM choice:

> Give up some expressive power to avoid Tier-3 “global puzzle” behaviour.

### 6.4 Instance graphs and diamonds

Instances can themselves have **preconditions**:

```text
instance Monoid α ⇒ Monoid (List α) where …
```

Resolving `Monoid (List Int)` may require:

* finding `Monoid Int`,
* then applying the list instance.

You can get **diamond** situations:

* multiple derivation paths for the same obligation `C τ`,
* possibly producing different dictionaries or expectations.

If you combine:

* rich constraints,
* overlapping instances,
* liberal orphan rules,

then instance resolution is a non-trivial search problem:

* potential non-termination,
* ambiguous or context-dependent choices,
* poor error locality.

That is exactly what pushes traits/typeclasses toward a **type-level meta-language** (Tier-3/4), rather than a simple interface layer.

## 7. WSM/Tiers: Traits as Meta-Interfaces vs Type-Level Meta-Language

Using the WSM/Tier lens (M01C04–C05):

### 7.1 Tier-2: Traits/typeclasses as disciplined meta-interfaces

Traits/typeclasses are in **Tier-2** when:

* Interfaces are small, well-scoped, and come with clear laws.
* Instance graphs are shallow; instance resolution is simple and predictable.
* Overlaps are forbidden or tightly controlled with a clear notion of “more specific”.
* Orphan instances are restricted (or disallowed).
* Associated types are used to express simple relationships, not arbitrary logic.
* “Which implementation runs here?” can be answered locally without simulating a solver.

Realistic note:

* Many codebases *aim* for this but occasionally dip into more complex patterns.
* That is acceptable if those parts are clearly isolated as “advanced infrastructure” and treated with extra discipline.

### 7.2 Tier-3/4: Trait/typeclass layer as type-level meta-language

Traits/typeclasses drift into **Tier-3/4** when:

* Constraints encode **complex logic** (essentially theorem-proving in the typechecker).
* Instance graphs are deep and recursive.
* Overlaps and orphans are routinely used.
* Associated types / families encode non-trivial algorithms.
* Resolution is effectively **logic programming** at the type level.

Symptoms:

* Tiny library changes cause large, opaque type errors.
* Behaviour depends on imports and the precise instance set in scope.
* Understanding a line of code requires mentally simulating constraint solving and instance search.

M04C20 will make this explicit:

> In these regimes, trait/typeclass resolution *is* constraint solving and search; it functions as a meta-language embedded in the type system.

Design rule:

> Treat trait/typeclass usage as Tier-2 by default. If you *consciously* build a type-level meta-framework using traits, isolate it and accept you are operating in Tier-3/4.

## 10. Glossary

* **Trait / typeclass / concept**
  Interface over types: a named collection of operations (and usually laws) parameterised by type variables, with instances providing concrete implementations.

* **Instance / impl**
  A definition that realises a trait/typeclass for specific type arguments.

* **Constraint**
  Requirement that a trait/typeclass hold for a type, written `C τ` or `C τ ⇒ …` in type signatures; collected in the constraint environment Δ.

* **Dictionary**
  A record value representing an instance of a trait/typeclass, containing concrete implementations of its operations.

* **Dictionary passing**
  Translation that converts constrained polymorphic functions into functions with explicit dictionary parameters.

* **Lawful instance**
  Instance that satisfies the intended algebraic laws of its trait/typeclass, enabling equational reasoning and sound generic optimisations.

* **Meta-interface**
  Trait/typeclass treated not just as a method bundle, but as a structured, law-governed abstraction supporting representation independence and generic theorems.

* **Associated type / type member**
  Type-level component attached to a trait/typeclass, behaving as a type-level function from implementing types to result types.

* **Coherence**
  Global property that each (class, type) pair has at most one active instance and resolution always chooses that instance.

* **Overlapping instances**
  Instances whose applicability sets intersect so that more than one instance can satisfy the same constraint.

* **Orphan instance**
  Instance declared in a module that defines neither the class/trait nor the implementing type; threatens coherence and modular reasoning.

* **Tier-2 trait usage (WSM)**
  Disciplined use of traits/typeclasses as coherent, lawful meta-interfaces with shallow instance graphs and predictable resolution.

* **Tier-3/4 trait usage (WSM)**
  Use of traits/typeclasses as a powerful type-level logic or meta-language, with complex instance search, overlaps, and orphans, leading to global complexity.

## 11. Rust Case Study – Traits in Practice (Primary Implementation Language)

Rust will be the main implementation language in this series, so we look at how the abstract model materialises there.

### 11.1 Traits and bounds

Basic trait:

```rust
trait Eq {
    fn eq(&self, other: &Self) -> bool;
}
```

Impl:

```rust
impl Eq for i32 {
    fn eq(&self, other: &Self) -> bool {
        self == other
    }
}
```

Generic function with a trait bound:

```rust
fn equal<T: Eq>(x: &T, y: &T) -> bool {
    x.eq(y)
}
```

Mapping to the abstract model:

* `Eq` is a trait `Eq T` with op `eq : &T → &T → bool`.
* `impl Eq for i32` is an instance `Eq i32`.
* `fn equal<T: Eq>` is `∀T. Eq T ⇒ &T → &T → bool`.

### 11.2 Dictionary-passing mental model

Rust does not literally implement traits by passing a `struct` dictionary everywhere. But for semantics, you can model:

```rust
struct EqDict<T> {
    eq: fn(&T, &T) -> bool,
}

fn equal_desugared<T>(d: &EqDict<T>, x: &T, y: &T) -> bool {
    (d.eq)(x, y)
}
```

Instances:

```rust
fn eq_i32(x: &i32, y: &i32) -> bool { x == y }

static EQ_I32: EqDict<i32> = EqDict { eq: eq_i32 };
```

A call like:

```rust
let r = equal(&3, &4);
```

can be reasoned about as:

```rust
let r = equal_desugared(&EQ_I32, &3, &4);
```

The compiler will actually use monomorphization and inlining; but:

> This “dictionary passing” view is the right IR for understanding traits as semantic meta-interfaces, especially when we discuss specialisation and trait objects.

### 11.3 Coherence and orphan rules in Rust

Rust enforces coherence:

* For each `(Trait, Type)` pair, at most one `impl Trait for Type` is allowed in the entire program (modulo specialisation and crate boundaries).
* Rust’s **orphan rules** are the concrete form of §6.3:

  * You can implement a *foreign trait* for a *local type*.
  * Or a *local trait* for a *foreign type*.
  * But you cannot implement a foreign trait for a foreign type.

This is exactly the “you must own at least one side” rule:

* prevents two independent crates from inventing conflicting `impl Trait for Type`;
* preserves global coherence of trait resolution.

Rust also restricts overlapping impls:

* Blanket impls and more specific impls must be carefully controlled (with the unstable specialisation feature).
* Aim: avoid ambiguous or context-dependent resolution.

This is the concrete manifestation of:

* **No arbitrary overlaps**, or only under precise “more specific” semantics;
* **No orphans** without ownership.

### 11.4 Associated types in Rust

Rust traits support associated types, directly matching §5:

```rust
trait Iterator {
    type Item;

    fn next(&mut self) -> Option<Self::Item>;
}
```

Impl:

```rust
struct IntIter { /* ... */ }

impl Iterator for IntIter {
    type Item = i32;

    fn next(&mut self) -> Option<Self::Item> {
        // ...
    }
}
```

Abstract mapping:

* `Iterator` is a class `Iterator it` with a type member `Item it : Type`.
* Constraints include `T: Iterator` and equalities involving `T::Item`.

Rust’s trait solver must:

* handle both membership (`T: Iterator`) and type equality constraints (`T::Item = i32`),
* combine this with other trait bounds and lifetimes.

This is a concrete, industrial example of associated types as **type-level functions attached to traits**.

### 11.5 WSM/Tiers in Rust trait usage

**Tier-2 Rust trait usage:**

* Small, coherent traits (`Display`, `Clone`, `Iterator`).
* Lawful semantics (e.g. `Ord` respecting ordering axioms).
* Controlled use of `where` bounds and associated types.
* Respect for coherence and orphan rules.
* Resolution that remains local and predictable.

**Tier-3/4 Rust trait usage:**

* Extremely complex trait bounds (“logic programming in trait solver”).
* Deeply nested `where` clauses with multiple associated type equalities.
* Heavy blanket impls and specialisation patterns.
* Traits and associated types used as a general type-level DSL.

Symptoms:

* error messages that effectively encode small proofs,
* behaviour sensitive to subtle changes in impl sets or bounds,
* need to “run the trait solver in your head” to understand basic calls.

Course stance:

> Use Rust traits primarily as Tier-2 meta-interfaces.
> Treat “trait-solver-as-logic-engine” as specialised infrastructure, to be contained and documented, not normal application style.

## 12. Python Case Study – Protocols and ABCs (Short)

Python offers trait-like facilities mostly at runtime, with optional static checking via type hints.

### 12.1 Protocols

Using a type checker (e.g. `mypy`) you can define **protocols**:

```python
from typing import Protocol

class SupportsEq(Protocol):
    def __eq__(self, other: object) -> bool: ...
```

Any type with a compatible `__eq__` satisfies `SupportsEq` **structurally**.

Mapping to the abstract model:

* **R**: protocol definition + method signatures.
* **T**: type-checker enforces structural compatibility; no global instance environment.
* **S**: static analysis only; runtime Python does not know about protocols.

Coherence / overlaps / orphans:

* not enforced; protocols are advisory constraints.
* Multiple types may “accidentally” satisfy the same protocol; there is no notion of a unique instance.

### 12.2 ABCs (Abstract Base Classes)

Python **ABCs**:

* define abstract methods at runtime,
* allow concrete classes to subclass and/or register.

ABCs can be used to express “this class supports foo() and bar()”.

In WSM terms:

* Protocols/ABCs are **runtime meta** with a thin static veneer.
* They do not implement a coherent, global trait/typeclass layer.
* They are useful, but operate far from the strongly-typed, Tier-2 meta-interface regime.

## 13. C++ Case Study – Concepts (Short)

C++ **concepts** are static constraints on template parameters.

Example:

```cpp
template<typename T>
concept EqualityComparable =
  requires(T a, T b) {
    { a == b } -> std::convertible_to<bool>;
  };

template<EqualityComparable T>
bool equal(T a, T b) {
  return a == b;
}
```

* A concept describes required expressions and their types.
* A template parameter is accepted if instantiation satisfies those requirements.

Mapping to the abstract model:

* **R**: concepts, template signatures, available overloads.
* **T**: template argument deduction + concept satisfaction + overload resolution (M04C17).
* **S**: entirely static; no runtime dictionary.

Differences from the ideal typeclass model:

* No explicit dictionaries; satisfaction is *structural* over expressions.
* Laws are informal; no enforcement.
* Coherence is not guaranteed; ADL, partial ordering, and specialisation can produce surprising choices.

Concepts significantly improve **error reporting** and let you state intent. They do **not** magically downgrade heavy template metaprogramming from Tier-3 to Tier-2:

> Concepts make Tier-3 C++ template meta *less opaque*,
> they do not turn it into a clean, globally coherent trait/typeclass layer.

They are best used as:

* constraints that guard templates,
* documentation of intent and readable preconditions,

not as the foundation of a large type-level logic system—unless you are consciously building such a meta-framework and prepared to pay the complexity cost.
