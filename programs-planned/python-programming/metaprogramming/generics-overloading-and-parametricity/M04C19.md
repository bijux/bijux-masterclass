# M04C19 – Monomorphization vs Shared Generics

---

## 0. Learning Objectives

After this core you should be able to:

1. State the **ideal semantic model** of generics (System F style), and list the concrete assumptions under which different implementation strategies are **contextually equivalent**—and where real languages deliberately break those assumptions.
2. Describe **monomorphization** (“copy per instantiation”) vs **shared/erased generics** (“one body with uniform representation/indirection”), and recognise the richer design space (representation polymorphism, JIT specialisation, shape vs layout polymorphism).
3. Formulate **monomorphization** and **erasure** as explicit **R–T–S transforms** from a polymorphic IR to:

   * a family of monomorphic functions (Tᵐ),
   * or a single representation-polymorphic body plus boxing/dictionaries (Tᵉ),
     and clearly separate these semantic transforms from later optimisations.
4. Build simple **cost/budget models** for generics, relating:

   * number of instantiations and body size to compile-time and code size,
   * shared/erased strategies to runtime overhead.
5. Analyse how **traits/typeclasses/dictionaries** interact with monomorphization and erasure, including:

   * dictionary-passing and inlining,
   * **witness explosion** and when it actually occurs,
   * forced sharing via trait objects/dynamic interfaces.
6. Connect monomorphization to **staging and specialisation** (M06C28–30) by viewing it as static partial evaluation over type arguments and understanding **instantiation explosion** as a concrete instance of **stage/specialisation explosion**.
7. Place generics in the **WSM/Tier** framework:

   * Tier-1/2: controlled specialisation, bounded costs, generics as “zero-cost abstraction” in practice;
   * Tier-3/4: generics as a powerful static meta-language with uncontrolled instantiation and systemic compile-time/binary problems.
8. Map the theory onto real languages:

   * **Rust** (primary case): MIR-level generics, monomorphization, traits and trait objects,
   * **Python**: dynamic semantics, effectively always shared/erased,
   * **C++**: templates as a monomorphizing meta-language.

## 1. Ideal Semantics vs Real Leaks

### 1.1 System F baseline

In the clean theoretical picture (System F):

```text
id : ∀α. α → α
id = Λα. λ (x : α). x

id @Int 3   ⇝β   3
```

* There is one semantic object `id`.
* Type abstraction/application (Λ/ @) and value abstraction/application (λ / application) are logical constructs.
* Implementation is required to be **semantics-preserving**: any compiled program is contextually equivalent (M02C10) to its System F meaning.

Implicit assumptions:

* No reflection on generic instantiations.
* No visibility of code layout, symbol names, or function addresses as stable “values of interest”.
* Performance and binary size are *not* part of the semantic contract.

Under those observables, different implementation strategies for generics are **contextually equivalent**.

### 1.2 How real languages break the glass

Real languages intentionally relax these assumptions:

1. **Reflection / introspection / RTTI**

   * C++: different template instantiations have distinct symbols, addresses, and debug info.
   * JVM/Java: generic signatures and erased types are visible through reflection APIs; `instanceof` and `getGenericSuperclass` expose erasure.
   * Stack traces and profilers expose which instantiations exist and where they execute.

2. **Binary size and memory footprints as “soft semantics”**

   * Embedded systems, kernels, and WASM environments treat code size and memory usage as part of the specification.
   * A “semantics-preserving” change that doubles code size may still be unacceptable.

3. **Performance contracts**

   * APIs often have implicit or explicit complexity/latency expectations.
   * Implementation strategies for generics (monomorphization vs sharing) directly affect constant factors, cache behaviour, warmup time, etc.

In this core we:

* keep the System F view as the **semantic reference model**;
* but treat implementation strategy and its leaks as a **first-class design dimension**, not an accidental detail.

## 2. Two Extremes: Monomorphization vs Shared/Erased Generics

We start with the textbook extremes, then refine.

### 2.1 Monomorphization (clone per instantiation)

Polymorphic IR:

```text
f : ∀α. σ[α]
f = Λα. λ (x : α). body[α, x]
```

Instantiation sites:

```text
… f @τ₁ e₁ …
… f @τ₂ e₂ …
```

**Monomorphization transform** (T^m) (at IR level):

For each `τ` in the set of discovered instantiations `Inst(f)`:

```text
f_τ : σ[τ]
f_τ = λ (x : τ). body[τ, x]

f @τ e  ↦  f_τ e
```

Properties:

* T^m is intended to be **semantics-preserving** relative to the ideal model: programs before and after T^m are contextually equivalent (ignoring reflection and performance).
* After T^m, the polymorphic `f` never appears in IR; only monomorphic `f_τ`.

Advantages:

* Each `f_τ` sees concrete types; optimisers can:

  * unbox values,
  * constant-fold type-dependent branches,
  * vectorise or layout-specialise,
  * inline aggressively.

Costs (conceptual):

* Code size:

  ```text
  size_mono ≈ Σ_{τ ∈ Inst(f)} size(f_τ)  ≈ |Inst(f)| × size(f)  (crude model)
  ```

* Compile-time:

  ```text
  compile_mono ≈ Σ_{τ ∈ Inst(f)} opt_cost(f_τ)
  ```

where `opt_cost` grows with body complexity.

The core risk is **instantiation explosion**: `|Inst(f)|` becoming large, especially under nested generics.

### 2.2 Shared / erased generics (one body + uniform representation)

At the other extreme, we **share** one implementation across type arguments using a **uniform runtime representation** `Rep`.

Toy erasure transform (T^e):

```text
f : ∀α. σ[α]
f = Λα. λ (x : α). body[α, x]
```

becomes:

```text
f_erased : Rep → Rep
f_erased = λ (x : Rep). body_erased[x]
```

Call sites:

```text
f @τ e  ↦  unrep_τ (f_erased (rep_τ e))
```

* `Rep` is an abstract “uniform representation” (machine word, pointer, tagged value, etc.).
* `rep_τ` / `unrep_τ` are boxing/unboxing or (in ML-style runtimes) tagging/untagging functions.

For constrained functions (M04C18):

```text
g : ∀α. C α ⇒ σ'[α]
```

core dictionary form:

```text
g_core : ∀α. dictC α → τ_val[α] → τ_ret[α]
g_core = Λα. λ (d : dictC α) (x : τ_val[α]). body'[α, d, x]
```

After erasure of *value-level* types:

```text
g_erased : ∀α. dictC α → Rep → Rep
g_erased = Λα. λ (d : dictC α) (x : Rep). body'_erased[α, d, x]
```

At runtime:

* `α` is not available as a first-class value;
* each `dictC α` carries all method implementations needed for that `α` and knows enough about representation to interpret `Rep` correctly.

**Important:**
We do **not** replace `dictC α` by something like `dictC Rep`. The dictionary remains logically indexed by `α`; we simply compile it to some concrete runtime structure (often vtable-like).

Advantages of shared/erased:

* Code size and compile-time:

  ```text
  size_shared ≈ Σ_f size(f_erased)
  compile_shared ≈ Σ_f opt_cost(f_erased)
  ```

independent of `|Inst(f)|`.

* Works well with separate compilation and stable ABIs.

Costs:

* Per-call overhead for `rep_τ / unrep_τ` and possibly dictionary/trait dispatch.
* Fewer automatic layout-specific optimisations.

### 2.3 Representation polymorphism vs heap boxing

The “Box everything” picture is **pedagogical**, not realistic:

* Many runtimes use **representation polymorphism**:

  * most values are pointers with a few tagged cases (e.g. small ints),
  * generic code manipulates `Rep` uniformly without explicit user-visible boxing.
* Boxing as “heap allocation” is one *implementation* of `Rep`, not the definition.

We’ll stick to `Rep` as the abstraction:

* think “whatever uniform representation your core IR/runtime uses”,
* treat `rep_τ` / `unrep_τ` as coercions between source-level types and `Rep`.

## 3. Beyond the Cartoon: Shape vs Layout, Static vs JIT

### 3.1 Shape polymorphism vs layout polymorphism

Two useful dimensions:

1. **Shape polymorphism**

   * Values share a representation *class* (pointer-sized, aligned, GC-managed).
   * Generic code can be shared across many types because they all inhabit the same `Rep`.
   * This is what erased/shared generics normally exploit.

2. **Layout polymorphism**

   * Code is specialised to the exact memory layout of types (e.g. unboxed `struct { double x, y; }` vs `struct { int x; }`).
   * Monomorphization can target layout, not just shape.

Some languages/compilers:

* do monomorphization only until a “shape frontier” (e.g. unboxed primitives vs heap refs),
* share code for layouts that fit the same shape.

### 3.2 Static vs JIT specialisation

Static toolchains (Rust, C++):

* make mono vs shared decisions during compilation and link-time,
* optionally perform LTO-level specialisation,
* must live with the result in the final binary.

Managed/JITted environments (JVM, .NET, JS engines):

* start with shared/erased implementations,
* perform **profile-guided specialisation**:

  * specialise hot call sites for prevalent types,
  * treat “actual type at hot site” as static for the specialised version,
  * deoptimise back to the generic body if assumptions break.

From our point of view:

* Monomorphization is **offline** specialisation over type parameters.
* JIT specialisation is **online** specialisation over runtime-observed types (and sometimes values).
* Both are instances of the same pattern as partial evaluation (M06C28), with the same explosion risks (M06C30); only the timing differs.

## 4. R–T–S and Instantiation Discovery

### 4.1 Representation (R)

Polymorphic IR (System F + dictionaries) contains:

* polymorphic definitions:

  ```text
  f : ∀α. σ[α]
  f = Λα. λ (x : α). body[α, x]

  g : ∀α. C α ⇒ σ'[α]
  g = Λα. λ (d : dictC α) (x : τ_val[α]). body'[α, d, x]
  ```

* instantiation sites, which may be:

  * **explicit** (`f @Int e`),
  * or **implicit**, inferred from usage (e.g. `f 3` where type inference concludes `α = Int`).

Crucially:

* determining the set `Inst(f)` is not purely syntactic in languages with inference:

  * type inference and constraint solving (M04C20) jointly determine which `τ` actually appear,
  * inlining and specialisation passes can later expose *more* instantiations.

So in practice, “R” for monomorphization includes:

* polymorphic IR,
* plus the current **approximation** of `Inst(f)` derived from type+constraint analysis.

### 4.2 Transform (T): Tᵐ (mono) vs Tᵉ (erasure)

We separate:

* **semantic transforms** Tᵐ/Tᵉ (change the shape of the program in IR),
* subsequent **optimisations** (constant folding, inlining, etc.).

**Monomorphization Tᵐ** (schematic):

For each polymorphic `f` and each `τ ∈ Inst(f)`:

```text
T^m(f, τ):
  introduce f_τ : σ[τ]
  f_τ = λ (x : τ). body[τ, x]

  replace all f @τ e by f_τ e
```

For constrained `g`:

```text
T^m(g, τ):
  introduce g_τ : dictC τ → τ_val[τ] → τ_ret[τ]
  g_τ = λ (d : dictC τ) (x : τ_val[τ]). body'[τ, d, x]

  replace g @τ e by g_τ dictC_τ e
```

**Erasure/shared Tᵉ** (schematic):

For `f`:

```text
f : ∀α. σ[α]
  ↦  f_erased : Rep → Rep
      f_erased = λ (x : Rep). body_erased[x]

f @τ e  ↦  unrep_τ (f_erased (rep_τ e))
```

For `g`:

```text
g : ∀α. C α ⇒ σ'[α]
  ↦  g_erased : ∀α. dictC α → Rep → Rep
      g_erased = Λα. λ (d : dictC α) (x : Rep). body'_erased[α, d, x]

g @τ e  ↦  unrep_τ (g_erased @τ dictC_τ (rep_τ e))
```

Here:

* the *code* for `g_erased` may be shared across `α`, possibly after dropping `α` from the runtime representation;
* each `dictC_τ` is still specific to `τ`.

### 4.3 Static dimension (S)

After Tᵐ or Tᵉ:

* The IR is:

  * monomorphic (Tᵐ), or
  * representation-polymorphic with explicit conversions/dictionaries (Tᵉ).

* Subsequent passes (M11C52) operate on this IR:

  * optimisation,
  * codegen,
  * linking.

The choice of Tᵐ vs Tᵉ (or a hybrid) is:

* a **static meta decision** about where work happens (compile-time vs runtime),
* a key driver of compile-time, code size, and runtime cost.

## 5. Simple Cost Models

We want rough models, not precise accounting.

Let:

* `F` be the set of polymorphic functions.
* For `f ∈ F`:

  * `Inst(f)` is the set of instantiations that actually occur in the final program.
  * `size(f)` is an approximate IR size of `f` pre-specialisation.
  * `opt_cost(f)` is an approximate cost of optimising `f` once.

We assume `size(f_τ)` is bounded by a small multiple of `size(f)` after Tᵐ, and similar for `opt_cost`.

### 5.1 Monomorphization

Code size:

```text
size_mono ≈ Σ_{f ∈ F} Σ_{τ ∈ Inst(f)} size(f_τ)
         ≈ Σ_{f ∈ F} |Inst(f)| × size(f)   (coarse upper bound)
```

Compile-time (for monomorphised bodies):

```text
compile_mono ≈ Σ_{f ∈ F} Σ_{τ ∈ Inst(f)} opt_cost(f_τ)
```

Scaling pressure:

* large/complex `f`,
* large `|Inst(f)|`,
* deep generic nesting that multiplies combinations.

Some instances may shrink under optimisation; we treat `size(f)` and `opt_cost` as upper bounds to keep the model simple.

### 5.2 Shared/erased generics

Code size:

```text
size_shared ≈ Σ_{f ∈ F} size(f_erased)
```

Compile-time:

```text
compile_shared ≈ Σ_{f ∈ F} opt_cost(f_erased)
```

Independent of instantiation count.

Runtime overhead per call involves:

```text
overhead_shared(call to f @τ) ≈ cost(rep_τ) + cost(unrep_τ) + cost(indirection/dict lookup)
```

Net trade-off:

* monomorphization: more static cost, less dynamic cost;
* shared: less static cost, more dynamic cost.

M10C49 will turn this into a systematic **meta-budget**; here we fix the scaling intuitions.

## 6. Traits/Typeclasses and Witness Explosion

### 6.1 Dictionaries as witnesses

From M04C18:

```text
class Ord α where compare : α → α → Ordering

sort : ∀α. Ord α ⇒ List α → List α
```

Core dictionary form:

```text
sort_core : ∀α. dictOrd α → List α → List α
sort_core = Λα. λ (d : dictOrd α) (xs : List α). body[α, d, xs]
```

Each `dictOrd α` is a **witness** that `Ord α` holds, carrying method implementations and possibly additional structure.

### 6.2 Where witness explosion actually happens

Under monomorphization:

* we create `sort_τ : dictOrd τ → List τ → List τ` for each instantiation `τ`,
* and **inline** or optimise `dictOrd τ` into the body when possible.

The number of *distinct* specialisations can be driven by:

1. **Distinct types `τ`**: obvious dimension.

2. **Distinct composite constraints**:

   * `sort` may be used in larger constrained contexts (`Ord τ, Show τ, Eq τ, ...`),
   * the compiler may generate different specialisations based on different compositions of evidence (e.g. derived vs manually written).

3. **Overlaps/orphans (language-dependent)**:

   * In languages that permit overlapping instances and orphans (e.g. Haskell with pragmas), there can be multiple *legally distinct* ways to satisfy `Ord τ` depending on imports and instance resolution.
   * Under monomorphization, distinct paths to dictionaries can induce distinct `sort_τ^{w}` variants.

In **coherent, non-overlapping systems** (Rust-style:

* “at most one `impl Trait for Type` globally”):

* for a fixed `(Trait, Type)` pair there is essentially one canonical dictionary,

* witness explosion is mainly driven by composite constraints and generic context, not multiple competing instances.

In more permissive systems (Haskell with overlapping instances, logic-programming style resolution):

* the space of witness paths is larger,
* and genuine `f_τ^{w1}, f_τ^{w2}, …` variants can arise even for the same `τ`.

### 6.3 Trait objects and forced sharing

Trait objects / existential wrappers (`dyn Trait`, `exists α. C α ∧ α`) force a **shared** regime:

* calls are routed through a dictionary/vtable pointer stored in the object,
* the callee cannot specialise on `α` anymore.

Effects:

* On hot paths, accidental use of trait objects can:

  * disable monomorphization,
  * reduce inlining and constant propagation,
  * introduce pointer chasing and branch mispredictions.

* On the other hand, trait objects can:

  * reduce code size and I-cache pressure by sharing implementations,
  * improve performance for large codebases where I-cache misses dominate over call overhead.

The trade-off is architectural:

> APIs that expose `T: Trait` are invitations to monomorphization; APIs that expose `dyn Trait` are invitations to shared/dynamic dispatch.

## 7. Monomorphization as Staging / Specialisation

M06C28/30 defined **staging** and **partial evaluation**:

* treat some inputs as **static** (known at specialisation time),
* others as **dynamic** (only known at runtime),
* specialise code with respect to static parts.

For generics:

* type parameters are natural **static** inputs,
* runtime values are **dynamic**.

A simple binding-time view:

```text
f : ∀α. α → α
f = Λα. λ (x : α). x
```

Binding-time annotations (schematic):

```text
α   : static
x   : dynamic
f   : static → (dynamic → dynamic)
```

Monomorphization:

* specialises `f` at static `α = Int`, `α = Bool`, etc.,
* producing `f_Int`, `f_Bool` as residual dynamic functions.

This is exactly an **offline partial evaluation** of `f` with respect to type arguments.

Same pattern appears in JIT specialisation:

* static dimension: current “assumed type” and sometimes runtime-constant values at hot sites,
* dynamic dimension: remaining value variation,
* risk: specialising on too many “static” aspects leads to **specialisation explosion**.

Monomorphization is therefore:

> a particular, type-driven form of staging. If you ignore budgets, you get the same kind of blow-ups as with over-aggressive staging or partial evaluation (M06C30).

## 8. Meta-Budgeting for Generics

We now turn cost intuitions into simple policy knobs.

### 8.1 Budget parameters

Examples:

* `max_inst_per_fn` – soft limit on `|Inst(f)|` per function.
* `max_generic_code_ratio` – upper bound on `size_mono / size_shared_baseline`.
* `max_specialisation_depth` – bound on generic nesting depth subject to monomorphization.

These define a **meta-budget**:

* how much compile-time and code size you are willing to spend on generics.

### 8.2 Policy sketches

Sample policy:

1. For each `f`, track `|Inst(f)|`.

   * If `|Inst(f)| ≤ max_inst_per_fn`, monomorphize normally.
   * If `|Inst(f)|` exceeds the limit:

     * stop generating new `f_τ` variants,
     * redirect further instantiations to a shared/erased fallback `f_shared`.

2. Track cumulative `size_mono` estimate.

   * If it exceeds `max_generic_code_ratio × size_shared_baseline`:

     * emit warnings for functions with largest `|Inst(f)| × size(f)`,
     * encourage users to add annotations or refactor.

3. For “deep” generic stacks (combinator-heavy code), allow explicit opt-outs:

   * attributes to force “always shared” for some functions,
   * or conversely “always mono” for known hot cases.

Such policies deliberately trade some potential performance for **predictability**.

### 8.3 Tier classification via budgets

Within WSM/Tiers:

* **Tier-1/2 generics**:

  * default policies keep most code well within budget,
  * explosions require pathological patterns or explicit opt-in,
  * tooling exposes instantiation counts and generic hot spots.

* **Tier-3/4 generics**:

  * “normal” generic usage can easily violate budgets,
  * build times and binary size are structurally fragile,
  * users routinely fight template/generic bloat without clear guidance.

Unbudgeted monomorphization is the generic analogue of unbounded macro power.

## 9. WSM/Tiers and Real Failure Modes

### 9.1 Tier-1/2 – generics as controlled meta

Characteristics:

* Monomorphization is targeted:

  * common small functions and data structures,
  * performance-sensitive abstractions.
* Erased/shared generics (or trait objects) are used:

  * for cold paths,
  * across subsystem boundaries,
  * when code size is critical.
* Diagnostic and profiling tools:

  * report instantiation counts,
  * attribute build time and binary size to generic code.

Generics behave as intended: **zero-cost abstraction in the common case**, with costs visible and bounded.

### 9.2 Tier-3/4 – generics as static meta-language

Symptoms:

* Binaries routinely reach hundreds of MB due to template/generic bloat.
* Single changes in deeply generic code cause multi-minute rebuilds.
* Call stacks in perf/build profiles are dominated by generic instantiation and optimisation.
* Simple combinator libraries for collections, async, or functional programming cause dense layers of monomorphized variants.

This is structurally analogous to:

* overpowered macro systems (M10C46),
* unconstrained staging (M06C30).

Generics here are not “just an abstraction”; they are a **full-blown static meta-language**, and must be treated as such in language and library design.

## 12. Glossary

* **Monomorphization**
  A semantics-preserving transform that replaces polymorphic functions with a family of monomorphic specialisations for each used type instantiation and rewrites call sites accordingly.

* **Erased / shared generics**
  A compilation strategy where type parameters are removed from value positions and a single generic implementation operates on a uniform runtime representation `Rep`, with `rep_τ`/`unrep_τ` conversions and optional dictionary/trait dispatch.

* **Representation polymorphism**
  Implementation technique in which most values share a uniform low-level representation (e.g. heap pointer or tagged word), enabling shared generic code without explicit user-level boxing.

* **Layout polymorphism**
  Specialisation of code to the concrete memory layout of types, enabling unboxed storage and layout-specific optimisations.

* **Dictionary / witness**
  A structure (explicit or implicit) that carries implementations of trait/typeclass methods and serves as evidence that a constraint (e.g. `C α`) holds.

* **Instantiation explosion**
  Rapid growth in the number of monomorphized specialisations as generics are instantiated at many type combinations, often compounded by deep generic nesting.

* **Witness explosion**
  Growth in the number of specialised variants not only over type arguments but over distinct ways of satisfying constraints (different dictionary compositions and paths), especially in the presence of overlaps/orphans.

* **Meta-budget (for generics)**
  Explicit limits and policies governing compile-time and code-size expenditure on generic instantiations and specialisation.

* **Tier-1/2 vs Tier-3/4 generics (WSM)**
  Tier-1/2: generics as controlled meta with bounded specialisation and predictable cost;
  Tier-3/4: generics as a static meta-language with uncontrolled instantiation and systemic build/binary pathologies.

## 13. Rust Case Study (Primary) – MIR Generics and Monomorphization

Rust is a concrete, relatively clean example of a mostly-monomorphizing design.

### 13.1 Pipeline placement

Conceptually:

```text
parse → expand (macros) → name resolution → type/trait checking
     → build polymorphic MIR
     → monomorphization (MIR-level T^m)
     → LLVM IR + optimisation → codegen → binary
```

* Generics exist at the MIR level as polymorphic functions with type and trait parameters.
* Monomorphization clones MIR bodies for each used combination of type arguments and trait bounds.
* Trait bounds (`T: Trait`) are translated into implicit dictionary-like parameters at MIR, then usually inlined away after Tᵐ.

### 13.2 Consequences

Advantages:

* Specialised MIR leads to tight LLVM IR:

  * static dispatch for trait methods under generic bounds,
  * unboxed and layout-specialised code when possible.
* Idiomatic abstractions (iterators, futures, generic collections) compile down to efficient code.

Costs:

* Generic-heavy crates (iterator/futures combinators, numeric libraries) can cause **instantiation explosion**:

  * many `f_τ` variants,
  * large binaries,
  * long optimising codegen phases.
* Changes in widely used generic functions can heavily impact compile times.

Rust is explicit about this trade-off:

* you get powerful zero-cost abstractions,
* but you must manage **generic meta-budget** and code size yourself,
* tooling (e.g. `cargo bloat`, build profiling) helps attribute costs to generics.

### 13.3 Trait bounds vs trait objects

Rust offers:

* **Static trait bounds** (`T: Trait`):

  * monomorphized generics,
  * best performance when types are known,
  * worst code size in heavily generic code.

* **Trait objects** (`dyn Trait`):

  * shared code + vtable dispatch,
  * lower code size and clearer ABI boundaries,
  * weaker auto-optimisation of hot loops.

API design in Rust is therefore partly:

> Choosing where the type system exposes monomorphization and where it forces shared interfaces.

## 14. Python Case Study – Dynamic Generics as “Always Shared”

Python’s runtime:

* values are heap-allocated objects with runtime type information,
* functions are implicitly polymorphic and perform type checks at runtime.

Type annotations (`typing`, `Generic`, etc.):

* are used by static analysers and IDEs,
* are erased at runtime (modulo introspection on annotations themselves).

For generics:

```python
from typing import TypeVar, Generic

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value
```

* At runtime, there is exactly one `Box` class.
* All instances share the same implementation; type annotations do not influence layout or code generation.

From this core’s perspective:

* Python is effectively always on the **shared/erased** side:

  * one body per function/class,
  * dynamic dispatch and runtime checks for behaviour.

Specialisation and monomorphization happen, if at all, in:

* C extensions,
* JIT-like engines beneath the language,
* not in the Python semantics proper.

Python is thus an example of **maximal sharing** with all the performance trade-offs handled ad hoc by lower layers.

## 15. C++ Case Study – Templates as Monomorphizing Meta-Language

C++ templates are the archetype of generics as a static meta-language.

### 15.1 Monomorphization and explosion

```cpp
template<typename T>
T id(T x) { return x; }
```

Each distinct `T` used in a translation unit yields a separate instantiation:

```cpp
int  a = id(3);      // id<int>
bool b = id(true);   // id<bool>
```

The compiler:

* generates `id<int>`, `id<bool>`, …
* optimises each independently,
* instantiates templates transitively in dependent code.

With heavy use:

* STL containers, algorithms, meta-programming templates, and user templates combine,
* `|Inst(f)|` and the transitive closure of template use grow large,
* binaries and compile times follow.

Templates are thus:

* a **monomorphizing engine**,
* with very weak budget controls in the language itself.

### 15.2 Concepts and constraints

C++20 concepts:

* constrain template parameters,
* provide better error messages,
* prune some candidate instantiations earlier.

They do *not* fundamentally change:

* the monomorphization model,
* the risk of instantiation explosion,
* the structural Tier-3/4 nature of heavy template meta-programming.

From the perspective of this core:

* C++ templates plus concepts illustrate both the power and danger of **unbudgeted monomorphization**:

  * extremely expressive static meta,
  * high potential for pathological compile-time and binary behaviour,
  * strong reliance on discipline and tooling rather than architectural limits.
