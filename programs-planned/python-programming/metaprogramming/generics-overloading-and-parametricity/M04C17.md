## 1. Ad-Hoc vs Parametric vs Subtyping

Three different “polymorphisms”:

### 1.1 Parametric polymorphism (M04C16)

One implementation works **uniformly** for *all* types. No per-type code decisions.

Example type:

```text
id : ∀α. α → α
```

The implementation cannot depend on the concrete `α`; it’s forced to behave the same way (modulo effects) for any `α`.

### 1.2 Ad-hoc polymorphism

Many implementations; one is chosen **per type combination** at (static) call sites.

Informally:

> Ad-hoc polymorphism is a **compile-time mechanism** that chooses one of several implementations based on types (and sometimes constraints).

Forms:

* Ordinary overloading: same name, different parameter types.
* Operator overloading: `+`, `*`, etc. redefined for user types.
* Typeclass/trait-style resolution: “find the implementation for this type”.

### 1.3 Subtyping-based polymorphism

Single implementation over a **supertype**, with dynamic dispatch at runtime.

Example:

```text
draw : Shape → Unit        -- accepts any subtype of Shape
```

Dispatch choice is **dynamic** (vtable, tag, etc.), not statically rewritten.

## 2. R–T–S and Pipeline Placement

### 2.1 Representation (R)

To model ad-hoc polymorphism statically, you need:

1. **Overload sets**

   For each overloaded name `f`, a set of declarations:

   ```text
   f : τ₁
   f : τ₂
   …
   ```

   Possibly with constraints:

   ```text
   f : (C α) ⇒ σ          -- usable when constraint C α holds
   ```

2. **Instance / impl environment**

   For typeclass/trait-like systems:

   ```text
   instance C τ₁ where …
   instance C τ₂ where …
   …
   ```

   Think: a global or module-level map `(C, τ) ↦ implementation`.

3. **Call sites and local constraints**

   For each call `f(e₁,…,eₙ)`:

   * some combination of:

     * argument types (inferred or declared),
     * expected result type,
     * in-scope constraints (`C τ` requirements).

### 2.2 Transform (T): Resolution as Search + Rewrite

Resolution is a **static transform**:

* Before:

  ```text
  f(e₁,…,eₙ)
  ```

* After:

  * either a monomorphic call:

    ```text
    f_int(e₁,…,eₙ)
    ```

  * or a call with explicit dictionaries (for class/trait systems):

    ```text
    f @τ dictCτ e₁ … eₙ
    ```

Abstract algorithm at a call site:

1. Build the **candidate set** for this name/constraint:

   * all overloads named `f`,
   * or all instances that can satisfy `C τ`.
2. Filter by **applicability**:

   * parameter and argument types must be compatible,
   * all required constraints must be satisfiable with available instances.
3. Order by **specificity**:

   * more specific types win over generic ones,
   * fewer or more precise conversions is “better”.
4. If there is a **unique best** candidate: rewrite call to that implementation.
5. Otherwise: report **no match** or **ambiguity**.

Real languages define a complex partial order of conversions (widening vs narrowing, boxing, etc.). That conversion lattice is where “brittle precedence rules” and surprising overload choices come from.

### 2.3 Static dimension (S) and pipeline slot

In a phase-clean toolchain (M10C47):

```text
parse → expand (macros) → resolve/bind → type + resolve_overloads → lower → optimise → codegen
```

* Overload / instance resolution lives in the **type + resolve_overloads** phase:

  * it uses binding + type information (M02C07, M02C10),
  * it may itself drive some type inference (M04C20).

After resolution, the IR:

* has **no ad-hoc polymorphism**: all calls are to specific functions/dictionaries,
* becomes easier to reason about for lower phases.

## 3. Simple Function Overloading

Assume a simple language with `Int`, `Bool`, `Text`, and implicit `Int ≤ Number`:

```text
f : Int    → Text
f : Bool   → Text
f : Number → Text
f : α      → Text    -- polymorphic fallback
```

Resolution rules (toy):

1. Exact type match > match via supertype > polymorphic fallback.
2. If two non-polymorphic candidates are incomparable in specificity, the call is ambiguous.

Examples:

* `f(3)` with `3 : Int`:

  * Candidates: `Int→Text`, `Number→Text`, `α→Text`.
  * Most specific: `Int→Text` ⇒ choose that.

* `f(True)` with `True : Bool`:

  * Exact `Bool→Text` ⇒ choose that.

* `f(x)` with `x : Number` but not known to be `Int`:

  * `Number→Text` and `α→Text` applicable.
  * `Number→Text` more specific ⇒ choose that.

* Ambiguity case:

  ```text
  f : FloatLike → Text
  f : Serializable → Text
  ```

  For an argument type that is both `FloatLike` and `Serializable` with no declared subtype relation, neither is more specific ⇒ ambiguity.

Core idea:

> Overloading is ad-hoc polymorphism with resolution based purely on **types and a conversion lattice**, plus a specified “more specific than” relation.

## 4. Operator Overloading

Operators are typically desugared into ordinary function calls:

```text
(+) : Int × Int → Int
(+) : Vec × Vec → Vec
(+) : Vec × Scalar → Vec
```

Expression:

```text
a + b
```

is shorthand for:

```text
(+)(a, b)
```

Resolution then proceeds as for ordinary overloading, with `+` as the function name.

Two key issues:

1. **Special treatment of built-ins**

   Primitive `+` is often baked into the language:

   * special typing rules,
   * direct mapping to CPU instructions,
   * constant folding, etc.

   Many languages make user-defined `+` **secondary** to built-in `+` (e.g. only considered when types are non-primitive).

2. **Semantic expectations and readability**

   Overloading `+` for something non-additive (e.g. logging, side-effect injection) is technically legal but semantically hostile.

WSM/Tier view:

* Natural extensions (vector addition, string concatenation) with obvious semantics remain **Tier-2** convenience.
* Overloading `+` for unrelated behavior or mixing too many overloads makes **“what does `a + b` mean here?” a non-local search problem** ⇒ Tier-3.

Guideline:

> Only overload operators when the meaning is *obviously compatible* with the built-in operator semantics.

## 5. Typeclasses / Traits as Ad-Hoc Polymorphism (Preview)

Typeclasses/traits generalise overloading from “per name” to “per **constraint**”.

Sketch (language-neutral):

```text
class Eq α where
  (==) : α → α → Bool

instance Eq Int  where (==) = eqInt
instance Eq Bool where (==) = eqBool

instance Eq α ⇒ Eq [α] where (==) = eqList
```

At a call:

```text
equal : ∀α. Eq α ⇒ α → α → Bool
equal x y = x == y
```

Resolution workflow:

1. Infer a type `τ` for `x` and `y`.
2. Generate the constraint `Eq τ`.
3. Search the instance environment for a unique `Eq τ` instance:

   * e.g. `Eq Int` or `Eq [Int]` via `Eq [α]` + `Eq Int`.
4. Rewrite the program to pass the chosen implementation (dictionary) explicitly:

   ```text
   equal @Int dictEqInt x y
   ```

Differences vs simple overloading:

* Resolution is constraint-driven (`Eq τ`), not just name + argument types.
* Instances can be **derived** from other instances (e.g. lists from element).
* Coherence conditions and restrictions (no orphans, no overlaps) are needed to avoid ambiguity and global inconsistency.

Full semantics (laws, associated types, etc.) are M04C18’s topic. Here we only care about resolution as a static meta-mechanism.

## 6. Coherence, Ambiguity, Overlaps, Diamonds, Orphans

### 6.1 Ambiguity

A call is **ambiguous** if:

* more than one candidate is applicable, and
* no candidate is strictly more specific than the others.

Example (overloading):

```text
g : Number     → Text
g : Printable  → Text
```

If `x` is both `Number` and `Printable` with no declared subtyping relationship, `g(x)` is ambiguous.

A robust design treats this as a **compile-time error**, not “pick one arbitrarily”.

### 6.2 Coherence

Informal but concrete:

> A system is **coherent** if, for each ad-hoc requirement (e.g. a class/type pair `(C, τ)` or a particular overloaded call), there is **at most one semantically active implementation in any well-typed program**, and the resolution algorithm always picks that same implementation.

Coherence implies:

* Different modules cannot “silently disagree” on what `Eq Int` is.
* Adding imports or unrelated instances cannot change which implementation is chosen, as long as the program remains well-typed.

Non-coherent systems exhibit:

* behavior changing when you alter imports,
* different parts of a program resolving the same requirement differently.

### 6.3 Overlaps and Diamonds

**Overlapping instances/overloads**:

Two candidates *overlap* if there exist types for which both apply.

Example (typeclass style):

```text
instance Show [α]    where …    -- generic lists
instance Show [Char] where …    -- special case for strings
```

For `[Char]`, both `Show [α]` (with `α = Char`) and `Show [Char]` apply ⇒ overlap.

The compiler must:

* choose one as “more specific”, or
* reject the overlap, or
* require explicit disambiguation.

**Diamond overlaps**:

“Diamond” refers to multiple derivations of the same requirement:

```text
C τ₁      C τ₂
  \      /
   C τ
```

If there are two derivations for `C τ`:

* `C τ` via `τ₁`,
* `C τ` via `τ₂`,

and they induce different behavior, you have a coherence problem. This is especially dangerous when instances are defined across different modules.

### 6.4 Orphan Instances

An **orphan instance** is an instance declared in a module that defines neither:

* the class/trait, nor
* the type for which the instance is provided.

Sketch:

```text
-- Module A
class C α where …

-- Module B
data T = …

-- Module X
instance C T where …     -- orphan: X owns neither C nor T

-- Module Y
instance C T where …     -- another orphan
```

Hazards:

* Multiple orphans for the same `(C, T)` can exist in different modules.
* Which one is “seen” depends on what is imported where.
* Coherence and modular reasoning are destroyed.

Most coherent systems forbid or severely restrict orphans, e.g.:

* “An instance must be defined in the module that defines the class or the type.”

**Bridge to next section:**
Overlaps, diamonds, and orphans are exactly where **resolution becomes an underspecified search problem**. The more freely you allow them, the more ad-hoc polymorphism behaves like a global meta-language rather than a local convenience.

## 7. Resolution as Search and Interaction with Inference

### 7.1 Resolution as Constraint Search

Abstract view:

1. From the program, collect **constraints** (e.g. `Eq τ`, `Parse τ`).
2. Maintain an environment of **available implementations** (overloads, instances).
3. Find an assignment of implementations to constraints such that:

   * all constraints are satisfied,
   * coherence is preserved (no conflicting choices),
   * no ambiguous choices occur.

This is a **search problem** over a candidate graph:

* overlaps enlarge the candidate set,
* recursive instances (`Eq [α]` needs `Eq α`) cause recursive search,
* global visibility (imports, modules) shapes the graph.

### 7.2 Entanglement with Type Inference

In inferential languages, resolution and type inference are tightly coupled.

Example:

```text
parse : ∀α. Parse α ⇒ Text → α
```

Instances:

```text
instance Parse Int
instance Parse Bool
```

Consider:

```text
v = parse "1"
```

Without annotation:

* we get a fresh type variable `α` and constraint `Parse α`.
* there are at least two candidates: `α = Int`, `α = Bool`.
* without more information, `α` is underdetermined ⇒ **ambiguous**.

With annotation:

```text
v : Int
v = parse "1"
```

* the expected type fixes `α = Int`,
* resolution can choose `Parse Int` unambiguously.

If we now add:

```text
instance Parse Text
```

then calls like:

```text
parse "hello"
```

may become ambiguous unless constrained by context.

General pattern:

* Inference uses resolution to refine types (“this must be `Int` because only `Parse Int` exists”).
* Resolution uses inferred types to prune candidates.
* M04C20 will treat this as **constraint solving + search**; design must restrict expressiveness so this remains tractable and decidable.

## 8. WSM/Tier Classification for Ad-Hoc Polymorphism

Using the **WSM/Tier** lens:

* **Tier-1:**
  A small number of local overloads, no subtle conversions, no constraints. You can see all candidates on one screen.

* **Tier-2 (healthy, intended use):**

  * Simple coherent overloading.
  * Operator overloading with obvious semantics.
  * Typeclass/trait systems with:

    * global coherence,
    * no (or tightly constrained) orphans,
    * simple, mostly tree-shaped instance graphs.
  * Resolution rules that are clearly documented and deterministic.

* **Tier-3/4 (danger zone):**

  * Global implicit search over many modules.
  * Overlapping instances with ad-hoc priority rules.
  * Unrestricted orphan instances.
  * Resolution used as a **compile-time logic engine** (non-obvious meta-computation).
  * Strong entanglement with complex inference, where error messages and behavior are highly non-local.

Heuristic:

> If answering “what implementation is used here?” forces you to read multiple modules and simulate a search procedure, you are no longer in Tier-2.

This is structurally similar to overpowered macro systems (Module 3): once resolution becomes a global, under-specified meta-layer, refactoring and debugging become systematically hard.

## 11. Glossary

* **Ad-hoc polymorphism**
  Polymorphism realised via multiple distinct implementations, one chosen per type (and context), rather than a single uniform implementation.

* **Overload set**
  The set of all declarations (functions, methods, operators) sharing a name and eligible for resolution at a call site.

* **Overload resolution**
  Static algorithm that, given a call and an overload set, selects a unique applicable implementation (or reports ambiguity) based on type information and a specificity order.

* **Typeclass / trait resolution**
  Ad-hoc polymorphism driven by constraints over types (e.g. `C τ`) and a set of instances/impls. Resolution finds a suitable instance for each constraint.

* **Coherence**
  Global property that for any ad-hoc requirement (e.g. `(C, τ)`), there is at most one semantically active implementation in any well-typed program, and all call sites consistently use it.

* **Ambiguity**
  Situation where more than one candidate is applicable and none is more specific, so the language cannot choose a unique implementation.

* **Overlapping instances / overloads**
  Instances or overloads that are simultaneously applicable for some type(s), creating potential ambiguity or requiring extra disambiguation rules.

* **Diamond overlap**
  A pattern in the instance/overload graph where the same requirement can be satisfied via multiple distinct derivation paths, risking inconsistent behavior.

* **Orphan instance**
  Instance declared in a module that defines neither the class/trait nor the type; undermines coherence and modularity.

* **Resolution as search**
  Viewing overload/instance resolution as a search problem over a candidate graph subject to constraints and coherence conditions, often entangled with type inference.

* **Tier-2 ad-hoc polymorphism (WSM)**
  Disciplined, mostly local usage with clear, deterministic resolution and strong coherence guarantees.

* **Tier-3/4 ad-hoc polymorphism (WSM)**
  Overly powerful, globally entangled mechanisms where resolution behaves like a sophisticated meta-language and is difficult to reason about.

## 12. Python: Dynamic Ad-Hoc Polymorphism (Optional Case Study)

Python uses **dynamic** ad-hoc polymorphism.

### 12.1 Dunder Protocols

Operator overloading uses “dunder” methods:

```python
class Vec2:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __add__(self, other):
        return Vec2(self.x + other.x, self.y + other.y)
```

`a + b` dispatches at runtime to `a.__add__(b)` (and possibly `b.__radd__(a)`).

* R: runtime types and method tables.
* T: runtime dispatch, no static rewrite.
* S: meta happens at runtime, not at compile time.

### 12.2 `functools.singledispatch`

Provides runtime single-argument overloading:

```python
from functools import singledispatch

@singledispatch
def area(shape):
    raise TypeError("unknown shape")

@area.register
def _(s: int):
    return s * s

@area.register
def _(s: tuple):  # (w, h)
    w, h = s
    return w * h
```

* Dispatch is by runtime type of the first argument.
* Overload set is a registry mapping types → implementations.

WSM/Tier:

* Small, explicit registries: acceptable dynamic Tier-2 meta.
* Global, implicit registries: quickly becomes Tier-3/4; hard to reason about which implementation is used where.

## 13. C++: Overloads, ADL, Templates (Optional Case Study)

C++ exercises most of the machinery described above.

### 13.1 Ordinary Overloading

```cpp
void log(int);
void log(const std::string &);
```

`log(42)` vs `log("hi")`:

* Compiler constructs overload set `{log(int), log(std::string const&), …}`.
* Uses a detailed conversion ranking to choose the “best viable” function.

The conversion lattice (integral promotions, floating conversions, user-defined conversions, etc.) is where resolution becomes unintuitive.

### 13.2 ADL (Argument-Dependent Lookup)

C++ adds functions from namespaces associated with argument types to the candidate set (Argument-Dependent Lookup). This:

* makes resolution depend on which namespaces define which functions,
* can change behavior when you add a new function far away,
* increases non-locality.

This is a textbook example of ad-hoc polymorphism drifting toward **Tier-3**: “what `f(x)` means” depends on global namespace state.

### 13.3 Templates and Specialisation

Templates mix parametric and ad-hoc polymorphism:

```cpp
template<typename T>
void print(const T &);

template<>
void print<int>(const int &);
```

Resolution involves:

* template vs non-template overloads,
* template argument deduction,
* partial ordering of templates (“more specialised”),
* possible specialisations.

From an R–T–S viewpoint:

* R: overload sets + template patterns.
* T: template instantiation + partial ordering + rewrite.
* S: purely compile-time, often expensive and subtle.

In practice:

* Small, obvious overload sets: Tier-2.
* Templates + ADL + partial specialisation used as a compile-time programming language: **Tier-3/4** ad-hoc polymorphism.

C++ serves as a cautionary case: once resolution rules become globally powerful and complex, ad-hoc polymorphism ceases to be a local convenience and becomes a full metaprogramming substrate—with all the associated failure modes.
