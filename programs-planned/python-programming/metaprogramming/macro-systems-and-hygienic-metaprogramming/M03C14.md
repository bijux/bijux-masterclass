# M03C14 – Expansion Phases & Macro Phase Ordering

   parse → expand → resolve/bind → type → lower → optimise → codegen

2. View macro expansion as a **rewrite strategy** (M02C09) over syntax objects:

   * redex = macro call,
   * strategy = expansion order (outermost / innermost / fixed-point / on-demand),
   * **macro-normal form** = syntax with no macro calls left, and explain why this is a useful pipeline invariant.

3. Explain how **recursive and mutually recursive macros** are handled:

   * when expansion terminates cleanly,
   * when it diverges or “explodes” in size,
   * and practical design rules to avoid non-termination and macro blow-ups.

4. Describe typical **macro dependency and ordering** constraints:

   * “macros first” vs local/module/block macros,
   * macros that expand into other macros,
   * layered macro systems with multiple expansion phases.

5. Analyse **phase separation vs cross-phase leaks**:

   * expand-before-type vs type-directed macros,
   * why “expand ↔ type ↔ expand” loops are dangerous,
   * how this ties into the WSM/Tier framework (M01C05) and **phase-clean** toolchains (M10C47).

6. Relate macro expansion phases to **semantic preservation** (M02C10) and **hygiene** (M03C12–M03C13):

   * expansion should preserve binding graphs (up to α-renaming),
   * phase ordering should not make correctness reasoning intractable.

In the storyline:

* **Backward:** Uses CST/AST/IR (M02C06–08), rewriting (M02C09), correctness (M02C10), and hygienic quasiquote/pattern macros (M03C11–M03C13).
* **Forward:** Provides the phase and ordering invariants that M03C15 (debuggability/tooling) and M10C47 (phase-clean toolchains) rely on.

## 1. Macro Expansion as a Phase

### 1.1 Phase-Clean Pipeline (Recap)

The “ideal” front-to-back pipeline (simplified):

```text
source text
  → [lex] tokens
  → [parse] CST/AST
  → [expand] macros (syntax → syntax)
  → [resolve/bind] names & environments (M02C07)
  → [type] type checking / inference
  → [lower] IRs (HIR → MIR → SSA / low-level IR)
  → [optimise] IR → IR passes
  → [codegen] machine code / bytecode
```

Macro expansion is:

* a **front-end rewrite phase**:

  * input R: syntax objects (AST + scope marks + locations; M03C13),
  * output R: syntax objects again, but in **macro-normal form** (no macro calls),

* constrained by:

  * hygiene (binding preservation; M03C12),
  * quasiquotes and pattern languages (M03C13),
  * semantic preservation (M02C10).

We want expansion to be:

* **early**: before name resolution/type/lowering, so later phases see only desugared code,
* **complete**: no macro calls leak into type/lower/optimise unless explicitly part of a multi-phase design,
* **deterministic**: same expanded form for the same program, independent of accidental traversal details (strategy is part of the language spec).

### 1.2 Where Different Macro Kinds Sit

Rough placement:

* **Textual macros / preprocessors** (M03C11):

  * run *before* parse (or interleaved with lexical scanning),
  * see bytes or flat tokens, not ASTs,
  * phase: lex / pre-parse.

* **Token-tree / syntactic macros**:

  * run **after** parsing,
  * see CST/AST or structured token trees,
  * phase: expand (between parse and resolve/bind).

* **Typed macros / type-directed macros** (preview for M11C51):

  * can depend on type information,
  * expansion interleaved with type checking as an additional expansion phase.

This core focuses on syntactic macros as a **distinct expansion phase** in the front end. Typed macros are noted where they affect ordering.

### 1.3 R–T–S View for Expansion

For macro expansion specifically:

* **R (representation)**

  * syntax objects: AST nodes + scope marks + source positions (and later possibly types).

* **T (transform)**

  * macro expansion engine =

    * set of macro definitions (pattern + template, or procedural transformers),
    * expansion strategy (traversal order, rule-order priorities, recursion policy),
    * fixed-point check (when to stop).

* **S (staging)**

  * where expansion sits in the overall pipeline,
  * whether there are multiple macro phases (core vs user, syntax-only vs typed),
  * which macros are available at each phase and scope (macro environment).

Everything else in this core is about choosing **T** and **S** so that:

* expansion terminates,
* expansion is deterministic,
* later phases see a clean, macro-free syntax as their input.

## 2. Models of Expansion: Single-Shot, Fixed Point, On-Demand

### 2.1 Single-Shot Expansion (No Recursive Macros)

Simplest conceptual model:

1. Parse source to syntax objects.
2. Traverse the tree once, expanding each macro call at most once.
3. Done: no further macro calls exist in the result.

This is viable only if:

* macros are **non-recursive** (their expansions do not contain macro calls), or
* any macro calls they emit belong to an **earlier phase** that has already been run.

In practice, “single-shot” usually means:

* Phase 1: expand core macros,
* Phase 2: run user macros once,

with the guarantee that neither phase reintroduces macros from its own phase.

### 2.2 Iterative / Fixed-Point Expansion

Most macro systems allow:

* macros that expand into other macros,
* recursive or mutually recursive macros.

General expansion model:

```text
repeat:
  find macro calls (redexes)
  expand according to macro definitions and strategy
until no macro calls remain (macro-normal form)
```

This is exactly a **fixed-point rewrite strategy** (M02C09):

* redex: macro invocation node,
* T: set of macro rules,
* strategy: top-down, bottom-up, outermost, innermost, or a specific traversal,
* normal form: syntax tree with no macro invocations.

Termination is not guaranteed by the framework; it is a property (or bug) of the macro definitions + strategy.

### 2.3 On-Demand (Lazy) Expansion

Compilers or IDEs often expand macros **on demand**:

* expand only the modules/functions currently being type-checked,
* expand only the part of the tree under the cursor in an IDE,
* cache expanded forms across sessions.

Conceptually, this is the same rewrite system; the strategy is **demand-driven** rather than “expand everything eagerly”.

Key invariant must still hold:

> **Invariant:** any fragment of syntax that enters **binding**, **typing**, or **lowering** is in macro-normal form for all macros in scope for that fragment.

On-demand expansion is an implementation detail; the semantic model is still: “type/lower sees fully expanded code”.

## 3. Recursive Macros, Termination, and Macro Explosions

### 3.1 Direct Recursion and Divergence

Direct self-recursion without a decreasing metric yields divergence.

Scheme-like:

```scheme
(define-syntax forever
  (syntax-rules ()
    [(forever body ...)
     (forever body ...)]))
```

Expanding `(forever (display "hi"))`:

* pattern matches,
* expansion reproduces the same macro call,
* infinite expansion: no macro-normal form.

Rust-like:

```rust
macro_rules! bad {
    ($e:expr) => { bad!($e) };
}
```

Again, expansion diverges.

In M02C09 terms: an **infinite rewrite sequence**; macro expansion does not terminate.

### 3.2 Structural Recursion and Termination

Useful recursive macros usually recurse over **finite structure** with a decreasing metric.

Example (schematic; list-based structural recursion):

```scheme
(define-syntax tuple-case
  (syntax-rules ()
    [(tuple-case () t)
     t]
    [(tuple-case (x xs ...) t)
     (let ((tmp x))
       (tuple-case (xs ...) t))]))
```

Here:

* metric = length of the `(x xs …)` list,
* each recursive step removes one element from `xs`,
* for a finite list, the metric strictly decreases until base case `()`.

Thus expansion terminates after a number of steps equal to the tuple length.

### 3.3 Size Blow-Up (“Macro Explosions”)

Even terminating macros can be pathological:

* expansions that double the size of their input each step,
* nested expansions that expand an `O(n)` input into `O(2^n)` syntax.

This is a **macro explosion**: expansion terminates but yields enormous code.

Causes:

* naive duplication of arguments or bodies in recursive macros,
* recursive generation of many nearly-identical branches (e.g. badly written DSLs).

Practical mitigations:

* compiler-level expansion depth and size limits,
* diagnostics that point at the macro responsible,
* design rule: use macros to **build** loops or combinators, not to represent unbounded unfolding at expand-time.

### 3.4 Design Rules for Termination and Size Control

Most macro systems don’t statically enforce termination or size bounds; these are **design disciplines** plus runtime checks.

Rules of thumb:

1. **Guard all recursion with a decreasing syntactic metric**:

   * size of a list/tuple,
   * numeric literal counter,
   * size of a syntactic tree.

2. **Avoid mutual recursion without a simple termination argument**:

   * A → B → A cycles on constant-size arguments are a red flag.

3. **Be wary of unbounded duplication**:

   * repeatedly splicing arguments in multiple places.

4. **Let run-time loops be run-time**:

   * use macros to assemble loops, not unroll them unboundedly.

From WSM/Tier (M01C05):

* structural, obviously terminating pattern macros are Tier-2,
* recursion with non-trivial metrics and potential blow-ups is Tier-3/4 and should be used sparingly, with strong justification.

## 4. Macro Definitions, Dependencies & Ordering

### 4.1 Macro Environments and Availability

Expansion uses a **macro environment**:

* a mapping from macro names to definitions,
* indexed by:

  * phase (which macro phase is running),
  * lexical scope (module/block-local macros).

Two simple models:

1. **Global “macros first”**

   * macros are defined in separate files or sections loaded before code,
   * environment is filled *once* before expansion of user code,
   * simple but less modular.

2. **Local/module/block macros**

   * macros can be defined in modules or blocks (`let-syntax`, module-local macros),
   * environment is extended as the expander traverses syntax,
   * expansion must respect lexical scoping for macros themselves.

We ignore deeper **phase levels** (compile-time vs run-time modules etc.) here; those belong to more advanced systems (Module 11). Here “macro environment” means: definitions visible in the current syntactic scope and expansion phase.

### 4.2 Macros Expanding Into Other Macros

Common pattern: macros layered on top of each other.

Example:

```scheme
(define-syntax my-while
  (syntax-rules ()
    [(my-while cond body ...)
     (my-loop cond body ...)]))

(define-syntax my-loop
  (syntax-rules ()
    [(my-loop cond body ...)
     (if cond
         (begin body ... (my-loop cond body ...))
         (void))]))
```

Expansion of `(my-while c e1 e2)`:

1. `my-while` expands first, yielding `my-loop c e1 e2`.
2. `my-loop` expands, yielding an `if` with recursive `my-loop` calls.
3. Recursively expand `my-loop` calls until macro-normal form.

If both macros are in the same phase:

* a **fixed-point** expansion strategy is natural:

  * repeatedly expand macro calls until no `my-while` or `my-loop` invocations remain.

### 4.3 Layered Macro Phases

Languages often layer macro phases:

* **Phase 1: core macros**

  * defined by the language / standard library,
  * may desugar high-level syntax into a smaller core,
  * expand to either:

    * core constructs, or
    * Phase-2 macros.

* **Phase 2: user macros**

  * defined in user modules,
  * see a slightly desugared surface (post-core-macro syntax).

Conceptually:

* Phase 1: rewrite to first normal form (no core macros).
* Phase 2: rewrite to second normal form (no user macros).

This layering:

* improves determinism,
* reduces pattern overlaps between core and user macros,
* makes the macro system easier to reason about and debug.

## 5. Expansion vs Binding vs Types

### 5.1 Expand-Before-Type: Hygienic Default

The cleanest, hygiene-friendly discipline:

```text
parse
  → expand (macro-normal form, syntax-only)
  → resolve/bind (names & environments)
  → type (checking/inference)
  → lower → optimise → codegen
```

Here:

* expansion is **purely syntactic**:

  * it must not depend on type information,
  * R for expansion is syntax objects without types.

* hygiene is enforced during expansion:

  * scope marks and syntax objects ensure binding graphs are preserved (M03C12),
  * once in macro-normal form, binding resolution works on macro-free syntax.

Advantages:

* binding and type systems don’t “see” macros,
* macro reasoning and type reasoning are separated,
* macro expansion is a well-defined pre-typing rewrite pass.

### 5.2 Typed Macros: Expansion Interleaved with Types (Preview)

Some systems support **typed macros**:

* macros that:

  * depend on type information in their arguments,
  * or produce expansions whose correctness is checked at macro-time.

Pipeline sketch:

```text
parse
  → expand₁ (syntax-only macros)
  → resolve/bind
  → type₁
  → expand₂ (typed macros over typed AST/HIR)
  → type₂
  → lower → optimise → codegen
```

Here:

* R for `expand₂` is a **typed AST/HIR**,
* macros can inspect types or rely on type-directed pattern languages.

Use cases:

* deriving trait/typeclass instances from data declarations,
* generating specialised code based on type-level sizes,
* embedding domain-specific static checks in macro expansions.

Risks:

* expansion and type checking can become mutually recursive,
* without discipline, you can create **expand ↔ type** loops.

Therefore typed macros:

* are powerful but higher Tier (3/4),
* require explicit contracts (preconditions, effects, invariants),
* are treated in detail in Module 11.

### 5.3 Expansion vs IR-Level Transforms

Macro expansion:

* operates on **syntax objects** (AST/HIR-with-syntax),
* before lowering to IR.

IR passes (M02C08–C09):

* operate on HIR/MIR/SSA,
* after type checking and lowering,
* have their own invariants and tooling.

Strong design rule:

> IR passes should **not** invoke macros. Once you’ve lowered to IR, you are past the “expand” slot in the pipeline (M10C47).

Reasons:

* mixing macros with IR transforms entangles phases,
* makes correctness proofs (M02C10) and debugging (M03C15) harder,
* encourages cross-phase leaks (next section).

If you need IR-level “meta”, use dedicated IR transforms, not syntax macros.

## 6. Phase Separation vs Cross-Phase Leaks

### 6.1 Phase-Clean Ideal

The **phase-clean** ideal (formalised in M10C47):

```text
text
  → lex/parse
  → expand (macro-normal form)
  → resolve/bind
  → type
  → lower (IR)
  → optimise
  → codegen
```

Invariants:

* after expand:

  * no macro calls remain in the syntax seen by bind/type/lower,
  * macro-normal form is a stable input for later phases.

* later phases:

  * do not create new syntax that requires macro expansion,
  * do not call back into the macro engine.

Benefits:

* reasoning: each phase has clear pre/post-conditions,
* tooling: macro debuggers and type checkers don’t interfere,
* performance: macro expansion cost is localised.

### 6.2 Cross-Phase Leaks

Violations of phase-clean discipline:

1. **Macros peeking at types/IR**

   * expansion decisions depend on:

     * whether an expression is a constant,
     * whether a function will be inlined,
     * IR-level shapes.

   * e.g. a macro that asks “has the optimiser constant-folded this?” and changes expansion based on the answer.

   * consequence: different compiler flags / optimisation levels can change the *expanded* code.

2. **IR passes re-invoking macros**

   * an optimiser that recognises a pattern and calls back into the macro expander to “re-sugar” code.

   * creates loops: expand → type → lower → optimise → expand → …

3. **Macros expecting post-type or IR transformations**

   * macros that only behave correctly if certain downstream optimisations occur.

   * makes macro correctness dependent on optimisation heuristics.

These cross-phase leaks:

* turn local expansion rules into **global system properties**,
* push macro usage into Tier-3/4:

  * high expressiveness,
  * poor predictability,
  * fragile correctness and tooling.

### 6.3 WSM/Tier Lens

Under WSM/Tiers (M01C05):

* **Tier 1–2 macro systems**

  * expansion is syntactic, phase-clean,
  * macros do not depend on type/IR/optimiser decisions,
  * most library/user macros live here.

* **Tier 3–4 macro systems**

  * typed/procedural macros mixing phases,
  * macros and optimisation mutually aware,
  * reserved for compiler teams and critical infrastructure, with strict contracts.

Enforcing “parse → expand → type → lower → optimise → codegen” is one of the few architectural levers that reliably keeps macro usage in Tier-2 instead of degenerating into global Tier-3/4 complexity.

## 7. Expansion Strategy as Rewrite Strategy (M02C09 Tie-In)

Macro expansion is a term rewriting system; **strategy** matters.

### 7.1 Outermost vs Innermost Expansion

Two basic strategies:

* **Outermost-first (top-down)**

  * expand macro calls at outer positions before inner ones,
  * natural for surface sugars:

    * e.g. `when`, `for`, `match`.

* **Innermost-first (bottom-up)**

  * expand deepest macro calls first,
  * sometimes needed if outer macros expect their subtrees already expanded.

Most practical systems use a **deterministic top-down traversal**:

* recursively walk the syntax tree,
* when a macro call is encountered, expand it,
* then recurse into the result.

Key point:

> Strategy is part of the **language definition**, not an incidental implementation detail.

Programmers should not have to guess the order; compilers must document it and keep it stable.

### 7.2 Confluence and Overlapping Macros

If two macros can both apply to the same syntax pattern at the same phase:

* different expansion orders may yield different expanded trees,
* in extreme cases, different *semantics* (non-confluent rewriting).

Design rules:

1. **Avoid overlapping macro patterns** at the same phase when possible.

2. When overlap is unavoidable:

   * specify a **priority**:

     * textual rule order within a macro definition,
     * phase ordering between macro sets (core vs user),
     * explicit “this macro only matches when X has not already matched”.

3. Understand that:

   > Determinism is guaranteed by the specified strategy and rule order, even if the abstract rewrite system is not confluent.

Correctness (M02C10):

* ideally: any legal expansion order yields contextually equivalent programs,
* in practice: the specified strategy defines the one legal expansion order; macro authors must reason about correctness under that strategy.

### 7.3 Macro-Normal Form as Pipeline Invariant

**Macro-normal form** (for a given phase):

* syntax tree in which no macro calls remain from that phase’s macro environment.

In a single-phase system:

* macro-normal form = “no macros at all”.

In multi-phase systems:

* after Phase 1: no Phase-1 macros,
* after Phase 2: no Phase-1 or Phase-2 macros, etc.

This is a crucial pipeline invariant:

* bind/type/lower assume macro-normal form,
* macro debuggers (M03C15) can:

  * show original code,
  * show macro-normal form,
  * map between the two reliably (via source maps).

Without a clear notion of macro-normal form per phase, both reasoning and tooling degrade quickly.

## 9. Exercises

1. **Fixed-Point Expansion**

   Consider a Scheme-like system:

   ```scheme
   (define-syntax inc
     (syntax-rules ()
       [(inc x) (+ x 1)]))

   (define-syntax twice
     (syntax-rules ()
       [(twice e) (inc (inc e))]))
   ```

   a. Starting from `(twice 3)`, show the expansion sequence step by step under a **top-down** expansion strategy until macro-normal form.
   b. Is a single pass over the AST sufficient to fully expand all macro calls here? Why or why not?
   c. Describe this expansion process as a term rewriting system with a fixed-point strategy (identify R, T, redexes, normal form).

2. **Recursive Macro, Termination Metric, and Explosion Risk**

   Consider:

   ```scheme
   (define-syntax repeat
     (syntax-rules ()
       [(repeat 0 body ...) (begin)]
       [(repeat n body ...)
        (begin body ... (repeat (- n 1) body ...))]))
   ```

   Assume `n` is a non-negative integer literal.

   a. Explain why this macro terminates for any such literal `n`. Identify the **metric** that strictly decreases at each step.
   b. What goes wrong if `n` is allowed to be an arbitrary expression evaluated at runtime? Discuss both termination and predictability.
   c. How could this macro cause a **size blow-up** if used with large `n`? In WSM/Tier terms, argue why restricting `n` to small literals keeps it in Tier-2, whereas lifting that restriction pushes it toward Tier-3/4.

3. **Expansion vs Type Checking**

   Compare two designs:

   * **Design A:** All macros are fully expanded before any type checking.
   * **Design B:** Macros can query types and expand based on type information, with expansion interleaved with type inference.

   a. For each design, list one **advantage** and one **disadvantage**.
   b. Give an example of a macro that is impractical in Design A but straightforward in Design B.
   c. Explain why Design B requires stronger discipline and explicit contracts to avoid expand ↔ type loops and cross-phase leaks.

4. **Macro Overlap and Ordering**

   Suppose you have:

   ```scheme
   (define-syntax log
     (syntax-rules ()
       [(log e) (display e)]))

   (define-syntax log-twice
     (syntax-rules ()
       [(log-twice e) (log e) (log e)]))
   ```

   a. Show the expansion of `(log-twice 42)` under a strategy that always expands `log-twice` before `log`.
   b. Would trying to expand `log` “inside” `log-twice` first change the final observable behaviour here? Why or why not?
   c. Construct a *different* pair of overlapping macros where expansion order can change the **semantic** outcome. Describe which ordering you would choose and why.

5. **Phase Separation Thought Experiment**

   A design proposal:

   > “Macros can inspect and manipulate the mid-level IR directly, and IR optimisation passes may invoke macros to ‘re-sugar’ complex patterns back into higher-level constructs to aid further optimisation.”

   a. Identify at least two ways this violates the **phase-clean** ideal from this core and M10C47.
   b. Describe likely consequences for tooling (debuggers, profilers, error messages) and for semantic reasoning (M02C10).
   c. Propose a safer alternative that still gives macro authors expressive power over IR-like structures while preserving phase separation (hint: IR-level DSLs or dedicated IR transforms).

## 10. M03C14 Glossary (Compact Reference)

| Term                     | Definition                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Expansion phase**      | Compiler/interpreter phase where macro calls in syntax objects are rewritten to macro-normal form, typically after parsing and before binding/type checking.          |
| **Macro-normal form**    | Syntax tree in which no macro calls from the relevant macro environment remain; fixed point of the macro expansion rewrite system for that phase.                     |
| **Expansion strategy**   | Policy for choosing which macro calls (redexes) to expand and in what order (outermost/innermost, single-pass vs fixed-point, eager vs on-demand).                    |
| **Recursive macro**      | Macro whose expansion contains (directly or indirectly) a call to itself or to other macros that eventually call it; may terminate (with a decreasing metric) or not. |
| **Macro explosion**      | Situation where macro expansion terminates but produces code whose size is exponentially larger than the input, often due to unbounded duplication in expansions.     |
| **Macro environment**    | Mapping from macro names to their definitions, parameterised by phase and lexical scope, used by the expander to resolve macro calls.                                 |
| **Phase-clean pipeline** | Compilation pipeline with well-separated phases (parse → expand → bind → type → lower → optimise → codegen) and no feedback loops between expansion and later phases. |
| **Cross-phase leak**     | Dependency between phases (e.g. macros depending on IR or IR passes invoking macros) that violates phase separation and complicates reasoning and tooling.            |
| **Typed macro**          | Macro whose expansion depends on type information or operates over typed AST/HIR; requires interleaving expansion and type checking.                                  |
| **Layered macro phases** | Organisation of macros into multiple expansion phases (e.g. core then user macros), each with its own macro-normal form and invariants.                               |
