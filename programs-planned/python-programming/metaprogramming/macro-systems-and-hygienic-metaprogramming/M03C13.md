## 1. Why Quasiquotation? AST Rewriting Is Too Low-Level

Conceptually, macros are:

* **IR rewrites** on CST/AST (M03C11),
* expressed as a **transform T** over some representation **R** (M01C01–M02C09).

Naïve implementation: write macros as functions that construct ASTs directly:

```text
If(Var "x", Add(Var "x", Const 1), Const 0)
```

Problems:

* verbose and brittle; small surface syntax changes mean large changes to macro code,
* hard to see what the macro “really expands to”,
* error messages and tooling have little relation to source code.

We want:

* to write **code-shaped templates** that look like the surface language,
* mark holes where meta-data (subtrees or lists of subtrees) will be plugged,
* pattern-match user code in the same language-shaped style.

That is exactly what **quasiquotation and pattern languages** provide:

* **Quasiquotes**: build syntax objects using code-like templates.
* **Anti-quotes / splices**: inject meta-values (subtrees, lists) into those templates.
* **Patterns**: match user code using code-like templates with pattern variables and repetition.

Together they form the primary surface API for hygienic syntactic macros.

## 2. Quote vs Quasiquote vs Anti-Quotation

### 2.1 Plain Quotation: Code as Inert Data

Plain quotation turns code into data without evaluation.

Scheme (value is a *list of symbols* in the core language):

```scheme
'(1 + 2)  ;; => list '(1 '+ 2)
```

In macro space (Racket-style), an analogous form yields a **syntax object** carrying:

* the same tree shape,
* plus scope and source-location marks.

Template Haskell:

```haskell
[| 1 + 2 |]   -- type: Q Exp, a quoted expression
```

Abstract view:

* `quote(e)` or `[| e |]` produces a **syntax value** representing `e`,
* it is not evaluated; it is a tree that meta-code can inspect and transform.

### 2.2 Quasiquotation: Templates with Holes

Plain quotation is rigid — no parameters. Quasiquotation introduces *holes*.

Scheme:

```scheme
(let ((x '(2)))
  `(1 + ,x))
;; quasiquote `( ... )` with anti-quote `,x`
;; result: syntax for (1 + 2)
```

Template Haskell:

```haskell
[| 1 + $(exprQ) |]
```

Abstractly:

```text
qq[ 1 + aq[x] ]
```

* `qq[...]` = quasiquote;
* `aq[x]` = anti-quote: “inject the syntax represented by `x` here”.

Quasiquote builds the template; anti-quote fills the hole.

### 2.3 Splicing: Injecting Sequences

Often you need to insert a **list of syntax nodes**.

Scheme:

```scheme
(let ((xs '(2 3)))
  `(1 ,@xs 4))
;; => syntax for (1 2 3 4)
```

* `,@xs` = splice: insert each element of `xs` into the surrounding list.

Rust / macro-like systems:

```rust
$( $x ),*   // pattern
$( stmt )*  // template repetition (one stmt per match)
```

Abstractly:

* `aq_splice[xs]` inside `qq[...]` inserts *all* elements of `xs` at that position.

We now have:

* **quotation**: treat code as data,
* **quasiquotation**: code templates,
* **anti-quotation / splicing**: parametrize those templates with meta-values.

## 3. Syntax Objects: AST + Scopes + Locations (+ Types)

Hygienic macro systems do not operate on raw ASTs or strings, but on **syntax objects**:

* **AST node** (from M02C06): kind + children,
* **scope / mark set**: which lexical scopes are active (M02C07, M03C12),
* **source-location metadata**: file, line, column,
* possibly **type info** in typed macro systems (Module 11).

Scoping and hygiene:

* From M03C12: macros conceptually see two environments:

  * **definition site** (where macro is defined),
  * **call site** (where macro is used).
* Syntax objects encode these via **scope marks**:

  * ids from macro body carry def-env marks,
  * ids from arguments carry call-site marks.

During expansion:

* pattern matching binds syntax objects (with their marks),
* quasiquote + anti-quote construct new syntax objects, combining marks appropriately,
* the binding resolver uses marks to reconstruct the **binding graph** and enforce hygiene.

R–T–S lens:

* **R** = syntax objects (AST + scopes + locations [+ types]),
* **T** = macro-defined pattern → template rules implemented with quasiquotes and anti-quotes,
* **S** = macro expansion phase (between parse and type/lower; see M03C14, M10C47).

## 4. Pattern Languages: Matching Structured Syntax

Quasiquotes build syntax objects. Macros also need to **match** user code.

A **pattern language** is a restricted syntax for:

* matching syntax objects by *shape* and *category* (expression, identifier, type, etc.),
* binding **pattern variables** to matched subtrees or lists,
* controlling repetition (ellipses, `*`, `+`-like operators).

### 4.1 Simple Pattern Rules: `syntax-rules`-Style

Scheme example:

```scheme
(define-syntax when
  (syntax-rules ()
    [(when cond body ...)
     (if cond
         (begin body ...)
         (void))]))
```

Pattern:

* literal keyword `when`,
* pattern variable `cond` for the condition expression,
* pattern variable `body` with ellipsis `body ...` for a sequence of expressions.

Template:

* uses `cond` once,
* uses `body ...` in `begin` under ellipsis.

Semantics:

* `(when e1 e2 e3)` matches the pattern:

  * `cond ↦ e1`,
  * `body ... ↦ [e2, e3]`,
* macro rewrites to:

  ```scheme
  (if e1
      (begin e2 e3)
      (void))
  ```

No manual AST manipulation appears in the macro; a pattern + template fully specify the rewrite.

### 4.2 Token-Tree Patterns: Rust `macro_rules!`

Rust’s `macro_rules!` operates on token trees with syntactic categories:

```rust
macro_rules! vec {
    ( $( $x:expr ),* ) => {
        {
            let mut tmp = Vec::new();
            $(
                tmp.push($x);
            )*
            tmp
        }
    };
}
```

Pattern features:

* `$x:expr` — pattern variable `$x` matching an expression,
* `$( ... ),*` — repetition: zero or more comma-separated matches of `$x:expr`.

Template features:

* `$x` inside the template is an anti-quote,
* `$(
     tmp.push($x);
   )*`
  splices one statement per matched `$x`.

Pattern language:

* classifies subtrees by category: `expr`, `ident`, `ty`, etc.,
* controls repetition and separators,
* constrains what macro calls are legal and what shape their expansions can have.

### 4.3 Shape-Only, Not Semantic, Patterns

Deliberately, pattern languages:

* match **syntactic shape**, not dynamic meaning,
* avoid arbitrary semantic predicates in patterns (“match only if this evaluates to 3”),
* avoid unbounded recursive matching logic inside patterns.

Consequences:

* matching is decidable and structurally simple,
* failing matches yield clear “no rule applies” errors at expansion,
* macro-level non-termination comes only from **explicit recursive macro calls**, not from the matcher itself.

They are expressive enough for most syntactic sugar and DSLs, but stop short of full meta-Turing-complete inspect-everything logic.

## 5. Patterns + Templates as Term Rewriting (M02C09 View)

Recall M02C09:

* terms, patterns, rewrite rules, strategies, normal forms.

Pattern-based macros instantiate that model:

* **Terms** = syntax objects (AST + metadata),

* **Patterns** = restricted term patterns with:

  * pattern variables,
  * syntax categories (`expr`, `ident`, ...),
  * repetition constructs (ellipses, `*`, `+`),

* **Rewrite rules** = macro clauses:

  ```text
  pattern  →  template
  ```

* **Strategy** = macro expansion engine:

  * locate macro call sites (redexes),
  * consider clauses in order,
  * apply the first pattern that matches,
  * replace the call with the instantiated template,
  * repeat until **macro-normal form** (no macro calls remain).

Rule order is part of the strategy:

* if several patterns could match, the **first** one wins,
* pattern ordering therefore affects which rule fires and must be designed carefully.

Recursive macros and expansion to a fixed point (re-expanding generated macro calls) are real and will be treated explicitly in M03C14; here we assume a terminating strategy for each macro definition.

Hygiene adds binding constraints (M03C12):

* the rewrite must preserve the binding graph on original identifiers (up to α-renaming),
* macro-introduced binders are fresh and scoped only where intended,
* syntax objects propagate def-env and call-env marks correctly.

So for a hygienic, pattern-based system:

* **syntactic constraints** come from the pattern language,
* **binding constraints** come from hygiene machinery.

Together, they sharply constrain `T` in the R–T–S triad.

## 6. Safety and Limits of Pattern-Based Hygienic Macros

Pattern-based, syntax-object macros buy you several important safety properties.

### 6.1 Structure, Not Strings

* Patterns and templates operate on syntax objects, not string concatenation.
* This avoids precedence bugs, accidental token splits/joins, and other text-macro pathologies from M03C11.
* E/S/C: Safety ↑, Complexity ↓, Tooling ↑.

### 6.2 No Semantic Inspection in Patterns

* Patterns cannot encode “this subtree generates a constant 3” or “this function is pure”.
* Semantic analyses (type checking, constant folding) stay in **later passes** (M02C08–C10).
* Keeps expansion phase-clean (M10C47) and prevents the macro matcher from becoming a mini evaluator.

### 6.3 Linearity and Well-Scoped Pattern Variables

Well-designed pattern languages enforce:

* **linearity**: a pattern variable appears in the template either:

  * exactly once, or
  * under a repetition structure compatible with how it was matched.
* **scope compatibility**: pattern variables are only used in positions where they remain well-typed/well-scoped.

This avoids:

* silently dropping an argument,
* duplicating an argument in contexts that change its meaning,
* or moving identifiers under different binders in unsound ways (capture).

Linearity and scoping discipline directly support semantic preservation (M02C10) and hygiene (M03C12).

### 6.4 Hygiene by Construction

Because:

* syntax objects carry def-env / call-env scope marks,
* quasiquote and patterns propagate those marks systematically,

you get a **default** behaviour:

* identifiers from arguments refer to **call-site** bindings,
* identifiers introduced in macro templates refer to **definition-site** bindings or fresh binders,
* name capture is prevented unless you explicitly use escape hatches.

This is precisely the binding-graph preservation story from M03C12, implemented via syntax objects and pattern-directed rewrites.

### 6.5 Expressiveness Boundaries

By design, pattern-based macros:

* are hugely expressive for syntactic sugar, DSL front-ends, boilerplate,
* but restricted compared to full procedural macros or IR passes:

  * no arbitrary semantic tests in patterns,
  * no unconstrained recursion in the matcher,
  * no direct access to type or flow information unless the system explicitly exposes it.

WSM/Tier perspective (M01C05):

* **Pattern-based hygienic macros** are the **Tier-2 sweet spot**:

  * high expressiveness for syntax,
  * strong safety guarantees,
  * controlled complexity; tools remain viable.
* **Procedural macros / IR-level transforms** move you into **Tier-3/4**:

  * more power (inspect types, flows, do complex analyses),
  * but with significantly higher complexity and risk.

## 7. Keystone #1: Quasiquotes + Patterns Are the Macro Surface

Keystone #1 for macro systems:

> The *user-facing* surface of syntactic macro power should be **quasiquotation + pattern languages over syntax objects**.

Internally, the compiler can represent and transform code however it likes; externally:

* macro authors write patterns and quasiquotes,
* the implementation turns those into term-rewriting on syntax objects,
* hygiene and scope/mark machinery ensure lexical correctness,
* later phases (types, IR, optimisation) handle semantic analyses.

Design implications:

* For a new language or macro system:

  * first design a **pattern macro layer**:

    * syntax objects,
    * quasiquotes and anti-quotes,
    * category-aware patterns with repetition,
    * hygiene built in.
  * only then add **procedural macros / custom expanders** as Tier-3/4 escape hatches.
* For most application-level use:

  * encourage pattern macros as the default,
  * reserve procedural/IR macros for rare, performance-critical or deeply structural tasks.

This is the central structural idea of Module 3.

## 10. M03C13 Glossary (Compact Reference)

| Term                            | Definition                                                                                                                                                      |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Quote**                       | Operation turning code into inert syntax data (list/AST/syntax object) without evaluation.                                                                      |
| **Quasiquote**                  | Quotation form treating its body as a syntax template, with holes that can be filled via anti-quotation and splicing.                                           |
| **Anti-quotation**              | Mechanism inside a quasiquote that injects a meta-level value (e.g. a syntax subtree) into the template at a marked position.                                   |
| **Splicing**                    | Anti-quotation that inserts multiple elements (a list of syntax nodes) into a template position, rather than a single node.                                     |
| **Syntax object**               | Structured representation of code (AST) enriched with metadata such as scopes (for hygiene) and source locations (for error reporting), sometimes types.        |
| **Pattern language**            | Restricted language for matching syntax objects in macro definitions, with pattern variables, categories, and repetition constructs (e.g. ellipses).            |
| **Pattern-based macro**         | Macro defined as a set of pattern → template rules over syntax objects; expansion is pattern matching plus quasiquote-based construction of new syntax objects. |
| **Macro-normal form**           | Syntax tree in which no macro calls remain; fixed point of the macro expansion rewrite system under the chosen strategy.                                        |
| **Procedural macro**            | Macro expressed as arbitrary code over syntax objects/ASTs rather than patterns; more expressive but less constrained and harder to analyse and tool.           |
| **Quasiquote/pattern keystone** | Principle that quasiquotes + pattern languages over syntax objects should be the primary user-facing interface to syntactic macro power.                        |
