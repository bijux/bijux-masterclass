## 1. Where Macros Sit in the Front-End

Recall the default front-end + mid-end pipeline:

```text
Source (text)
  → [lexer] → tokens
  → [parser] → CST
  → [AST builder] → AST / HIR
  → [lowering] → MIR / SSA / low-level IR
  → [codegen] → machine code
```

Macro systems hook in at different points:

1. **Pre-parse / preprocessor macros**

   * Act on **text** or **flat tokens** before the real parser.
   * Example: C preprocessor `#define`, `#include`, `#if`.
   * R = string / tokens, S = preprocessor phase.

2. **Parse-time / post-parse pre-binding macros**

   * Work with syntactic structure but without full binding/types.
   * Examples:

     * Lisp/Scheme `defmacro` / `syntax-rules` (AST-level),
     * Rust `macro_rules!` (token trees).
   * R = token trees / CST / AST, S = integrated with parsing or a distinct “expand” phase before type checking.

3. **Post-binding macros (typed macros)**

   * Operate on **typed AST/HIR** after name resolution.
   * Examples:

     * Template Haskell typed splices,
     * hypothetical “typed macros” that see types/binding.
   * R = typed AST/HIR, S = after (some) typing, before lowering.

R–T–S lens (M01C01):

* **R**: the representation exposed to macros (string, tokens, token trees, CST, AST, typed AST/HIR).
* **T**: the macro expansion engine (pattern-based or procedural rewrite).
* **S**: the stage(s) where expansion runs.

WSM/Tier lens (M01C05):

* Textual macros **afford** Tier-3/4 power (they *can* express arbitrarily complex meta).
* Good design confines their *actual use* to Tier-0/1 niches (constants, include guards).
* Syntactic/typed macros are the right tool once you need Tier-2/3 power (DSLs, control-flow, serious code generation).

## 2. Textual Macros: Definition and Placement

We call a macro system **textual** here if its R does *not* carry parse-tree structure:

* R is raw **text**, or
* R is a **flat token sequence** without CST/AST node structure.

Canonical example: **C preprocessor**.

```c
#define WIDTH 800
#define AREA(w, h)  w * h

int a = WIDTH;         // → int a = 800;
int b = AREA(2+1, 4);  // → int b = 2+1 * 4;   // precedence bug
```

Abstractly:

```text
R_text  = string or flat tokens
T_text  = macro substitution (scan for name, splice replacement text/tokens)
S_text  = preprocessor phase, before real parsing and type checking
```

In M01C03’s taxonomy, these are **static, textual meta mechanisms**.

Good for:

* simple symbolic constants,
* include guards,
* trivial feature flags.

Not good for:

* manipulating expressions,
* building control flow,
* introducing new binding forms.

Those require a structured R.

## 3. Failure Modes of Textual Macros (and Why They Happen)

Every classic text-macro bug is a consequence of using a **structure-poor R** and a **blind T**.

### 3.1 Precedence and Parentheses

```c
#define SQUARE(x)  x * x

int a = SQUARE(1 + 2);   // expands to 1 + 2 * 1 + 2 = 5, not 9
```

Root cause:

* R has **no expression tree**; precedence is not explicit.
* T performs raw token substitution; it cannot reorder or regroup.

Mitigation:

```c
#define SQUARE(x)  ((x) * (x))
```

But this is hand-emulating parsing — brittle and easy to get wrong.

Axes (M01C04):

* E: high (can splice arbitrary fragments),
* S: low (bugs are context-sensitive),
* C: high (debugging error sites is painful).

### 3.2 Double Evaluation

```c
#define MAX(a, b)  ((a) > (b) ? (a) : (b))

int x = 0;
int y = MAX(x++, 10);  // expansion may evaluate x++ twice
```

Root cause:

* R has no notion of **evaluation order** or **single-assignment binding**.
* T cannot introduce a proper binding and re-use it safely.

In an AST-based R, a syntactic macro could expand:

```pseudo
MAX(expr_a, expr_b)
→ { let tmp_a = expr_a; let tmp_b = expr_b; tmp_a > tmp_b ? tmp_a : tmp_b }
```

ensuring each expression is evaluated once.

### 3.3 Capture and Global Pollution

```c
#define TMP 42

int f() {
    int TMP = 0;
    return TMP;  // separate issue, but name pollution is global
}
```

Text macros:

* ignore lexical scopes (M02C07),
* inject identifiers into every translation unit that includes them,
* cannot do α-renaming or hygiene.

Root cause:

* R has **no binding / environment layer**.
* T cannot preserve binding invariants or systematically avoid capture.

### 3.4 Tooling Blindness

Refactoring/IDE tools operate on CST/AST:

* “rename symbol”, “go to definition”, “extract function” all rely on structure and binding.
* With text macros, tools must choose:

  * work on **preprocessed** code (losing original structure/locations), or
  * work on **raw** code, ignoring macro expansion.

Root cause:

* There are effectively **two languages**:

  * user-visible macro-laden code,
  * preprocessed code the compiler actually sees,
* with a non-structural, lossy mapping between them.

This is exactly the **error locality / tool reliability** problem emphasised in M01C04.

## 4. Token-Stream / Token-Tree Macros: Middle of the Spectrum

Many macro systems work on a more structured but still pre-AST representation:

* **flat tokens**: lexed tokens, but no nesting,
* **token trees**: nested by delimiters `()[]{}`, but no AST node kinds.

Examples:

* C/C++ preprocessor: token-aware but essentially flat.
* Rust `macro_rules!`: token **trees** with nesting and fragment kinds (`expr`, `ident`, `tt`).

Representation axis:

```text
bytes → flat tokens → token trees → CST → AST → typed AST/HIR
```

In this module, we group everything **below CST/AST** as “textual” from a *safety* perspective, but we distinguish within that group.

### 4.1 Rust `macro_rules!` as Token-Tree Macros

`macro_rules!` uses nested token trees:

* R: token trees (groups + tokens), not AST nodes like `If`, `Let`, `Match`.
* T: pattern → template substitution on token trees with some classification (`expr`, `ty`, etc.).
* S: expansion interleaved with parsing; the parser and macro system cooperate.

Terminology disclaimer:

* In Rust culture, `macro_rules!` is often called a “syntactic macro”.
* In this course, we reserve **“syntactic macros”** for systems that operate on CST/AST/typed AST with explicit node kinds and usually binding.
* On our axis, `macro_rules!` sits **between** raw textual macros and full CST/AST macros; for safety analysis, we treat it as a **token-level** system.

`macro_rules!` avoids some C-preprocessor pathologies, but it still lacks:

* explicit binding information,
* direct access to the language’s AST node taxonomy,
* type information.

Those appear in full syntactic and typed macro systems.

## 5. Syntactic Macros: Structure-Preserving Meta

Syntactic macros operate on **parsed trees**:

* R is CST/AST or typed AST/HIR,
* T is a **rewrite** over those trees,
* S is a distinct expansion phase after parsing (and possibly after name resolution).

### 5.1 Example: Scheme / Racket `when`

```scheme
(define-syntax when
  (syntax-rules ()
    [(when cond body ...)
     (if cond (begin body ...))]))
```

Pattern:

* LHS: `(when cond body ...)` — an AST pattern with pattern variables `cond` and `body ...`.

Template:

* RHS: `(if cond (begin body ...))` — an AST built from those variables.

Expansion:

```scheme
(when (> x 0) (display x) (newline))
;; → (if (> x 0) (begin (display x) (newline)))
```

Here:

* **R**: AST of the language.
* **T**: term rewriting (M02C09) over AST terms.
* **S**: macro expansion phase before evaluation / lowering.

### 5.2 Example: Template Haskell-Style Quasiquote (Sketch)

A typed macro in a Haskell-like system:

```haskell
-- Quasiquoted AST of an if-then expression
when :: Q Exp -> Q Exp -> Q Exp
when qcond qbody =
  [| if $qcond then $qbody else return () |]
```

Usage:

```haskell
$(when [| x > 0 |] [| print x |])
```

* R: typed AST (`Exp`) in the meta-language.
* T: Haskell code constructing new AST from quasiquotes and splices.
* S: compile-time, after type inference for splices (typed macros).

This is an example of a **post-binding** syntactic macro.

## 6. Macro Expansion as a Rewrite Strategy

From M02C09, every term rewrite system is:

* Terms: some language of trees,
* Rules: `l → r` patterns,
* Strategy: how/where you apply rules,
* Normal form: when no rule applies.

Macro expansion fits this exactly:

* **Terms**: CST/AST (or token trees for token-level macros).
* **Macro redex**: a macro *invocation node*.
* **Rules**: macro definitions: pattern → template.
* **Strategy**: “expand macro redexes” until a normal form.

Typical strategy:

* Outer-to-inner (or parser-driven) expansion until **no macro invocations remain**.
* Normal form: AST with **no macro nodes**.

Issues from M02:

* **Termination**: recursive macros can cause non-termination; M03C14 will return to strategies and fixed-point expansion.
* **Confluence**: overlapping macro patterns can make the result order-dependent; hygienic systems + phase discipline mitigate this.

M02C10: each rewrite `l → r` is supposed to be **semantics-preserving** (or have a clear contract, e.g. “adds logging”). Macro designers must treat their expansions as program transformations with the same obligations as any optimisation pass.

## 7. Textual vs Syntactic in R–T–S and E/S/C

### 7.1 R–T–S Comparison

| Aspect                 | Textual / Token(-Tree) Macros                                        | Syntactic / Typed Macros (CST/AST/HIR)                                    |
| ---------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **R (representation)** | bytes, flat tokens, or token trees (no full node taxonomy)           | CST / AST / typed AST/HIR                                                 |
| **T (transform)**      | substitution, token-level pattern → replacement                      | term rewriting or procedural AST/HIR transformation                       |
| **S (staging)**        | preprocessor / pre-parse / parse-time                                | macro expansion phase after parse (and possibly after name resolution)    |
| Structure awareness    | none or shallow; precedence and binding implicit                     | full tree structure; often access to binding and sometimes types          |
| Binding / hygiene      | absent; cannot systematically avoid capture                          | can be enforced (M03C12: hygiene; M11: typed macros)                      |
| Typical failure modes  | precedence, double eval, capture, tooling blindness, phase confusion | mainly design-level; structure + hygiene avoid most low-level pathologies |
| Tooling integration    | fragile; tools must simulate preprocessor or ignore macros           | natural; same CST/AST/HIR infrastructure as type checker and refactoring  |

### 7.2 Expressiveness / Safety / Complexity (M01C04)

Rough qualitative scores (0–10):

| Family                             | E (Expressiveness) | S (Safety) | C (Complexity) |
| ---------------------------------- | ------------------ | ---------: | -------------: |
| Textual / flat-token macros        | 8–9                |        2–3 |            8–9 |
| Token-tree macros (`macro_rules!`) | 8–9                |        3–5 |            7–9 |
| Syntactic macros (AST, no hygiene) | 8–9                |        4–6 |            6–8 |
| Hygienic / typed syntactic macros  | 8–9                |        7–9 |            7–9 |

Key point:

* Textual/token systems **afford** Tier-3/4 power with very low safety; good design confines them to Tier-0/1 roles.
* Syntactic/typed macros give you similar expressiveness but allow you to trade complexity for significantly higher safety via:

  * structure-aware R,
  * hygiene (M03C12),
  * and typing (Module 11).

## 8. When Text Macros Are (Barely) Acceptable

We want a design rule compatible with WSM/Tiers (M01C05).

Textual macros *afford* high-tier power. Our policy:

> If you use them at all, constrain them to **Tier-0/1 roles**, where failure modes are limited and obvious.

Typical acceptable niches:

1. **Simple constants**

   ```c
   #define MAX_BUFFER 4096
   #define PI 3.141592653589793
   ```

   * RHS is a literal or simple constant expression.
   * Semantics no more complex than a `const` or `enum`.

2. **Include guards and trivial configuration**

   ```c
   #ifndef LIB_CONFIG_H
   #define LIB_CONFIG_H
   ...
   #endif
   ```

   Or:

   ```c
   #ifdef USE_FAST_PATH
     fast_impl();
   #else
     slow_impl();
   #endif
   ```

3. **Extremely mechanical substitutions**

   * rarely-used alias tokens,
   * header compatibility shims,
   * no expressions or control-flow.

In all these cases:

* E: modest (Tier-0/1).
* S: acceptable, as long as macros *cannot* sneak in complex behaviour.
* C: low; the preprocessor usage is visible and can be audited quickly.

If you find yourself:

* manipulating expressions,
* introducing loops or conditionals,
* abstracting over binding or types,

you are in **Tier-2/3 territory** and should move to syntactic macros.

## 9. When You Need Syntactic Macros (Macro Design Dossier)

Consider designing a **logging abstraction** — a common macro use case.

### 9.1 Option A: Textual Macro (C-style)

```c
#define LOG_ERROR(msg, arg) fprintf(stderr, "[ERR] " msg "\n", arg)
```

Pros:

* trivial to write,
* call-site syntax looks like a function.

Cons:

* R is tokens; no type information:

  * mismatch between `msg` and `arg` is caught only at runtime (if at all).
* Can interact badly with control-flow constructs (`if (cond) LOG_ERROR(...); else ...`).
* Tooling cannot treat `LOG_ERROR` as a first-class construct:

  * refactors around logging are brittle,
  * errors often appear at the expanded `fprintf`.

WSM/Tier:

* This is Tier-2/3 concerns (logging, reliability, error diagnosis) built on Tier-3/4 machinery (text macros). Fragile.

### 9.2 Option B: Syntactic Macro (AST-level, Scheme-style)

```scheme
(define-syntax log-error
  (syntax-rules ()
    [(log-error expr)
     (let ([tmp expr])
       (fprintf (current-error-port) "[ERR] ~a\n" tmp)
       tmp)]))
```

Now:

* R is AST; `expr` is a proper expression node.
* T introduces a **fresh binding** `tmp` to ensure **single evaluation** of `expr`.
* Tools can:

  * recognise `(log-error expr)` as a logging construct,
  * attribute type errors to `expr` in user code, not to the macro expansion.

WSM/Tier:

* We are now using Tier-2/3 power (sophisticated logging abstraction) with:

  * much higher safety,
  * better error locality,
  * better alignment with the compiler’s representation.

Design conclusion:

> For any abstraction that touches control flow, evaluation order, or error reporting, **syntactic macros** are the appropriate tool. Textual macros are hard to justify outside trivial Tier-0/1 cases.

## 12. M03C11 Glossary (Compact Reference)

| Term                  | Definition                                                                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Textual macro**     | Macro system operating on raw text or flat tokens without parse-tree structure (e.g. C preprocessor).                                              |
| **Token-tree macro**  | Macro system operating on nested token trees (balanced delimiters, token fragments) but without CST/AST node kinds (e.g. Rust `macro_rules!`).     |
| **Syntactic macro**   | Macro system that manipulates CST/AST (or typed AST/HIR) as structured trees, usually integrated with binding and often with typing.               |
| **Preprocessor**      | Front-end phase performing includes, conditionals, and textual/token-level macro substitutions before real parsing.                                |
| **Macro expansion**   | Process of rewriting macro invocations into ordinary syntax according to macro definitions, typically until no macro invocations remain.           |
| **Hygiene** (preview) | Property that macro expansion preserves lexical binding and avoids name capture; core topic of M03C12.                                             |
| **Token tree**        | Nested structure of tokens grouped by delimiters; richer than flat tokens but poorer than CST/AST.                                                 |
| **Tier (WSM)**        | Qualitative level of meta-power vs safety/complexity (M01C05); textual macros afford high-tier power, but good practice confines them to Tier-0/1. |

You now have:

* a classification of macro systems by **representation (R)**,
* an understanding of why textual and token-level macros are fragile,
* and a view of syntactic macros as **term-rewriting over AST/HIR** with the same correctness obligations as compiler passes.

* how even syntactic macros can break lexical scope via **name capture** and **shadowing**,

* and how hygienic macro systems restrict T so that macros preserve binding structure by construction.
