## 1. Name Capture as a Binding Invariant Violation

From M02C07:

* A **binder** introduces a variable (e.g. `let x = …`, `λx. …`, `fn(x) { … }`).
* A **use** is an occurrence of an identifier.
* A **binding graph** links each use to the binder it refers to.
* Two programs are **α-equivalent** if they differ only by systematic renaming of bound variables.

From M02C10:

* Semantics and correctness are defined up to **contextual equivalence**:
  `P` and `P'` must behave the same in all contexts.

**Name capture** (in macros or any transform) is exactly the situation where:

> After transformation, some identifier uses now refer to **different binders** than before, in a way that was not intended by the programmer.

In terms of the binding graph:

* We start with program `P` and a binding graph `B(P)`.
* We transform `P` to `P'` (e.g. macro expansion).
* If there is **no** α-renaming of `P'` such that its binding graph matches `B(P)` on the original identifiers, we have suffered **capture**.

This is generally a **semantic preservation** failure: `P` and `P'` are not contextually equivalent because their binding structure (and hence values/effects) differ in some contexts.

Macros are particularly prone to capture because they:

* introduce new binders,
* duplicate or move user code,
* operate across lexical scopes.

## 2. Two Canonical Forms: Introduced-Name vs Argument Capture

We separate two common flavours of capture bugs in macros.

### 2.1 Introduced-Name Capture

The macro introduces a new binder whose name collides with a name in the user’s code.

Scheme-like example (non-hygienic):

```scheme
(define-syntax my-or
  (syntax-rules ()
    [(my-or a b)
     (let ((tmp a))
       (if tmp tmp b))]))
```

Intended client code:

```scheme
(my-or (> x 0) (> y 0))
```

Now put it in a context:

```scheme
(let ((tmp #f)
      (x 1))
  (my-or (begin (set! tmp #t) (> x 0))
         tmp))
```

Depending on the macro system:

* the `tmp` introduced by the macro can **collide** with the user’s `tmp`,
* the `set!` or the final `tmp` in the call can refer to the “wrong” `tmp`,
* behaviour changes in a context-dependent way.

Here:

* The macro introduced a binder `tmp`.
* That binder shadows or is shadowed by an existing `tmp`.
* The binding graph on `tmp` uses has changed.

> **Introduced-name capture:** new binders added by the macro accidentally collide with user-defined names, breaking binding invariants.

### 2.2 Argument Capture

The macro rearranges how user-supplied identifiers are scoped, so that their binding changes.

Toy Scheme example (deliberately bad):

```scheme
(define-syntax with-lock
  (syntax-rules ()
    [(with-lock lock expr)
     (let ((lock lock))          ; problematic
       (acquire lock)
       (let ((result expr))
         (release lock)
         result))]))
```

Intention:

```scheme
(with-lock my-lock
  (critical-section))
```

Now a problematic context:

```scheme
(let ((lock "outer"))
  (with-lock lock
    (begin
      (display lock)  ; which 'lock'?
      (critical-section))))
```

The macro:

* creates a new `lock` binding,
* the inner `lock` in `expr` may now refer to the macro-introduced binding, not the outer one,
* the **binding of the user’s `lock` inside `expr` changed**.

> **Argument capture:** the macro transform moves user code across binders or introduces new binders such that user identifiers in arguments are rebound or shadowed unintentionally.

Both forms are binding-graph changes. Introduced-name capture is “macro invented a bad binder name”; argument capture is “macro moved my code under a binder I didn’t expect”.

## 3. Manual Defences: α-Conversion and Gensyms

M02C07 gave us **α-conversion**:

* we can rename bound variables (`λx. x+1` → `λy. y+1`) without changing semantics,
* the binding graph structure is preserved (just node labels change).

In non-hygienic macro systems, authors emulate α-conversion manually.

### 3.1 Ad-Hoc Renaming Conventions

In C or raw Lisp `defmacro`, a common discipline is:

* “Use weird names for macro locals”:

  * `__tmp12345`, `__MY_LIB_INTERNAL_RESULT__`, etc.

This reduces collision probability, but:

* does not guarantee uniqueness across libraries,
* does not scale in the presence of many macro authors,
* relies entirely on human discipline.

### 3.2 Gensyms: Mechanised Freshness

Many Lisp systems provide **gensym**:

* `gensym "tmp"` returns a brand-new identifier, guaranteed to be distinct from any user-written identifier,
* macro systems can then expand using these unique binders.

Rewritten `my-or` (schematic):

```scheme
(define-syntax my-or
  (lambda (stx)
    (syntax-case stx ()
      [(_ a b)
       (with-syntax ([tmp (datum->syntax stx (gensym "tmp"))])
         #'(let ([tmp a])
             (if tmp tmp b)))])))
```

Here:

* For each expansion, `tmp` is a fresh binder.
* No user-written name can collide with it.

Gensyms are essentially **automated α-renaming** for macro-local binders.

### 3.3 Limits of Gensyms

Gensyms solve **introduced-name capture** (macro locals clashing with user names).

They do **not** automatically solve **argument capture**:

* macros can still move or duplicate user expressions,
* macros can still introduce new binders that change how user identifiers are resolved (even if those new binders have fresh names).

They also do not regulate which environment free identifiers in the macro body refer to (definition vs call site).

To control that, we need a richer invariant: **hygiene**.

---

## 4. Hygiene: Canonical Informal Definition

We now want a single, sharp description.

> **Hygiene (informal definition).**
> A macro system is **hygienic** if, for any well-formed program `P`, macro expansion produces a program `P' = Expand(P)` such that:
>
> 1. There exists an α-renaming of `P'` whose **binding graph** on the original identifiers is the same as in `P` (no accidental rebinding or capture), and
> 2. Any new binders introduced by macros are **fresh** and their uses do not alter existing binding relationships.

Equivalent views:

* **Lexical scope preservation:** expansion does not break or create lexical links except where the macro explicitly intends to.
* **Free/bound set stability:** for the original program, free vs bound variables remain free vs bound after expansion, up to α-renaming.
* **Sugar view:** a hygienic macro behaves like a trusted desugaring pass: if you hand-expanded it with fresh names and correct scopes, you’d get an α-equivalent program.

Key point:

* Hygiene is about **binding structure**, not about performance or other optimisations.
* It is a **necessary condition** for semantic preservation in binding-sensitive languages (though not sufficient: macros can still reorder side effects, etc.).

## 5. Binding-Aware Expansion and Rewrite Strategies

To enforce hygiene, expansion must see more than raw syntax.

### 5.1 R = AST + Binding

Conceptually, for hygienic macros:

* **R (representation)** is not just AST, but **AST annotated with binding information**, e.g.:

  * each identifier use has a link to its binder,
  * or each AST node carries scope marks / environment markers.

Macro expansion is then:

* a transformation `Expand : R → R` on this binding-aware AST.

### 5.2 Expansion as a Rewrite System (M02C09 Lens)

From M02C09, we saw term rewriting:

* terms,
* patterns,
* rewrite rules,
* strategies,
* normal forms.

Macro expansion fits directly:

* **Terms:** AST + binding info.
* **Redexes:** macro invocation nodes.
* **Rules:** macro definitions (pattern → template).
* **Strategy:** macro expansion policy (outermost/innermost, fixed-point).
* **Normal form:** AST with **no macro invocations** (macro-normal form).

Hygiene adds:

> Every rewrite step must preserve the binding graph on the **non-macro parts** of the program (up to α-renaming).

So macro expansion is:

* a **rewrite strategy** that:

  * repeatedly eliminates macro redexes,
  * maintains a strong binding invariant.

Later (M03C14) we will look at strategies in more detail (e.g. recursive macros, fixed-point expansion).

### 5.3 Binding Graph Illustration (Conceptual)

Consider a tiny program (pseudo-ML):

```text
let x = 1 in
let y = f x in
log_and_return!(y + x)
```

Bindings before expansion:

* `x` at use in `f x` → `let x = 1`.
* `x` at use in `y + x` → `let x = 1`.
* `y` at use in `y + x` → `let y = f x`.
* `f` at use in `f x` → some global `f`.
* `log_and_return!` → macro definition.

Suppose (ignoring logging details) the macro expands to:

```text
let x = 1 in
let y = f x in
let tmp = y + x in
print tmp;
tmp
```

A hygienic expansion ensures:

* a **fresh** `tmp` binder,
* the uses of `x`, `y`, `f` still point to the same binders as before,
* the new uses of `tmp` point only to the macro-introduced binder.

The **binding graph** over original identifiers (`x, y, f`) is unchanged; we’ve simply extended it by adding a new node `tmp` and its edges. This is exactly the condition in the hygiene definition.

## 6. Definition-Site vs Call-Site Environments, and Referential Transparency

Macros conceptually live in two lexical environments:

1. **Definition-site environment (def-env)**:

   * where the macro itself is defined,
   * contains bindings the macro author expects to use (e.g. standard functions, helpers).

2. **Call-site environment (call-env)**:

   * where the macro is invoked,
   * contains bindings visible to the user at the call.

Hygienic macro systems must decide:

* identifiers appearing in the macro **body/template**:

  * usually resolved in the **def-env**,
* identifiers appearing in macro **arguments**:

  * resolved in the **call-env**.

This is one way to phrase **referential transparency** for macros:

> A hygienic macro is referentially transparent if:
> – free identifiers in its *definition* refer to the bindings intended by the macro author (def-env), and
> – identifiers in its *arguments* refer to the bindings intended by the macro user (call-env).

Without such a discipline:

* a locally defined `+` at the call site might accidentally override the macro’s intended `+`,
* or conversely, a macro might pick up an unintended binding from a local scope.

Hygienic systems implement this with marks/scopes in the syntax object, but conceptually it is just: **keep def-env and call-env separate, and use each where appropriate**.

## 7. Intentional Capture and Escape Hatches

Sometimes capture is **intentional**:

* a macro that introduces implicit bindings for a user-supplied identifier (e.g. a DSL that translates `with x = … in …` into a let-binding),
* a macro that implements dynamic scoping or parameter rebinding by carefully crafted lexical binding.

If a system were “perfectly hygienic” in a rigid sense, such macros would be impossible.

Real systems therefore:

* enforce **hygiene by default** (no accidental capture), and
* offer **explicit escape hatches** to allow controlled capture.

Typical patterns:

* low-level APIs (e.g. `datum->syntax` in Scheme/Racket) that allow manual control of scope,
* procedural macros that can create identifiers bound to either def-env or call-env,
* “unsafe” primitives for advanced users.

In the WSM/Tier lens:

* **Default hygienic macros**:

  * Tier-2: structured abstractions, widely usable,
  * safety high; complexity moderate.
* **Intentional-capture macros**:

  * Tier-3/4: power tools for experts,
  * must be rare, documented, and carefully audited.

Design rule:

> Make “no capture” the default. Make “capture” explicit, rare, and clearly marked.

## 8. Hygiene in Real Systems: Rust as a Sketch

Rust provides two main macro mechanisms:

1. **Declarative macros (`macro_rules!`)**

   * Operate on **token trees** (M03C11).
   * Provide a **hygiene-like discipline**:

     * pattern variables are bound hygienically,
     * newly introduced names can be made fresh,
     * accidental capture is reduced compared to C macros.
   * However, they work at the token-tree level, not over an explicit binding graph:

     * hygiene is encoded structurally via scoping rules on token trees,
     * not via a full AST + binding graph in the sense of M02C07.

2. **Procedural macros (derive, attribute, function-like)**

   * Operate on compiler ASTs exposed via APIs (e.g. `TokenStream` + libraries such as `syn`).
   * Macro authors have substantial power:

     * can construct identifiers to refer to items in the macro crate (def-env) or in the call site,
     * must manage freshness and capture largely by convention and helper utilities.

We mention Rust here purely as an **illustrative ecosystem**:

* declarative macros show how far you can get with structured token-level hygiene,
* procedural macros illustrate the challenges once you let users manipulate (typed) ASTs directly.

Later (Module 11) we will look at systems where R is **typed AST/HIR with an explicit binding graph**, and hygiene becomes part of a **typed macro** contract.

## 9. Hygiene as a Correctness Condition (M02C10 Lens)

From M02C10:

* A transform `T` is semantics-preserving if, for all programs `P`, `⟦P⟧ = ⟦T(P)⟧` in all contexts.

For macro expansion `Expand`:

* we want `Expand` to be semantics-preserving modulo explicitly intended changes (e.g. logging macros that add I/O).

Name capture is almost always a **witness of non-equivalence**:

* there exist contexts where the original and expanded programs behave differently,
* the difference arises purely from changed bindings, not from the macro’s stated purpose.

Thus:

* **Hygiene is a necessary (but not sufficient) condition** for macro correctness in binding-sensitive languages:

  * if hygiene fails, contextual equivalence almost certainly fails,
  * if hygiene holds, we still must consider effects, evaluation order, etc.

In R–T–S terms:

* **R**: AST + binding (and later types).
* **T**: expansion strategy (rewrite system) satisfying hygiene.
* **S**: expansion phase in the front-end pipeline (M03C14, M10C47).

Viewing hygiene as a **global invariant on T** aligns with the general design philosophy from M02C10: passes must have explicit, verifiable correctness obligations.

## 10. WSM/Tier Perspective

Recall WSM/Tiers (M01C05):

* Tier-0/1: simple, local features, low global risk.
* Tier-2: structured, composable abstractions; some risk.
* Tier-3/4: high-power features with significant global impact.

Positioning macro mechanisms:

* **Textual macros** (M03C11):

  * afford Tier-3/4 power,
  * disciplined use confines them to Tier-0/1 tasks (constants, guards),
  * inherently low safety.

* **Hygienic syntactic macros** (this core):

  * intended as Tier-2 by default:

    * they behave like compiler-implemented sugar,
    * can be widely used without constant fear of capture bugs.
  * more expressive systems (with procedural/typed macros) can reach Tier-3:

    * powerful, but need more expertise and careful review.

* **Intentional-capture / low-level macro features**:

  * Tier-3/4:

    * should be rare and reserved for macro library authors,
    * part of the “power tools” surface of the language.

Design takeaway:

> If your language has a significant macro story, hygiene is what keeps that story in Tier-2 rather than turning the whole ecosystem into permanent Tier-3/4 crisis mode.

## 13. M03C12 Glossary (Compact Reference)

| Term                            | Definition                                                                                                                                            |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Name capture**                | Unintended change in which binder an identifier refers to after a transformation (e.g. macro expansion), breaking the original binding structure.     |
| **Introduced-name capture**     | Capture caused by new binders introduced by a macro colliding with names already present in the user’s program.                                       |
| **Argument capture**            | Capture where the bindings of user-supplied identifiers change because the macro rearranges scopes or inserts additional binders.                     |
| **α-conversion**                | Renaming bound variables (and their uses) to fresh names, preserving semantics and the binding graph.                                                 |
| **Gensym**                      | Mechanism that generates a fresh, globally unique identifier at macro expansion time, used to avoid introduced-name capture.                          |
| **Hygiene (macros)**            | Property of a macro system that macro expansion preserves lexical scope and the original binding graph up to α-renaming, avoiding accidental capture. |
| **Binding-aware expansion**     | Expansion model where macros operate on ASTs annotated with binding information and must preserve the binding graph for original identifiers.         |
| **Definition-site environment** | Lexical environment where a macro is defined; typically used to resolve free identifiers appearing in the macro’s own body/template.                  |
| **Call-site environment**       | Lexical environment at the macro invocation; used to resolve identifiers in macro arguments.                                                          |
| **Intentional capture**         | Deliberate use of macros to change binding relationships (e.g. introducing new bindings for user-supplied identifiers), usually via explicit escapes. |
