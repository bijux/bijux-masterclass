## 1. Why Macro Debugging Is Harder

### 1.1 Three Views of the Program

Macro-heavy compilation has at least three distinct views:

1. **Source view** (what the user wrote)

   * files, tokens, CST,
   * macro invocations appear as compact, readable constructs.

2. **Expanded view** (macro-normal form; M03C14)

   * all macros expanded (or expanded for the relevant phase),
   * typically a much larger AST,
   * what the type checker, optimiser, and code generator see.

3. **IR / machine-code view**

   * lowered representations (M02C08),
   * relevant for performance and low-level debugging.

All real errors happen in *some* internal configuration of the compiler:

* type mismatch in expanded code,
* missing field in desugared pattern,
* non-terminating loop in generated IR.

But humans reason in terms of **source view**.

**Debuggability goal (invariant):**

> Every error that is structurally located in expanded or IR-level code must be explainable, in the *primary diagnostic*, in terms of a small, recognisable patch of user-written source.

Macro systems make this non-trivial because:

* expansion is a separate phase (M03C14),
* expanded structure can be very far from the original macro call,
* hygiene and phase separation hide some causes “on purpose”.

### 1.2 A “Correct but Miserable” Example

Consider a perfectly hygienic macro:

```text
when_debug!(expr)  =>  if DEBUG { log(expr); expr }
```

Now, in user code:

```text
when_debug!(foo(bar, baz));
```

Suppose `log(expr)` is badly typed in some configuration (e.g. wrong trait bound) but only in certain modules.

* Semantics and hygiene are fine: expansion is correct *as a macro*, binding is preserved.
* But the type checker reports:

  ```text
  error[E1234]: no method `log` for type `Foo` in the current scope
    --> expanded.rs:5000:17
  ```

with no connection to `when_debug!` on line 42 in `user.rs`. From a user perspective:

* the macro system is “correct”,
* but debugging is painful,
* they must mentally reconstruct which macro invocation caused the error.

This core is about avoiding that situation in well-designed macro systems and libraries.

## 2. Spans, Origin Chains & Expansion Maps

### 2.1 Spans on Syntax Objects

In a macro-aware compiler, every syntax node in R (AST / syntax object) carries at least:

* a **span**: `(file, start_offset, end_offset)` or `(file, start_line/col, end_line/col)`,
* optionally a tag: `synthetic` vs `from_source`.

In syntax-object terms (M03C13):

* R = AST node + scope marks + span metadata.
* T (macro expansion) must transform R→R while:

  * preserving scope/hygiene invariants (M03C12),
  * maintaining enough span information to support diagnostics.

### 2.2 Origin Chains and Expansion Maps

Simple model:

* each node has:

  ```text
  span: current location
  origin: pointer to some earlier node
  ```

In practice, you often need an **origin chain**:

```text
user source node
   ^  (macro call)
   |
expansion from macro body
   ^  (further macro call)
   |
nested expansion
   ...
   → final expanded node where error occurs
```

An **expansion map** records, for each node:

* its current span,
* its immediate origin (which in turn has its own origin, forming a chain),
* the macro call (if any) and macro definition responsible for the step from origin→current.

When the type checker reports an error at expanded node `n`:

1. It knows `n.span` in the expanded file.

2. It walks `origin` links to find:

   * the nearest **macro call site** in user code,
   * relevant **macro definition** locations.

3. It can choose a primary reporting location at the *call site* and additional notes at macro definitions.

**Invariant (for phase-clean expansion):**

> After expansion to macro-normal form for a given phase, every remaining AST node must either:
>
> * have an origin chain that reaches some user source span, or
> * be explicitly marked synthetic and appear only in contexts where synthetic nodes are expected.

### 2.3 Span Propagation Policies

Different policies have different ergonomics.

1. **All definition spans**

   * All expanded code inherits spans from macro definitions.
   * Diagnostics mostly point at macro files.
   * Users see: “error in macro” even when they misused it.

   → Almost always a bad choice.

2. **All call-site spans**

   * All expanded code inherits the span of the macro invocation.
   * Diagnostics point at macro call sites.
   * Good for error locality, but macro authors lose context.

3. **Mixed / origin chain-aware**

   * Structural scaffolding sometimes tagged with macro-definition spans.
   * User arguments carry call-site spans.
   * Origin chains record both.

   → Good compromise: user-facing primary locations at call sites, optional macro-author views that walk back to macro definitions and body.

Design recommendation:

> Make **call-site spans** the primary anchor for diagnostics. Use definition spans only when reporting bugs *inside* the macro implementation, and keep full origin chains for tooling and macro-author modes.

## 3. Macro Backtraces & Responsibility

### 3.1 Expansion Stack and Backtrace

When macros expand other macros, expansion has a **stack**:

```text
error in expanded node
 ↳ came from expansion of helper_macro! (call site B, definition at macros.rs:30)
   ↳ came from expansion of my_macro! (call site A, definition at macros.rs:10)
     ↳ came from user code (user.rs:42)
```

A schematic diagnostic:

```text
error[E1234]: mismatched types
  --> src/user.rs:42:15
   |
42 |     my_macro!(x);
   |               ^
   |
note: in expansion of `my_macro!` (defined at src/macros.rs:10:1)
  --> src/user.rs:42:5
   |
42 |     my_macro!(x);
   |     ^^^^^^^^^^^^
note: in expansion of `helper_macro!` (defined at src/macros.rs:30:1)
  --> src/macros.rs:12:9
   |
12 |         helper_macro!(x)
   |         ^^^^^^^^^^^^^^^^^
```

Conceptually:

* primary error at **user call site**,
* secondary notes show the **macro expansion stack**.

### 3.2 Signal vs Noise

Full macro backtraces can be long and intimidating:

* deep generic derivations,
* DSLs expanding through many layers.

Practical strategy:

* **User mode**:

  * show primary diagnostic at call site,
  * show one short note: “in expansion of `my_macro!` defined here: …”,
  * allow user to expand full backtrace on demand (flag or IDE action).

* **Macro-author mode**:

  * compiler flag: full macro backtraces for all errors,
  * integrate with expansion visualisation tools.

### 3.3 Misuse vs Macro Bug

The compiler and macro API design should make it **easy** to distinguish:

* **Macro misuse** (user error):

  * arguments have wrong shape,
  * required attributes or patterns missing,
  * semantics contract violated.

* **Macro bug** (library error):

  * valid usage expands to ill-typed or ill-formed code,
  * expansion fails internally.

Design guidance:

1. Macro APIs should check preconditions and fail with **explicit compile-time errors** at the call site when misused.

2. Only when preconditions are met and expansion still generates bad code should the compiler treat it as a **macro bug**, with diagnostics pointing at the macro definition and expanded code context.

Origin chains and macro backtraces support both views:

* call-site centric for users,
* macro-definition centric for authors.

## 4. Expansion Visualisation

### 4.1 Full Expansion

An essential tool: “show me what the compiler sees”.

* Given a module or file, show its code after macro expansion to macro-normal form for the relevant phase (M03C14).
* Optionally annotate:

  * which fragments came from which macros,
  * which nodes are synthetic,
  * origin spans.

**Critical requirement:**

> Expansion visualisation must use the same expansion algorithm, phases, and strategies as real compilation. A debug-only expander that behaves differently is worse than no tool.

### 4.2 Stepwise & Phase-by-Phase Expansion

Full expansion can be huge. For many debugging tasks, users want:

* a **single step**:

  * expand macros in the file once,
  * show one layer of expansion while leaving nested macro calls visible.

* or **phase-wise views**:

  * after core macros but before user macros,
  * after user syntactic macros but before typed macros,
  * etc.

These map directly to:

* **macro phases** and **tiered macro layers** (M03C14),
* **macro-normal forms** per phase: “no core macros left”, “no user macros left”, etc.

Stepwise tools:

* help users understand a particular macro in isolation,
* reduce cognitive load by not showing irrelevant expansions.

### 4.3 Hygiene and Binding Views

For hygienic macros (M03C12):

* correctness is about binding graphs and scope marks (M02C07).
* Debugging hygiene issues often requires seeing:

  * which use binds to which definition,
  * def-site vs call-site resolution.

Tools can:

* highlight all uses bound to a particular var,
* show scope regions and arrows (binding graph overlays),
* annotate identifiers with scope marks.

This essentially exposes:

* the **binding graph** (M02C07),
* hygiene metadata (M03C12),

in a human-readable form.

## 5. Designing Debuggable Macro APIs

### 5.1 Structural, Hygienic Macros Over Syntax Objects

Debuggable macros are:

* structural: operate on syntax objects (AST + scopes + spans),
* hygienic: preserve binding and lexical scope.

Textual macros / string templates (M03C11):

* lose structure and binding,
* are invisible to structural tools (e.g. AST-based linters),
* produce poor source mapping.

Design rule:

> For any macro intended for broad use, design it as a **structural, hygienic macro** over syntax objects. Treat stringly codegen as a separate code-generation pipeline (Module 8), not as your primary macro mechanism.

### 5.2 Naming, Control Flow, and Surface Clarity

Macros can hide a lot of behaviour. To keep them debuggable:

1. **Name signals intent**

   * Names that look like functions should behave function-like:

     * no surprising non-local control flow,
     * no hidden resource management.
   * Names that indicate control (e.g. `if_`, `loop_`, `with_`) may encode control flow.

2. **Control-flow transparency**

   * Do not introduce non-local control flow (`return`, `break`, `throw`) from macros unless:

     * the macro is explicitly control-like (syntactically obvious), and
     * language syntax makes this clear (e.g. dedicated macro-only keywords, special forms).

   * Tailored control constructs (e.g. `for_each!`) are fine if they look like control constructs.

3. **Argument shape clarity**

   * Use pattern languages (M03C13) to constrain arguments to specific categories (`expr`, `pat`, `type`).
   * Avoid “catch-all” token slurping that interprets arbitrary syntax in non-obvious ways.

4. **Public vs internal macros**

   * Keep the **public macro surface** small and namespaced.
   * Internal helper macros may be rougher but should not leak into public diagnostics.

### 5.3 Fail Early, at the Call Site

A debuggable macro:

* validates its inputs early,
* fails **at the call site** with clear messages.

Mechanics:

* use pattern matching and syntax inspection to enforce shape constraints,
* on violation, emit a compile-time error (e.g. `compile_error!`) whose span is the macro call span.

Bad pattern:

* rely on type-checking of deeply nested generated code to catch misuse.

Good pattern:

* macro inspects argument,
* if shape is wrong, error like:

  > “`my_macro!` expects an enum type, got a struct here.”

anchored at the macro call.

### 5.4 Stable Contracts and Compatibility

Macros are APIs:

* they have input assumptions,
* output invariants,
* semantic guarantees (M02C10),
* hygiene guarantees (M03C12).

Once a macro is public:

* its behaviour is part of the **compatibility surface**,
* changes to its expansion are akin to API changes.

Design expectations:

* document the contract,
* enforce it with compile-time checks and tests,
* treat behaviour changes as potentially breaking changes.

This is why golden tests and metamorphic tests (next section) are not optional niceties but tools to preserve user trust.

## 6. Testing and Regression for Macros

### 6.1 Golden Expansion Tests

A simple but powerful strategy:

* pick representative macro invocations,
* run them through the actual expander,
* pretty-print the expanded form,
* compare against a stored baseline (golden file) in CI.

Purpose:

* detect unintended changes in macro expansion behaviour,
* ensure refactors don’t silently alter semantics.

Better targets:

* rather than raw expanded surface AST, consider:

  * a **canonicalised core form** (post-desugaring, stable AST),
  * with a stable pretty-printer.

This aligns with:

* IR-first thinking (M11C52),
* stability under internal compiler changes.

### 6.2 Property and Metamorphic Testing

Beyond fixed examples:

* express invariants as **relations** between:

  * macro-generated code, and
  * a specification implementation.

Examples:

* `log_and_return!(e)`:

  * property: same return value as `e` for all inputs, plus an extra log effect.

* `derive_eq!`:

  * property: generated `eq` matches a reference definition for randomly generated values.

Method:

* generate random input structures within a constrained grammar,
* expand macros and run both the generated implementation and a hand-written oracle,
* compare results (and possibly side effects).

This is metamorphic testing at the macro level.

### 6.3 Integrating with Ordinary Tests

Ultimately, macros produce plain code:

* functions, trait instances, types.

Strategy:

1. Use macros in your codebase.
2. Test the generated APIs with ordinary unit/property tests.
3. Combine with explicit macro-level tests (goldens, metamorphic tests) for additional assurance.

This gives:

* indirect semantic testing via API behaviour,
* plus direct shape/expansion testing at the macro level.

## 7. Macro Telemetry and Meta-Budgeting

### 7.1 Tracing and Scoped Logging

During macro development:

* you may want to:

  * trace expansions,
  * log intermediate syntax,
  * measure expansion depth/size.

Pitfalls:

* global “log every expansion” is unusable in large codebases,
* logging must not change semantics.

Design:

* provide **scoped tracing**:

  * flags or attributes to trace specific macros or modules,
  * IDE options to enable tracing for the file under inspection.

* ensure logging is:

  * compile-time only,
  * disabled in normal builds by default.

### 7.2 Expansion Size, Depth and Compile-Time Cost

Macros can contribute significantly to compile-time cost and binary size:

* deeply recursive expansions,
* large code templates,
* combinatorial explosions.

Telemetry:

* per-macro statistics:

  * number of expansions,
  * average/max expansion size,
  * max expansion depth,
  * compile-time spent in expansion.

This folds into **meta-budgeting** (M10C49):

* define acceptable budgets for:

  * expansion depth,
  * generated code size,
  * compile-time overhead per macro.

* enforce via:

  * warning thresholds,
  * lints,
  * CI checks.

Well-designed macro systems:

* make it possible to see which macros are consuming the budget,
* give library authors feedback to redesign macros if they are too expensive or noisy.

## 8. WSM/Tiers and the Macro Paradox (Preview)

M01C05 and M10C46 define **WSM/Tiers** and the **macro paradox**:

> More meta-power can *reduce* overall reliability if used without discipline and tooling.

Macro debuggability is one of the key discriminators between tiers:

* **Tier 1–2 macro usage**

  * structural, hygienic macros,
  * phase-clean expansion (M03C14),
  * good spans, origin chains, backtraces,
  * expansion visualisation and hygiene views,
  * clear contracts, early errors.

  From the user’s perspective, macro use feels like using a well-designed library.

* **Tier 3–4 macro usage**

  * opaque procedural macros,
  * cross-phase leaks (depends on type/IR/optimiser),
  * poor mapping from errors to source,
  * no reliable expansion tooling,
  * heavy compile-time costs with little visibility.

  Even if *theoretically* hygienic or correct, such systems are practically Tier 3/4 because debug cost and risk are high.

Key point:

> Debuggability is not an afterthought. It is a **core dimension** of where macro usage sits on the WSM/Tier axis.

A macro system with excellent hygiene but poor diagnostics/visibility is, in practice, closer to Tier 3 than Tier 2.

## 10. Exercises

1. **Span Propagation Policy**

   Consider a macro system where each AST node has:

   * `span`: file + start/end positions,
   * `origin`: optional pointer to another node (forming a chain).

   a. Design a span/origin propagation policy for:

   ```text
   when(cond) { body }  =>  if (cond) { body }
   ```

   so that type errors in `cond` or `body` are reported at the macro call site, not at synthetic internal nodes.

   b. Extend your policy for:

   ```text
   with_tmp(expr, body)  =>  { let tmp = expr; body }
   ```

   Explain how you distinguish macro-local scaffolding (`let tmp = …`) from user expressions in diagnostics.

   c. Describe a situation where pointing primarily to the **macro definition** (rather than the call site) is the right choice, and how your origin chains support that mode.

2. **Macro Backtrace Design**

   A compiler currently reports only:

   > “Type error at line 500 of `expanded.rs`.”

   You must improve diagnostics for macro users.

   a. Sketch a macro backtrace display for a type error arising in a nested macro expansion. Include:

   * primary error at the user call site,
   * at least one macro expansion frame,
   * macro definition location.

   b. Propose a UX strategy that:

   * keeps backtraces *collapsed by default* for beginners, and
   * allows experts to expand them on demand.

   c. Outline how you’d integrate backtraces with an IDE:

   * clicking on call-site frames jumps to user code,
   * clicking on definition frames jumps to macro code.

3. **Designing a Debuggable Error-Handling Macro**

   Define a macro:

   ```text
   try_or_log!(expr)
   ```

   which:

   * evaluates `expr: Result<T,E>`,
   * on `Ok(v)` returns `v`,
   * on `Err(e)` logs `e` and returns `Default::default()`.

   a. Sketch a plausible structural, hygienic expansion for `try_or_log!(expr)` (pseudo-code is fine).
   b. Identify two misuses you want to detect early (e.g. `expr` is not a `Result`, use in a non-returning context) and explain how the macro can emit clear compile-time errors at the call site.
   c. Describe a test suite for this macro:

   * golden tests for expansion shape,
   * property tests for semantic behaviour,
   * integration tests in a small example program.

4. **Golden Tests vs Compiler Changes**

   You maintain golden expansion tests for a set of macros (`when`, `for_each`, `log!`, etc.). A new compiler release changes its internal desugaring and pretty-printing, and many golden tests fail even though semantics are unchanged.

   a. Discuss how you could reduce flakiness by choosing a better **canonical form** as golden target (e.g. core AST form).
   b. Propose a process to update golden files when compiler changes are genuinely benign (tooling and review).
   c. Suggest one metamorphic property (e.g. “`when(cond){body}` behaves like `if (cond){body}`”) and outline a property-based test that is robust across compiler versions.

5. **WSM/Tier Evaluation of a Macro Library**

   You audit a macro-heavy library that:

   * uses procedural macros tightly coupled to type and IR details,
   * offers no expansion visualisation,
   * often produces error messages pointing only to generated code,
   * significantly increases compile time on large projects.

   a. Classify this library on the WSM/Tier scale and justify your rating.
   b. Propose three concrete steps to move everyday usage toward Tier 2 (e.g. adding expansion tools, improving error locality, limiting cross-phase assumptions, adding telemetry).
   c. For one of your steps, define how you would measure its impact on debuggability or meta-cost (e.g. average distance from error spans to user code, number of macro-related support tickets, or compile-time telemetry).

## 11. M03C15 Glossary (Compact Reference)

| Term                        | Definition                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Span**                    | Source location attached to a syntax node (file + start/end positions), used as the primary anchor for diagnostics.                                                             |
| **Origin chain**            | Chain of references from an expanded node back through macro expansions to original user source nodes; forms the basis of expansion maps.                                       |
| **Expansion map**           | Compiler-maintained metadata mapping nodes in expanded syntax to their origin chains (user spans, macro calls, macro definitions).                                              |
| **Macro backtrace**         | Stack-like trace of nested macro expansions (call sites and definitions) that explains how an error in expanded code arose from user source and macro invocations.              |
| **Expansion visualisation** | Tooling that shows macro-expanded code (fully or by phase) with annotations indicating macro origins and synthetic nodes.                                                       |
| **Structural macro**        | Macro that operates over structured syntax objects (AST + scopes + spans), typically hygienic and amenable to structural tooling and good diagnostics.                          |
| **Error locality (macro)**  | Property that diagnostics involving macros are reported as close as possible to the user’s macro call site and/or the responsible macro definition, not deep in generated code. |
| **Golden expansion test**   | Regression test that compares macro-expanded output against a stored canonical baseline to detect changes in expansion behaviour.                                               |
| **Metamorphic macro test**  | Test that checks relational properties (e.g. behavioural equivalence to a spec) over many inputs instead of directly asserting on expanded text.                                |
| **Macro telemetry**         | Measurements and logs specific to macro expansion (e.g. expansion size, depth, compile-time cost) used to manage meta-budget and detect problematic macros.                     |
| **Debuggable macro API**    | Macro interface designed with clear contracts, structural patterns, early error checks, and good error sites, making macro usage and failures understandable and diagnosable.   |
