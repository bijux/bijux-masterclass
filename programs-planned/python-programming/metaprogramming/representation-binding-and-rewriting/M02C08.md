## 1. IRs in the R–T–S Triad

Recall R–T–S:

* **R** – representation of programs.
* **T** – transforms over R.
* **S** – when/where in the toolchain T is applied.

In M02C06–07:

* R was **CST/AST (+ binding)**.
* T was mostly “AST → AST” transforms.
* S was the **front-end** (parsing, name resolution, early checks).

Here we extend the picture:

> Modern compilers use a *stack* of **IRs as R**, each chosen to make certain Ts cheap and robust at particular S points (front-end, middle-end, back-end).

So the high-level pipeline becomes:

```text
Source
  → CST
  → AST (+ binding)
  → HIR (high-level, desugared)
  → MIR / CFG / SSA (mid-level)
  → Low-level IR (LLVM IR, JVM bytecode, Python bytecode, …)
  → Machine code / VM execution
```

A serious metaprogramming system must decide:

* **Which IR(s) are the official R for meta?**
* **At which stages S do meta Ts plug in?**

## 3. What Is an IR?

An **Intermediate Representation (IR)** is an internal language used by compilers and tools to represent programs between front-end parsing and back-end code generation.

Key properties:

1. **Structured**
   Not strings. Has explicit node types / opcodes / typing rules.

2. **Simplified vs source**
   Many surface constructs are gone; behaviourally equivalent core constructs remain.

3. **Analysis-friendly**
   Designed so that **data-flow**, **control-flow**, and optimisations are easy to express.

4. **Layered**
   You don’t get “the IR”; you get a **hierarchy of IRs**, each with different invariants.

As R:

* AST is good R for *source-level* meta (macros, refactorings).
* IRs (HIR/MIR/SSA) are good R for *semantics-level* meta (optimisations, safety checks, performance Tunings).

## 4. The IR Stack on the Running Example

### 4.1 AST (Surface-Level R)

Ignoring details, the AST for `sum` has:

* `Fn` node with:

  * parameter `xs: &[i32]`,
  * body containing:

    * `let mut acc = 0;`
    * `for x in xs { acc += x; }`
    * `acc`.

AST invariants:

* **Surface constructs** preserved (`for`, `mut`, slice types).
* **Binding** and **types** may or may not be attached yet (depends on compiler stage).

Good for:

* macros that see `for`,
* refactorings that reason at loop level.

### 4.2 HIR – High-Level IR (Desugared Surface)

HIR is AST that has been:

* **desugared** into a smaller core language,
* annotated with **binding** and usually **types**.

For `sum`, a plausible HIR sketch:

```rust
fn sum(xs: &[i32]) -> i32 {
    let mut acc: i32 = 0;
    {
        let mut iter = IntoIterator::into_iter(xs);
        loop {
            match Iterator::next(&mut iter) {
                Some(x) => {
                    acc = acc + x;
                }
                None => break,
            }
        }
    }
    acc
}
```

Key changes vs AST:

* `for` loop → explicit `iter` + `loop` + `match`.
* pattern `for x in xs` → explicit `Some(x)` / `None` match.
* still recognisably high-level; still statements, blocks, variables.

HIR invariants:

* No “high sugar” constructs like `for`/`?`-operator in source form.
* All names resolved; all uses linked to bindings (M02C07’s R).
* Often typed.

### 4.3 MIR / CFG / SSA – Mid-Level IR

MIR breaks constructs into primitive operations and explicit control flow.

Sketch (highly simplified):

```text
bb0:
    acc0 = 0
    iter0 = IntoIterator::into_iter(xs)
    goto bb1

bb1:
    tmp0 = Iterator::next(&mut iter0)
    if is_some(tmp0) {
        goto bb2
    } else {
        goto bb3
    }

bb2:
    x0   = unwrap_some(tmp0)
    acc1 = acc0 + x0
    acc0 = acc1
    goto bb1

bb3:
    ret  = acc0
    return ret
```

Properties:

* **Basic blocks** (`bb0`, `bb1`, …).
* Simple instructions: assignments, calls, branches.
* Easy to convert into SSA form by versioning `acc0`, `acc1`, etc., and inserting φ-functions at joins.

MIR/SSA invariants:

* No complex expressions; everything is a sequence of simple ops.
* Control flow explicit as a graph.
* Ideal for **data-flow** and **control-flow** analyses and optimisations.

### 4.4 Low-Level IR

Finally, low-level IR (LLVM IR, JVM bytecode, etc.) for `sum` would:

* use explicit integer registers,
* pointer arithmetic for array/slice,
* explicit loads/stores.

You don’t need the exact code; important:

* types are often more hardware-oriented (e.g. pointers, `i32`),
* operations closer to instructions (e.g. `getelementptr`, `load`, `store`),
* still structured into blocks and SSA virtual registers (LLVM’s case).

As R, low-level IR is where **back-end metas** live (instrumentation, sanitizers, LTO passes).

## 5. Desugaring vs Lowering

The draft blurred these a bit; let’s pin them precisely.

### 5.1 Definitions

* **Desugaring**
  Semantics-preserving rewrite **within the same level** of representation, from richer surface syntax to a smaller core.

  * Example: surface AST → core AST / HIR.

* **Lowering**
  Semantics-preserving mapping **between distinct representation levels**, typically from a higher-level IR to a lower-level one.

  * Example: HIR → MIR, MIR → low-level IR.

You can think of desugaring as:

> “Simplify the language, keep the representation kind.”

and lowering as:

> “Change the representation kind, keep the behaviour.”

### 5.2 Examples

* `for` loop in `sum`:

  * Desugaring: `for x in xs` → iterator + `loop` + `match` in HIR.
  * Lowering: HIR `loop`+`match` → MIR basic blocks and branches.

* Pattern match:

  * Desugaring: high-level patterns → core pattern forms.
  * Lowering: core pattern forms → branch tree in MIR/CFG.

* Closures:

  * Desugaring: closure syntax → explicit closure objects in HIR.
  * Lowering: closure calls → indirect calls and environment struct accesses in MIR/low-level IR.

Being explicit about which you’re doing matters when you talk about what **R** your T operates on and which invariants your T must preserve.

## 6. CFGs and SSA as IR Forms

### 6.1 Control-Flow Graph (CFG)

A **Control-Flow Graph**:

* Nodes = **basic blocks** (straight-line sequences).
* Edges = possible jumps/branches.
* One entry, one or more exits.

Our `sum` MIR sketch already has a CFG:

* `bb0` → `bb1`.
* `bb1` → `bb2` or `bb3`.
* `bb2` → `bb1`.
* `bb3` exits.

CFG is the natural R for:

* reachability,
* dominance,
* loop detection,
* forward/backward data-flow analysis.

### 6.2 Static Single Assignment (SSA)

SSA enforces:

* each variable is assigned **exactly once**,
* joins use **φ-functions** to merge values from predecessors.

Mini example (not `sum`, to keep it compact):

Source:

```text
x = 0;
if (c) {
    x = 1;
}
y = x + 2;
```

SSA:

```text
x0 = 0;
if (c) {
    x1 = 1;
    goto bb_true;
} else {
    goto bb_false;
}

bb_true:
    goto bb_join;

bb_false:
    goto bb_join;

bb_join:
    x2 = φ(x0, x1);
    y0 = x2 + 2;
```

Benefits:

* each use has a single, well-defined defining assignment,
* data-flow (constant propagation, reaching definitions, etc.) becomes mechanically simple.

Many mid-level IRs are either in SSA or trivially SSA-convertible, precisely because **T as optimisations** is much easier to express on SSA R.

## 7. IR as R in R–T–S: Metaprograms as IR→IR

The key mental shift:

> After the front-end, most metaprograms are **IR→IR passes**.

Some examples:

* **Constant folding**

  * R: MIR/SSA.
  * T: replace `v = 2 + 3` with `v = 5`.
  * S: early middle-end.

* **Dead code elimination**

  * R: CFG-based MIR.
  * T: remove unreachable blocks and instructions whose results are unused.
  * S: middle-end, often iterated with other optimisations.

* **Loop-invariant code motion**

  * R: SSA + loop structure (CFG).
  * T: hoist computations whose operands are invariant across loop iterations.
  * S: mid-to-late middle-end.

Contrast with AST-level macro systems, where R is AST and T is AST→AST.

Design choice:

* If you expose **AST as R** to users, you get ergonomics and surface-level power.
* If you expose **IR as R** (e.g. LLVM passes), you get precise control over performance, but at a lower abstraction level.

Both are legitimate metaprogramming ecosystems; they simply choose different Rs and Ts.

## 8. Other Ecosystems (and a Non-Rust Lowering Example)

### 8.1 C++ / Clang Snapshot

Pipeline:

```text
C++ source
  → Tokens
  → AST (Clang AST, with templates, namespaces, overload resolution)
  → Semantic analysis
  → LLVM IR
  → Machine code
```

Typical choices of R:

* C++ tools and refactorings: **Clang AST (+binding, types)**.
* Optimisers and instrumentation: **LLVM IR**.

T:

* AST→AST (refactoring, clang-tidy),
* IR→IR (LLVM optimisation passes, sanitizers, coverage instrumentation).

S:

* AST-level Ts in front-end / tooling,
* IR-level Ts in middle-/back-end.

### 8.2 Python: AST → Bytecode Lowering

CPython pipeline:

```text
Source
  → Tokens
  → AST
  → Bytecode
  → VM execution
```

Take a Python-style loop:

```python
for x in xs:
    if x % 2 == 0:
        sum = sum + x
```

Very rough bytecode sketch (conceptual):

```text
SETUP_LOOP L_end
LOAD_NAME xs
GET_ITER
L_loop:
FOR_ITER L_end
STORE_NAME x
LOAD_NAME x
LOAD_CONST 2
BINARY_MODULO
LOAD_CONST 0
COMPARE_OP ==
POP_JUMP_IF_FALSE L_loop
LOAD_NAME sum
LOAD_NAME x
BINARY_ADD
STORE_NAME sum
JUMP_ABSOLUTE L_loop
L_end:
POP_BLOCK
```

Here:

* AST-level `for` and `if` lower to **stack-based bytecode**:

  * `GET_ITER`, `FOR_ITER`, `JUMP_ABSOLUTE`, etc.
* The bytecode is Python’s low-level IR:

  * simple opcodes,
  * implicit operand stack.

As R:

* AST is natural for tooling and dynamic AST transforms.
* Bytecode is natural for **runtime metas** (profilers, debuggers, coverage, tracing, JIT prototypes).

## 9. Passes, Pipelines, and Invariants

### 9.1 Passes

A **pass** is:

* a function over R:

  * `R_in → (R_out, diagnostics, metadata)`.

Types:

* **Analysis passes**: don’t change IR, just attach information.

  * e.g. liveness, alias analysis, borrow checking.

* **Transform passes**: IR→IR transformations.

  * e.g. constant folding, inlining, loop unrolling, pattern rewrites.

* **Lowering passes**: move between IR levels.

  * e.g. HIR→MIR, MIR→LLVM IR.

Each pass assumes certain **input invariants** and guarantees certain **output invariants**. Example:

* Input: MIR is well-typed, SSA, no critical edges.
* Output: MIR still well-typed and SSA, plus all constant expressions folded.

### 9.2 Pipelines

A **pipeline** is a composition of passes:

```text
AST
  → [desugaring] → HIR
  → [HIR→MIR lowering] → MIR
  → [optimisations: const fold, DCE, LICM, …] → MIR'
  → [MIR→Low-level IR lowering] → Low-level IR
  → [target-specific passes] → Machine code
```

In R–T–S terms:

* R changes over time (AST → HIR → MIR → low-level IR).
* T at each stage is a mix of desugaring, lowering, and optimisation.
* S is “where in the pipeline” a given T hooks.

M02C09 will reframe “pass = T” more formally as **term rewriting + strategy** with normal forms and convergence.

## 12. M02C08 Glossary (Compact Reference)

| Term                                 | Definition                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **Intermediate Representation (IR)** | Internal language used by a compiler/tool for representing programs between front-end and back-end.               |
| **AST (Abstract Syntax Tree)**       | Tree representation of source constructs, close to how code is written; good for macros and refactoring.          |
| **HIR (High-Level IR)**              | Desugared, binding- and often type-resolved form close to the source language; core surface language.             |
| **MIR (Mid-Level IR)**               | IR with primitive operations and explicit control flow, often organised as basic blocks and suitable for CFG/SSA. |
| **Low-level IR**                     | IR close to machine code (LLVM IR, JVM bytecode, Python bytecode), with explicit memory and primitive operations. |
| **Desugaring**                       | Semantics-preserving simplification within one representation level (e.g. surface AST → core AST/HIR).            |
| **Lowering**                         | Semantics-preserving transformation between representation levels (e.g. HIR → MIR → low-level IR).                |
| **Control-Flow Graph (CFG)**         | Graph of basic blocks with edges representing possible control transfers.                                         |
| **Basic block**                      | Straight-line sequence of operations with a single entry and a single exit.                                       |
| **SSA (Static Single Assignment)**   | IR discipline where each variable has exactly one defining assignment; joins use φ-functions.                     |
| **Pass**                             | Single analysis or transformation over a specific representation.                                                 |
| **Pipeline**                         | Ordered sequence of passes transforming source, via multiple IRs, into executable form.                           |
