## 1. From Syntax to Binding: Why “Just AST” Is Not Enough

M02C06 fixed the **syntax level**: CST vs AST as candidate **R** in the R–T–S triad.

AST alone tells you:

* which identifiers appear,
* where blocks, functions, and expressions are,
* how constructs are nested.

It does **not** tell you:

* *which declaration* a given identifier use refers to,
* whether two occurrences of `x` refer to the **same binding**,
* whether a variable use is **unbound** (undefined).

Example:

```rust
fn f(x: i32) -> i32 {
    let y = x + 1;
    y * 2
}
```

The AST knows there is:

* a parameter `x`,
* a local `y`,
* identifier occurrences at various positions.

But without binding information it does *not* know that:

* `x` in `x + 1` refers to the parameter,
* `y` in `y * 2` refers to the `let y = ...` above.

For serious metaprogramming—function inlining, macro expansion, refactoring—you must respect **binding invariants**. Treat identifiers as mere strings and you will:

* introduce **capture** (free variable accidentally bound by a new declaration),
* change **shadowing** relationships,
* create **dangling uses** (no visible binding).

Binding is where “code as data” stops being just trees and becomes a **semantically decorated** R.

## 2. R with Binding in the R–T–S Triad

So far:

* **R**: CST / AST / IR (M02C06, M02C08),
* **T**: transforms over R,
* **S**: where/when transforms run.

From this core onwards, for high-level languages, we will often assume:

```text
R = AST  +  binding information  +  (later) types
```

Concretely:

* AST nodes for declarations (functions, variables, parameters).
* For each **use** occurrence of an identifier, a link to:

  * its **binding** node, or
  * a special “unbound” marker if resolution fails.

This enriched R lets your T:

* perform **capture-avoiding substitution**,
* safely do **α-conversion** (renaming bound variables),
* reason about **shadowing** and **free variables** structurally.

The rest of this core defines the binding vocabulary you need to work with such Rs.

## 3. Identifiers, Bindings, and Uses

### 3.1 Occurrences

For a given name string `"x"`, a program contains many **occurrences**:

* some **introduce** a binding,
* others **use** an existing binding.

Rust-like example:

```rust
fn f(x: i32) -> i32 {
    let y = x + 1;
    y * x
}
```

Occurrences:

* `x` in `fn f(x: i32)` – **binding** (parameter).
* `y` in `let y = ...` – **binding** (local variable).
* `x` in `x + 1` – **use** of parameter `x`.
* `y` in `y * x` – **use** of local `y`.
* `x` in `y * x` – **use** of parameter `x`.

AST-only R sees a bag of identifier nodes; binding-aware R distinguishes which occurrence is which.

### 3.2 Scope

**Scope** determines, for each use occurrence:

* which binding it refers to, if any,
* or whether it is **unbound**.

Informally:

> Scope is the region of code where a binding is visible by name.

Most modern languages (Rust, C++, Python) are **lexically scoped**:

* scope is determined by **static source structure** (blocks, functions, modules),
* not by runtime call stacks.

## 4. Lexical Scope, Environments, and Symbol Tables

### 4.1 Lexical Scope

Example:

```rust
fn main() {
    let x = 1;
    {
        let y = x + 1;
        println!("{x}, {y}");
    }
    println!("{x}");
    // println!("{y}");  // error: y not in scope
}
```

* `x` is bound at function scope (`main`), visible in both prints.
* `y` is bound in the inner block; only visible inside that block.

This is purely lexical:

* No function calls are required to decide which binding each use refers to.
* You can decide using AST structure alone plus a scope model.

### 4.2 Environment Chains and Symbol Tables

Compilers implement lexical scope with:

* a stack of **environment frames** (or symbol tables),
* each frame maps names → bindings defined at that lexical level.

Conceptually:

```text
Frame 0 (global / module):
  - fn main

Frame 1 (inside main):
  - x

Frame 2 (inner block inside main):
  - y
```

When analysing:

* Enter a new block / function → **push** a frame.
* Exit block / function → **pop** a frame.
* On `let y = ...` → insert `y` into current frame.
* On use of `y` → search from top frame downwards.

ASCII picture for the inner `println!`:

```text
Use: y   → search Frame 2 → found (inner y binding)
Use: x   → search Frame 2 → not found
        → search Frame 1 → found (outer x binding)
```

A **symbol table** is simply the data structure implementing these frames and mappings.

In a binding-aware R, each identifier use node carries:

* a direct link (pointer/index) to its binding node,
* computed by walking environment chains once during name resolution.

## 5. Free vs Bound Variables

### 5.1 Informal Definitions

Given some fragment of code:

* A variable is **bound** in that fragment if a binding for it appears inside the fragment and covers that occurrence.
* A variable is **free** in that fragment if its binding lies **outside** the fragment (or is missing entirely).

Lambda-calculus notation makes the distinction sharp:

```text
λx. x + y
```

* `x` is bound (by `λx`).
* `y` is free in this term (binding must come from an outer environment or be unbound).

Rust analogue:

```rust
static GLOBAL: i32 = 10;

fn f(x: i32) -> i32 {
    x + GLOBAL
}
```

Relative to the **body of `f`**:

* `x` – bound (parameter).
* `GLOBAL` – free (binding comes from module scope).

### 5.2 Quick λ ↔ Rust Mapping

To avoid notation confusion:

* `λx. body` ↔ `fn f(x: T) -> ... { body }` (ignoring type annotations, names of functions).
* Free vs bound is always defined **with respect to a chosen fragment** (expression, function body, module, …).

For the function body:

```rust
fn f(x: i32) -> i32 {
    x + y
}
```

* `x` is bound (parameter).
* `y` is free in this body (must be defined outside or is an error).

You will use “free variables of a fragment” constantly when reasoning about inlining and macro expansion.

## 6. α-Conversion (Alpha-Renaming)

### 6.1 Definition

**α-conversion** is:

> Semantics-preserving renaming of a **bound variable** and all its **bound uses**, avoiding capture.

Lambda form:

```text
λx. x + 1    ≡α    λz. z + 1
```

if there is no free `z` in the body.

Rust form:

```rust
fn f(x: i32) -> i32 { x + 1 }
fn f(z: i32) -> i32 { z + 1 }
```

are α-equivalent, assuming nothing outside relies on the parameter name specifically.

### 6.2 Capture-Avoiding Condition

α-conversion must **not** change which binding any use refers to.

Bad λ example:

```text
λx. (λy. x + y)
```

If the surrounding context has a free `x`, then renaming inner `y` to `x` gives:

```text
λx. (λx. x + x)
```

Now:

* the occurrences inside the inner λ both refer to the **inner** x,
* the connection to outer x is lost,
* semantics changed.

Correct α-renaming:

* always picks a **fresh** name (one that is not free in the body),
* updates all bound uses of that variable consistently.

In an AST+binding R, α-conversion is mechanically:

1. Pick a fresh name `x'`.
2. Update the binding node’s name field from `x` to `x'`.
3. Update all uses whose binding link points to that node.

## 7. Shadowing and Variable Capture

### 7.1 Shadowing

**Shadowing** occurs when an inner binding uses the same name as an outer binding:

```rust
fn main() {
    let x = 1;
    {
        let x = x + 1;  // new binding shadows outer x
        println!("{x}"); // inner x
    }
    println!("{x}"); // outer x
}
```

Inside the block:

* The **binding occurrence** is `let x = ...`.
* The `x` on the right-hand side (RHS) still refers to the **outer** `x` (depending on language rules).
* Later uses of `x` in that block refer to the **inner** `x`.

Shadowing is usually legal but can be a source of confusion and subtle bugs.

### 7.2 Variable Capture

**Capture** is what happens when a transform changes which binding an existing use refers to, **unintentionally**.

Classic (Rust-like) macro example:

```rust
macro_rules! with_temp {
    ($body:block) => {{
        let tmp = 42;
        $body
    }};
}
```

User code:

```rust
fn main() {
    let tmp = 0;
    with_temp!({
        println!("{tmp}");
    });
}
```

Conceptual expansion:

```rust
fn main() {
    let tmp = 0;
    {
        let tmp = 42;
        {
            println!("{tmp}"); // now refers to inner tmp (42)
        }
    }
}
```

The user likely expected `0`; the macro **captured** the user’s `tmp`.

Capture is a violation of binding invariants:

* the R before transform and R after transform differ in the binding map for some use occurrences.

### 7.3 Binding-Invariant Transforms

A transformation is **binding-invariant** if:

* for every identifier use, the resolved binding (as seen via environments) is unchanged.

Binding-aware transforms must:

* avoid introducing new bindings that capture existing uses,
* avoid moving fragments into scopes where their free variables bind differently,
* perform α-conversion on newly introduced or moved bindings to avoid collisions.

Hygienic macro systems (Module 3) are exactly about **enforcing binding invariance** automatically.

## 8. Environments as Part of R

Pulling this together, we refine R further:

```text
R = AST
  + scope structure (nested blocks / frames)
  + environment mapping uses → bindings
```

Implementation strategies:

* Each identifier use node has a field `binding_id` pointing to a declaration node.
* Or symbol table keyed by (scope, name) with entries for declarations and a mapping index for uses.

Once R carries this, T can:

* check whether a proposed transform preserves binding for all uses,
* reject transforms that would capture free variables unless they are explicitly allowed (e.g., deliberate shadowing),
* implement α-conversion as a safe primitive operation.

For the running example from M02C06:

```rust
fn sum(xs: &[i32]) -> i32 {
    let mut acc = 0;
    for x in xs {
        acc += x;
    }
    acc
}
```

A binding-aware R would annotate:

* parameter binding: `xs`,
* local bindings: `acc`, `x`,
* uses of `xs`, `acc`, `x` inside the loop and in the final `acc`.

Any optimisation or macro that rewrites this function must preserve those bindings or make intentional, well-specified changes.

## 10. Binding in Rust, Python, and C++ (Snapshots)

### 10.1 Rust

Key features:

* Lexical scope with blocks (`{ ... }`), functions, modules.
* Closures capture outer variables.

Example:

```rust
fn main() {
    let x = 1;
    let f = |y: i32| x + y;
    println!("{}", f(2));
}
```

* `x` bound in `main`, captured by closure.
* `y` bound by closure parameter.
* Binding-aware R must record that `x` in `x + y` refers to outer `x`.

Transformations that:

* inline `f` into `main`,
* pull the closure out as a top-level function,

must adjust free-variable bindings correctly.

### 10.2 Python

Lexical scope with:

* module scope,
* function scope,
* class scope,
* `nonlocal` and `global` modifiers.

Example:

```python
x = 1  # module-level

def outer():
    x = 2  # outer-local

    def inner():
        print(x)  # refers to outer's x

    inner()
```

* `x` in `inner` is bound to the `x` in `outer`.
* If `inner` declared `global x`, `x` would refer to module-level `x`.

Binding-aware Python tools must model:

* nested scopes,
* `nonlocal` / `global` changing which environment frame a name points into.

### 10.3 C++

C++ adds:

* namespaces,
* class scopes,
* overloading and ADL (argument-dependent lookup).

Still, at core, binding is:

* map name occurrences to unique declarations,
* according to lexical rules + namespace rules.

Clang’s AST plus its symbol tables provide a binding-aware R that refactoring tools rely on for rename, move, and extraction operations.

## 11. Binding-Aware Transforms: Substitution and Inlining

### 11.1 Capture-Avoiding Substitution

Notation from λ-calculus:

* `[x := e] t` – substitute free occurrences of `x` in `t` with expression `e`.

Correct substitution is **capture-avoiding**:

* before substituting, α-rename bound variables in `t` that clash with free variables in `e`.

Example:

```text
λy. x + y
```

Substituting `x := y` naively:

```text
λy. y + y   (WRONG, captures y)
```

Correct approach:

1. α-rename inner `y` to a fresh `y1`:

   ```text
   λy1. x + y1
   ```

2. Substitute `x := y`:

   ```text
   λy1. y + y1
   ```

R with binding lets you implement this by structural inspection rather than string juggling.

### 11.2 Function Inlining (Conceptual)

Rust-like example:

```rust
fn inc(x: i32) -> i32 {
    let y = x + 1;
    y
}

fn main() {
    let y = 10;
    let z = inc(y);
    println!("{z}");
}
```

Inlining `inc` at the call site:

1. Take the body of `inc`:

   ```rust
   let y = x + 1;
   y
   ```

2. Note that `y` is bound locally inside `inc`, but we already have a `y` at the call site.

3. α-rename local `y` inside `inc` to `y_inc` (fresh):

   ```rust
   let y_inc = x + 1;
   y_inc
   ```

4. Substitute parameter `x` with argument `y` (call-site `y`):

   ```rust
   let y_inc = y + 1;
   y_inc
   ```

5. Replace `inc(y)` with this block:

   ```rust
   fn main() {
       let y = 10;
       let z = {
           let y_inc = y + 1;
           y_inc
       };
       println!("{z}");
   }
   ```

A binding-aware inliner performs exactly this α-renaming and substitution guided by the environment mapping.

## 14. M02C07 Glossary (Compact Reference)

| Term                 | Definition                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| **Identifier**       | Syntactic token representing a name (`x`, `value`, `foo_bar`), independent of what it denotes.       |
| **Binding**          | Declaration that introduces a name and associates it with an entity (variable, function, etc.).      |
| **Use / Occurrence** | A reference to a name; resolved via scope to a binding or reported as unbound.                       |
| **Scope**            | Region of the program where a binding is visible and its name can be used.                           |
| **Lexical scope**    | Scope determined purely by program text structure (blocks, functions, modules).                      |
| **Environment**      | Mapping from names to bindings (or values) used during analysis or evaluation.                       |
| **Symbol table**     | Compiler data structure implementing environments and scope nesting.                                 |
| **Free variable**    | Variable whose binding lies outside the considered fragment.                                         |
| **Bound variable**   | Variable whose binding is introduced within the considered fragment.                                 |
| **α-conversion**     | Semantics-preserving renaming of a bound variable and all its bound uses, avoiding capture.          |
| **Shadowing**        | Introduction of a new binding with the same name as an existing binding, hiding the outer one.       |
| **Variable capture** | Unintended change in which binding a use refers to, caused by a transformation that ignores binding. |
