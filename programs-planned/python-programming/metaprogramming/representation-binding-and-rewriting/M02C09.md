## 1. Why Term Rewriting?

Up to now:

* M02C06 gave you **syntax trees** (CST/AST).
* M02C07 added **binding**.
* M02C08 added **IRs and lowering**.

All the “passes” you’ve seen can be described uniformly as:

> **Rewriting terms** according to rules, under a strategy, until some notion of “done” (normal form).

This gives you:

* A language-agnostic view: same formalism for AST, HIR, MIR, SSA.
* A way to reason about:

  * **Does the pass terminate?**
  * **Does rule order matter?**
  * **Has the pass fully done its job?**

### 1.1 R–T–S for Passes

In this core we make R–T–S precise for compiler passes:

* **R** – a **term language**: AST, HIR, MIR, SSA, or a fragment thereof.
* **T** – a **rewrite system**: a set of rewrite rules **plus a strategy**.
* **S** – the **stage** in the pipeline where T runs (macro expansion, desugaring, mid-end optimisation, etc.).

Think:

```text
R: MIR  (from M02C08)
T: “constant folding + DCE” rewrite system
S: middle-end optimisation phase
```

M02C10 will then ask: when does such a T preserve semantics?

## 2. Terms, Patterns, Contexts

We start abstract, then connect to code.

### 2.1 Terms

A **term** in rewriting theory:

* is either a **variable**, or
* a **function symbol** applied to a list of terms.

Toy arithmetic signature:

* Constants: `0`, `1`, `2`, …
* Variables: `x`, `y`, …
* Constructors: `add(·,·)`, `mul(·,·)`.

Examples:

* `add(1, 2)`
* `mul(add(1, 2), x)`

For programs, you can treat AST/IR nodes as function symbols:

* `if(cond, then_branch, else_branch)`
* `assign(var("x"), add(var("x"), const(1)))`
* `call(name("f"), [arg1, arg2])`

So: **“term” = tree-shaped program fragment in your chosen R.**

### 2.2 Patterns and Substitutions

A **pattern** is a term containing **pattern variables** that stand for arbitrary subterms.

Examples:

* `add(x, 0)`
* `mul(x, 1)`
* `add(const(a), const(b))`

A **substitution** σ maps pattern variables to concrete terms:

* pattern: `add(x, 0)`
* term: `add(mul(2, 3), 0)`
* match: `x ↦ mul(2, 3)`

In AST-land:

* pattern: `assign(v, add(const(a), const(b)))`
* term: `assign(x, add(2, 3))`
* match: `v ↦ x`, `a ↦ 2`, `b ↦ 3`

### 2.3 Contexts

A **context** is a term with a single “hole” `□`:

* example: `mul(□, 3)` is a context
* plugging `add(1, 2)` yields `mul(add(1, 2), 3)`

Rewriting always happens **in context**:

> If `l → r` is a rule and `lσ` matches a subterm of `C[lσ]`, you may replace it with `C[rσ]`.

This is exactly “rewrite a subtree inside a larger AST/IR”.

## 3. Rewrite Rules: Syntax and Examples

### 3.1 Rules

A **rewrite rule** has the shape:

```text
l → r
```

with:

* `l` (LHS) a **pattern**,
* `r` (RHS) a **term** built from the same pattern variables,
* and optionally **side conditions** (e.g. `a + b` fits in 32-bit int).

Semantics:

> Any subterm matching `l` under some substitution σ may be replaced with `rσ`.

### 3.2 Arithmetic Simplification Rules

Classic algebraic simplifications:

1. Identity:

   ```text
   add(x, 0) → x
   add(0, x) → x
   mul(x, 1) → x
   mul(1, x) → x
   ```

2. Constant folding:

   ```text
   add(const(a), const(b)) → const(a + b)
   mul(const(a), const(b)) → const(a * b)
   ```

These rules:

* operate locally,
* respect **tree structure**,
* reduce complexity (fewer operations or smaller constants).

### 3.3 Program-Level Examples

1. **Constant folding on MIR**

   Instruction form:

   ```text
   assign(v, add(e1, e2))
   ```

   Rule:

   ```text
   assign(v, add(const(a), const(b)))
     → assign(v, const(a + b))
   ```

2. **Trivial if elimination**

   On a HIR/AST:

   ```text
   if (true)  { t } else { e }  →  t
   if (false) { t } else { e }  →  e
   ```

3. **Macro pattern**

   Pseudo-AST for a logging macro:

   ```text
   log_and_return(e) → { tmp = e; log(tmp); tmp }
   ```

In all cases, it’s the same formal shape: pattern `l`, result `r`, side conditions on when we’re allowed to apply.

## 4. Strategies: How the Rules Fire

A rule set does **not** say:

* which subterm to rewrite first,
* whether to keep rewriting,
* how to break ties between overlapping rules.

That’s the job of a **strategy**.

### 4.1 Innermost vs Outermost

Given `add(add(1, 2), 3)` and the rule:

```text
add(const(a), const(b)) → const(a + b)
```

* **Innermost** (evaluate children first):

  1. Rewrite inner `add(1, 2)` → `3`
  2. Now term is `add(3, 3)` → `6`

* **Outermost** (try outer redex first):

  1. Outer `add(add(1, 2), 3)` is not `add(const, const)` → no rewrite
  2. Descend to children; eventually the same normal form, but the path differs

Compilers often:

* traverse IR in a fixed order (pre-/post-order),
* apply rules either **innermost** (good for evaluation-like passes) or **top-down** (good for desugaring).

### 4.2 Fixed-Point Strategies

Most real passes are “run until stable”:

1. Walk IR, apply rules where they match.
2. If anything changed, repeat.
3. Stop when no rule applies: **fixed point**.

Formally: iterate rewriting until a **normal form** is reached.

Implementation tricks:

* worklists for efficiency,
* per-instruction “dirty” flags,
* explicit iteration limits when rules are not obviously decreasing.

### 4.3 Strategy as Part of T

Within R–T–S:

* **T is not just the rules**; it is **rules + strategy**.
* Two different strategies on the same rules can give different performance and, in pathological cases, **different results** if rules are not designed carefully.

You want:

* strategies that are simple and deterministic,
* rules that are robust enough that strategy choice doesn’t change semantics.

## 5. Termination, Confluence, Normal Forms (Compiler-Oriented)

### 5.1 Termination

A rewrite system **terminates** if no infinite rewrite sequence exists.

In a compiler:

* non-termination = hung pass = unusable toolchain.
* design rule: each rule should reduce a well-founded measure:

  * number of syntactic sugars,
  * size of expressions,
  * number of unoptimised patterns.

Examples:

* Desugaring `for` → `loop`+`match` decreases the count of `for`.
* Constant folding never introduces more operators than it removes.

Where you can’t easily prove termination, you still enforce it by:

* capping iterations,
* forbidding “backwards” rules that reintroduce complexity.

### 5.2 Normal Forms

A **normal form** (w.r.t. a rule set) is a term where *no* rule applies.

For a pass:

* normal form = “pass has nothing left to do”.

Examples:

* Constant folding:

  * normal form: no arithmetic operation has **two constant operands**.

* Desugaring:

  * normal form: zero `for`, `match?`, or other “high sugar” constructs remain.

In pipeline terms:

* each pass should aim at a clearly described normal form on its R.
* M01C04–C05’s “narrow responsibilities per tier” maps directly to this: each pass drives R to a tight normal form, then hands off.

### 5.3 Confluence and Why You Care

A rewrite system is **confluent** if:

* from any term `t`, if two different rewrite sequences produce `u` and `v`,
* there is a `w` that both `u` and `v` can still rewrite to.

Intuition:

> Even if you apply rules in different orders, you end up in the “same” place (up to normalisation).

In compilers you rarely prove full confluence, but you want:

* *semantics-level confluence*: any admissible ordering of passes yields a **semantically equivalent** program (M02C10).
* *shape-level robustness*: small changes in traversal order don’t wildly change IR shape.

Non-confluence in practice:

* two conflicting strength-reduction rules might yield different **performance** characteristics depending on order,
* overly aggressive, order-sensitive inlining decisions can change code size drastically.

So: confluence is the formal ideal behind “passes should not be order-fragile”.

## 6. Program Transformations as Rewriting over AST/IR

Now connect to the running example from M02C08:

```rust
fn sum(xs: &[i32]) -> i32 {
    let mut acc = 0;
    for x in xs {
        acc += x;
    }
    acc
}
```

Think about its **MIR/SSA** form and standard optimisation passes.

### 6.1 Constant Folding Walk-Through

Suppose MIR contains:

```text
bb0:
    _1 = 0 + 0
    acc0 = _1
    goto bb1
```

Rule:

```text
assign(v, add(const(a), const(b)))
  → assign(v, const(a + b))
```

Step under an **innermost** strategy:

1. Match `assign(_1, add(const(0), const(0)))`.
2. Apply rule: `_1 = 0 + 0` → `_1 = 0`.
3. Re-run pass; nothing else matches → normal form.

This is a self-contained rewrite system on:

* **R**: local MIR instruction terms,
* **T**: constant-folding rules + innermost strategy,
* **S**: early middle-end.

### 6.2 Dead Code Elimination (DCE)

On MIR for `sum`, after some optimisations you might have:

```text
bb0:
    tmp0 = acc0 + 0
    acc0 = tmp0
    ...
```

If an analysis marks `tmp0` as never used except for immediately assigning to `acc0`, you can have a rewrite:

```text
[dead(assign(v, e))] → (remove instruction)
```

where `dead` is a side condition.

Again:

* R: MIR instructions,
* T: DCE rule + worklist strategy,
* S: mid-end.

DCE is easier over MIR/CFG than AST because:

* control-flow and liveness are explicit,
* side conditions are local to blocks and use-def chains.

## 7. Pass Interaction, Non-Confluence, and Pipelines

### 7.1 Multiple Passes as Multiple Rewrite Systems

A pipeline:

```text
AST
  --[desugaring rules]--> HIR
  --[lowering rules]--> MIR
  --[opt rules A: const fold]--> MIR_A
  --[opt rules B: DCE]--> MIR_B
  --[opt rules C: loop opts]--> MIR_C
  --[lowering rules]--> low-level IR
```

Each opt pass is its own rewrite system:

* different R (HIR vs MIR vs low-level IR),
* different normal forms,
* different strategies.

They interact:

* const folding (A) may expose more dead code for B,
* DCE (B) may remove useless computations, shrinking opportunities for C.

### 7.2 A Non-Confluent Toy Example

Consider IR rules for strength reduction:

1. `mul(x, 2) → add(x, x)`  (replace multiply with add)
2. `add(x, x) → shl(x, 1)`   (replace add with shift)

If your system also has:

3. `shl(x, 1) → mul(x, 2)`   (for some target-specific canonicalisation)

Then:

* Starting from `mul(x, 2)`:

  * Path 1: rule 1 then 2:

    ```text
    mul(x, 2) → add(x, x) → shl(x, 1)
    ```

  * Path 2: rule 3 first (if someone wrote `shl(x,1)` elsewhere and you normalise to `mul(x,2)` then rule 1 again) can create loops:

    ```text
    shl(x, 1) → mul(x, 2) → add(x, x) → shl(x, 1) → ...
    ```

And depending on whether you normalise to `mul` or `shl`, you may get:

* different code shapes,
* different use of specialised instructions,
* even non-termination if you aren’t careful with strategy.

Lesson:

* avoid cycles,
* pick a **one-way canonical direction** (e.g. always end in `shl`),
* treat rule sets as defining **canonical forms**, not arbitrary equivalences.

This is the concrete reason you care about confluence/termination properties in compiler design, not just as theory.

## 8. Design Rules: Narrow, Normalised, and RTS-Aligned

This is where we tie back to M01C04–C05’s “tier discipline”.

For each pass:

1. **Choose R tightly**

   * HIR for desugaring and high-level refactors,
   * MIR/SSA for data-flow-heavy optimisations,
   * low-level IR only when you truly need machine details.

2. **Define a clear normal form**

   * “No high-level sugars,”
   * “No un-folded constant binary ops,”
   * “No dead basic blocks.”

3. **Keep T’s responsibilities narrow**

   * One kind of simplification per pass.
   * This matches “narrow, well-bounded tiers” from Module 1:

     * easier reasoning,
     * fewer cross-pass surprises.

4. **Engineer strategy for predictability**

   * Deterministic traversal order,
   * fixed-point iteration with a well-founded measure,
   * no rule cycles.

5. **Align S with pipeline structure**

   * Don’t mix high-level desugaring with low-level peephole in the same pass.
   * Insert passes where their invariants are stable and where their R is most informative.

Everything you liked from Module 1 about tiering and cost models reappears here as constraints on **rewrite systems per stage S**.

## 11. M02C09 Glossary (Compact Reference)

| Term                       | Definition                                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Term**                   | Tree-structured expression built from variables and function symbols (or AST/IR nodes); the basic object of rewriting.    |
| **Pattern**                | Term with variables representing subterms; used as the left-hand side of rewrite rules.                                   |
| **Substitution**           | Mapping from pattern variables to concrete terms, obtained when a pattern matches a term.                                 |
| **Context**                | Term with a distinguished hole `□` where a subterm can be plugged; models rewriting inside larger structures.             |
| **Rewrite rule**           | Directed equation `l → r` saying that any instance of `l` may be replaced by the corresponding instance of `r`.           |
| **Redex**                  | A subterm that matches the left-hand side of some rewrite rule; a candidate for rewriting.                                |
| **Strategy**               | Policy for choosing which redex to rewrite, in what order, and how often (innermost, outermost, fixed-point, etc.).       |
| **Termination**            | Property that no infinite rewrite sequence exists for the system.                                                         |
| **Normal form**            | Term to which no rewrite rule applies under a given system.                                                               |
| **Confluence**             | Property that different rewrite sequences from the same term can be joined to a common successor (unique outcome modulo). |
| **Program transformation** | System of rewrite rules (plus strategy) over AST/IR used to optimise, refactor, or otherwise transform programs.          |
