# Module 21 Investigations — Traits as Behavioral Contracts

[Chapter](../../course-book/module-21-traits-as-behavioral-contracts/index.md) · [Workbook](../../course-book/module-21-traits-as-behavioral-contracts/workbook.md) · [Course investigation method](../README.md)

> **Prediction question:** What behavior truly belongs in a shared contract, and which laws must every implementation preserve?

Before invoking a compiler or runner, draw a **trait-law table** and classify the expected result. The prediction must identify the earliest decisive phase or event and show why the result follows from **Define a trait whose methods express a coherent behavioral contract**. Diagnostic wording may vary; the causal relationship may not.

After observing Module 21 — Traits as Behavioral Contracts, preserve two repairs. The first is the smallest change that keeps the product requirement. The second is a tempting change that compiles, runs, or quiets the tool by erasing information, weakening a bound, changing ownership, hiding a failure, or narrowing the public contract. Explain precisely why the second repair is unacceptable here.

Finish by creating a new specimen that changes one relationship while keeping every incidental detail stable. Predict whether that variation changes parsing, name resolution, type checking, trait solving, borrow checking, build execution, runtime behavior, schedule behavior, or only architectural quality.
