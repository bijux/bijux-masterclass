# CommandForge — A Compile-Time Validated Command System

[Course 5 index](index.md) · [Executable capstone](../capstone/README.md)

CommandForge is the cumulative product for Modules 41–50. It is not a general-purpose command-line framework and it is not an excuse to place ordinary control flow inside macros. Its purpose is narrower and more educational: one small program uses every metaprogramming mechanism in the course, while each mechanism owns exactly one relationship.

The result must still be understandable as Rust. After expansion, the runtime crate contains ordinary structs, functions, constants, slices, error types, and command behavior. You should be able to reason about `add`, `slug`, `repeat`, and `contains` without reading the procedural-macro implementation. Conversely, you should be able to change argument-generation rules without touching the arithmetic or text behavior of the commands.

## Product behavior

CommandForge exposes these commands:

```text
commandforge list
commandforge explain <command>
commandforge run add --left <i64> --right <i64>
commandforge run slug --text <text>
commandforge run repeat --text <text> [--times <u32>]
commandforge run contains --text <text> --needle <text>
commandforge demo
commandforge help
commandforge version
```

The four runtime commands are deliberately small. Their job is to prove that generated argument decoding, generated descriptors, a generated catalog, and generated exit-code data connect to ordinary domain functions without taking those functions over.

- `add` performs checked signed addition and returns a domain error on overflow.
- `slug` converts ASCII letters and digits to lowercase, turns intervening non-alphanumeric runs into one hyphen, and rejects input containing no ASCII letters or digits.
- `repeat` repeats text between one and twenty times. Its `--times` argument is generated from a default-bearing field declaration.
- `contains` preserves the relationship and order between two text arguments.

Top-level usage failures and unknown command names use exit code `2`. Argument and domain failures use exit code `1`. Successful execution uses `0`. Those numbers do not appear independently in runtime source; the build script generates them from a checked table.

## The authority map

Before looking at implementation details, study the source-of-truth map.

| Fact | One authoritative declaration | Generated or consumed surfaces |
|---|---|---|
| argument field name and Rust type | ordinary argument struct field | decoder storage, parsing, construction |
| long option, help, default | `#[arg(...)]` on that field | usage text, metadata, required/optional behavior |
| handler behavior | ordinary Rust function body | called by generated wrapper |
| handler description | `#[command_handler(about = "...")]` | `HandlerDescriptor` |
| command name and order | `command_catalog!` entry | `CommandSpec` slice and lookup |
| diagnostic variant/code/message | `diagnostic_catalog!` declaration | enum, accessors, reverse lookup, `Display`, ordered table |
| process exit code/name/description | `config/exit_codes.tsv` | constants and lookup table generated by `build.rs` |
| top-level application behavior | ordinary `execute` function | CLI output and exit mapping |

This table is the capstone’s central invariant. A compile-time mechanism may reference a fact owned elsewhere, but it may not redeclare it independently.

The attribute macro therefore does **not** declare the command name. It declares only the description and generates a handler descriptor. The catalog DSL owns names and pairs them with descriptors. This avoids the common but defective design in which `#[command_handler(name = "add")]` and `command_catalog! { "add" => ... }` can drift.

The derive macro does not own domain validation. It can decode `u32` and provide a default of `1`, but the ordinary `repeat` function owns the permitted range `1..=20`. That range is product policy over a valid `u32`, not syntax-to-type conversion.

## Runtime architecture after expansion

The important runtime types are compact.

```rust
pub trait CommandArgs: Sized {
    const USAGE: &'static str;
    const ARGUMENTS: &'static [ArgumentSpec];

    fn decode(raw: &[String]) -> Result<Self, ArgError>;
}
```

A derived argument struct implements this trait. The generated decoder:

1. creates one `Option<ParsedType>` slot per field;
2. walks the raw flag/value sequence once;
3. rejects unknown flags;
4. rejects duplicate flags;
5. rejects a missing value immediately;
6. uses `FromStr` to parse each supplied value;
7. applies a declared default only when the option was absent;
8. rejects missing required arguments;
9. constructs the ordinary struct.

The derive adds only the trait bounds required for parsing. A `String` field needs no custom parser. A generic field causes generated `FromStr` and error-`Display` predicates to appear in the implementation’s where clause. A field that the generated code never formats does not receive a formatting bound merely because that is convenient for macro code.

A handler descriptor is a value:

```rust
pub struct HandlerDescriptor {
    pub about: &'static str,
    pub usage: &'static str,
    pub arguments: &'static [ArgumentSpec],
    pub invoke: fn(&[String]) -> Result<String, CommandError>,
}
```

The attribute macro preserves the original typed function and generates a private adapter from raw strings to the function’s argument type. The adapter calls the derived decoder, then invokes the function exactly once. The generated descriptor points to that adapter.

The catalog creates a separate name-bearing value:

```rust
pub struct CommandSpec {
    pub name: &'static str,
    pub handler: HandlerDescriptor,
}
```

`COMMANDS` is an ordered static slice of `CommandSpec`. `find_command` is ordinary linear lookup over a four-entry catalog. A hash map would introduce initialization machinery and nondeterministic iteration without solving a real product problem.

## Failure phases

CommandForge is designed so failures occur at the earliest phase that can know them.

| Failure | Phase |
|---|---|
| malformed `#[arg(...)]` syntax | derive helper-attribute parsing |
| duplicate `long` or `default` metadata | derive semantic validation |
| derive attached to an enum | derive input-shape validation |
| argument field type lacks `FromStr` | generated ordinary Rust trait checking |
| malformed handler attribute | attribute parsing |
| private, async, generic, or borrowed-argument handler | attribute item validation |
| handler result incompatible with generated adapter | generated ordinary Rust type checking |
| duplicate command name | catalog semantic validation |
| unresolved descriptor path | generated ordinary Rust name resolution |
| malformed exit-code row | build-script validation |
| duplicate process exit code | build-script semantic validation |
| unknown CLI command | runtime application logic |
| invalid integer text | generated runtime argument decoding |
| addition overflow | ordinary command-domain logic |

This table prevents two opposite mistakes. First, do not postpone a compile-time-known duplicate until runtime. Second, do not inspect token spelling and pretend to prove a trait relationship that only Rust type checking can establish.

## Module 41 increment — draw the boundary before writing code

Create an authority ledger with one row for every fact listed above. For each row, answer:

- Where is the fact written once?
- At what phase is it validated?
- Which generated surfaces repeat it mechanically?
- Which runtime code consumes it?
- What would drift if the generator were deleted?

Then apply the deletion test.

The diagnostic catalog passes: deleting its macro would require maintaining enum variants, two match functions, reverse lookup, `Display`, and ordered metadata separately. The command functions fail the test: turning `add` or `slug` into macros would not remove a cross-syntactic source-of-truth problem. Keep them ordinary.

Do not proceed until no fact has two owners. This catches architectural defects more cheaply than any compiler test.

## Module 42 increment — declarative diagnostic catalog

Implement `diagnostic_catalog!` with a compact grammar:

```rust
diagnostic_catalog! {
    pub enum Diagnostic {
        UnknownCommand = 1001 => "unknown command";
        ArgumentFailure = 1002 => "argument decoding failed";
    }
}
```

The macro generates:

- the enum;
- an ordered `ALL` slice;
- `code`;
- `message`;
- `from_code`;
- `Display`.

The input accepts identifiers, numeric literals, string literals, and explicit semicolon terminators. There are no caller runtime expressions, so evaluation-order questions do not arise. Repetition depth does: each captured variant, code, and message must remain aligned inside every generated surface.

Add positive round-trip tests. Add negative compiler cases for a missing code and malformed declaration. Do not claim that this declarative macro robustly validates duplicate numeric codes. For a larger public catalog where duplicate detection is essential, either add a targeted generated lint strategy with clear limitations or move the declaration to a procedural macro. The current small product keeps that boundary explicit.

## Module 43 increment — write the catalog grammar and normalized model

Before implementing the function-like procedural catalog, write its grammar:

```text
catalog      = visibility "static" identifier "{" entry* "}"
entry        = string-literal "=>" path ";"
```

The parser should create an AST that preserves each name literal and descriptor path with spans. A separate validator checks:

- names are nonempty;
- names contain no whitespace;
- names do not begin with `-`;
- names are unique.

The normalized model preserves source order. The generator later emits `CommandSpec` values.

This module’s practical work is intentionally design-first. The rich parser is implemented in Module 49, but its grammar and semantic rules are fixed now. This prevents parser implementation details from becoming the language specification accidentally.

## Module 44 increment — make generated paths deliberate

Procedural macros do not have declarative `$crate`. CommandForge chooses one stable runtime path in generated code:

```rust
::commandforge::CommandArgs
::commandforge::HandlerDescriptor
::commandforge::CommandError
```

Inside the runtime package, this is supported by:

```rust
extern crate self as commandforge;
```

That lets generated code use the same absolute path while expanding inside the crate that defines the runtime API.

This is a bounded capstone choice, not a universal public-crate solution. A reusable macro package should decide how dependency renaming is supported—often through an explicit crate-path helper attribute or a carefully justified helper dependency. The course deliberately makes the path visible rather than hiding the problem.

Audit every generated name. The handler attribute generates a private wrapper named from the function and a public descriptor constant. The catalog generates `COMMANDS` and `find_command` because both item names and visibilities are explicit in the capstone invocation. The derive generates only trait implementation items, avoiding extra public helper functions.

## Module 45 increment — prove the negative contract

Create a test matrix with four categories.

### Valid input that should compile and run

- each argument struct derives successfully;
- defaulted and required fields decode correctly;
- each handler descriptor invokes its function;
- the catalog preserves authored order;
- diagnostics and exit codes round trip.

### Invalid macro syntax

- unknown `#[arg]` key;
- duplicate helper key;
- missing semicolon in the catalog;
- unsupported diagnostic declaration shape.

### Valid syntax with invalid macro semantics

- duplicate command name;
- empty command name;
- `CommandArgs` on an enum;
- `#[command_handler]` on a private or async function;
- optional field combined with a default.

### Valid expansion rejected by ordinary Rust

- field type lacking `FromStr`;
- handler argument/result incompatible with the generated adapter;
- unresolved descriptor path.

A nonzero compiler exit is not enough for a negative case. Record the intended cause in `compiler-labs/manifest.json`, isolate the source, and reject incidental failures during review.

## Module 46 increment — create the procedural-macro crate

The `commandforge-macros` crate contains only compiler-facing transformation code. Keep entry points thin:

```text
TokenStream
    ↓ parse
AST or attached ItemFn/DeriveInput
    ↓ validate
normalized model
    ↓ generate
TokenStream
```

User mistakes become `syn::Error` values converted to compiler errors. Panics are reserved for genuine internal impossibilities such as parsing a fixed token literal written by the macro author; even those should be rare.

The crate pins `proc-macro2`, `quote`, and `syn`. These dependencies are permitted because the course is teaching real structural procedural macros. The dependency policy remains narrow: no command framework, parser generator, case-conversion package, or runtime registry crate is introduced.

Procedural macros execute during compilation and share the security concerns of build scripts. CommandForge’s macros perform no file access, network access, timestamp embedding, current-directory scanning, or debug printing. Their output depends only on their token input and fixed implementation.

## Module 47 increment — derive `CommandArgs`

The derive supports named-field structs only. Rejecting tuple structs and enums is not a missing feature; it protects a clear flag-to-field model.

For each field, parse a policy:

```rust
#[arg(long = "left", help = "left signed integer")]
left: i64
```

All keys are closed. Unknown keys and duplicates are errors. The default long name is the field identifier with underscores changed to hyphens. Leading dashes and whitespace are rejected because the derive adds `--` itself.

The derive treats syntactically unqualified `Option<T>` as optional. This is a documented syntactic convention, not semantic proof that an arbitrary path resolves to `std::option::Option`. Optional fields cannot also declare defaults because that creates two meanings for absence.

The implementation preserves generics with `split_for_impl` and appends parsing bounds to the where clause. It does not add unrelated bounds. It produces one usage literal and one ordered `ArgumentSpec` slice at expansion time, then ordinary runtime decoding code.

Test required fields, optionality, defaults, duplicate flags, unknown flags, invalid values, generic preservation, and no unnecessary field-type bounds.

## Module 48 increment — validate and preserve handlers

`#[command_handler]` accepts one key:

```rust
#[command_handler(about = "Add two signed integers with overflow checking")]
```

It requires a public, safe, synchronous, nongeneric free function with exactly one owned argument. The generated decoder must construct that argument, so borrowed arguments are rejected. The function must declare an explicit result type. The generated wrapper’s own typed signature asks Rust to prove that the handler result is `Result<String, CommandError>`.

The macro re-emits the original `ItemFn` without rebuilding a simplified copy. Documentation, visibility, attributes, parameter pattern, return syntax, and body are preserved. Then it emits:

- a private raw-argument wrapper;
- a public descriptor constant.

The wrapper calls `CommandArgs::decode`, then invokes the original function exactly once. Domain behavior remains in the original body.

Add compile-fail cases for private, asynchronous, generic, method-shaped, borrowed-argument, and wrong-result handlers. Add runtime tests that invoke through the descriptor and compare with direct calls.

## Module 49 increment — implement the command catalog DSL

Parse the grammar designed in Module 43. Require explicit semicolons. During semantic validation, store each name’s first span. Reject the later duplicate rather than silently keeping the first or last.

Generation emits:

```rust
pub static COMMANDS: &[CommandSpec] = &[
    CommandSpec { name: "add", handler: ADD_HANDLER },
    // ...
];
```

and a lookup function. The DSL keeps descriptor references as parsed Rust paths. It does not turn them into strings and try to resolve them itself. Ordinary name resolution and type checking establish whether each path exists, is visible, and has the required type.

Source order is the contract. It controls `list`, help presentation, and test output. Using a hash map during validation is acceptable only if generation still walks the ordered AST. The reference uses an ordered map only for duplicate bookkeeping and emits from the original entry vector.

## Module 50 increment — integrate checked external generation

`config/exit_codes.tsv` is the source of truth for process status values:

```text
SUCCESS<TAB>0<TAB>Command completed successfully
COMMAND_FAILURE<TAB>1<TAB>Command or domain validation failed
USAGE_FAILURE<TAB>2<TAB>Invocation or command-line usage was invalid
```

The build script:

1. emits `cargo::rerun-if-changed=config/exit_codes.tsv`;
2. reads the complete file;
3. validates exactly three tab-separated fields;
4. validates constant-style names;
5. parses codes in `0..=255`;
6. rejects duplicate names and duplicate codes;
7. rejects empty descriptions;
8. renders the complete generated module in memory;
9. writes one file under `OUT_DIR`.

The generated file contains `ExitCodeRecord` values and constants. It contains no timestamp, source-machine absolute path, random value, or filesystem-order dependency.

The build script does not modify `src/`. It does not duplicate diagnostic codes; process exit codes and application diagnostics are separate concepts with separate sources of truth.

## Expansion-to-runtime trace

CommandForge is complete only when you can reconstruct the ordinary Rust program produced by all generation layers. Trace one command—`repeat`—through these stages:

1. The source struct declares its fields and helper attributes. The struct is the authority for argument shape.
2. `#[derive(CommandArgs)]` parses only syntactic field structure and helper attributes. It emits an implementation that delegates value conversion to ordinary `FromStr` behavior.
3. `#[command_handler]` validates the attached function shape and emits companion descriptor/adapter items while preserving the original function.
4. `command_catalog!` parses command declarations, rejects duplicate command names, preserves source order, and emits the named catalog and lookup function.
5. The declarative diagnostic catalog emits stable codes, messages, reverse lookup, and authored order from one declaration.
6. `build.rs` validates `exit_codes.tsv`, writes deterministic Rust under `OUT_DIR`, and Cargo compiles the included generated module.
7. At runtime, ordinary argument parsing calls the generated `CommandArgs` implementation, ordinary handler code enforces the repetition domain rule, and ordinary application routing prints the result or maps an error to a generated exit code.

For each stage, name what it cannot know. The derive does not know whether a field type implements `FromStr`; generated Rust asks the type checker. The handler attribute does not know whether a path in another generated declaration resolves. The build script does not know runtime command arguments. Keeping those limits visible prevents macros from pretending to be a second type system.

## One authority per fact

Use this ownership table during every change:

| Fact | Authority | Generated consumers |
|---|---|---|
| argument field name and type | Rust command struct | `CommandArgs` implementation and help metadata |
| argument long name/default/help | field helper attribute | decoder and descriptor output |
| handler signature and about text | attributed function | invocation adapter and handler descriptor |
| command name and command order | `command_catalog!` invocation | catalog table and lookup function |
| diagnostic variant/code/message | declarative diagnostic catalog | enum methods, lookup, deterministic table |
| process exit symbol/code | `exit_codes.tsv` | generated constants and reverse/name lookup |
| runtime arithmetic or string policy | ordinary handler function | no generated owner |

A fact that appears authoritatively in two rows is a defect. For example, command help should not be copied independently into the catalog and the handler attribute. Either one declaration owns it or the model must explain why the values are intentionally different.

## Failure topology

CommandForge has several honest failure phases:

```text
invocation token parsing
    ↓
macro semantic validation
    ↓
expanded name resolution and type checking
    ↓
build-script input validation
    ↓
generated-source compilation
    ↓
runtime argument decoding
    ↓
handler domain behavior
    ↓
application reporting and exit mapping
```

Tests must distinguish them. A malformed `command_catalog!` separator should fail in macro parsing. A duplicate command name should fail in macro semantic validation with both relevant spans when possible. A handler path of the wrong type should survive expansion and fail during ordinary type checking. A malformed TSV row should fail the build script with physical line context. `--times nope` is runtime decoding. Checked-add overflow is handler-domain failure.

Do not replace this topology with one “macro error” category. The phase determines which code owns the repair and which diagnostic can be precise.

## Generated-code review

Review generated code as a public artifact even when users normally see only source invocations. Inspect:

- item names and visibility;
- qualification of definition-crate and invocation-site paths;
- preservation of generics and where clauses;
- caller-expression evaluation count and order;
- ownership and borrowing introduced by expansion;
- deterministic declaration order;
- size and readability of emitted code;
- trait bounds delegated to ordinary Rust;
- diagnostics attached to caller-owned spans;
- collisions with caller names or other generated items.

A macro can accept the right syntax and still emit a poor API. Expansion inspection complements behavioral and compile-fail tests; it does not replace them because token spelling may legitimately change while behavior stays stable.

## Test architecture by phase

| Evidence | What it proves |
|---|---|
| ordinary unit tests in runtime modules | handler and application behavior independent of macro implementation |
| positive macro fixtures | accepted language expands and behaves as promised |
| negative macro fixtures | rejected language fails for the intended reason and phase |
| generic derive fixtures | declaration generics and where clauses survive generation |
| downstream crate fixture | exported paths survive crate boundaries and renaming |
| build-support unit tests | schema, duplicates, ordering, and rendering are deterministic |
| clean rebuild after input changes | rerun directives include every authoritative input |
| CLI process tests | generated metadata, runtime parsing, handler dispatch, output, and exit status compose correctly |

Freeze one minimal fixture per causal rule. A giant invalid fixture produces many diagnostics but weak evidence because a different error may mask the intended one.

## Compatibility review

A macro’s invocation syntax and generated Rust API both participate in compatibility. Review changes such as:

- accepting a new optional separator that creates matcher ambiguity;
- changing a helper attribute’s default;
- renaming a generated associated item;
- adding an invented trait bound to a derive;
- changing the order of generated catalog entries;
- altering which span receives a diagnostic;
- raising the minimum supported Rust version through generated syntax;
- changing build input normalization or rerun behavior.

Not every diagnostic wording change is semver-breaking, but accepted syntax, generated names, trait obligations, runtime evaluation semantics, and stable numeric codes are much stronger contracts. Document which surfaces are stable and which are implementation details.

## Independent cross-layer change

Add a new `trim` command:

```text
commandforge run trim --text <text> [--mode both|start|end]
```

Do not begin in the catalog. Work through the authority map:

1. define an ordinary argument struct and decide how the optional mode is represented and defaulted;
2. derive argument parsing without teaching the derive the semantics of trim modes;
3. write the ordinary handler and domain error for unsupported mode values if the mode is not represented by a dedicated `FromStr` type;
4. attach handler metadata;
5. register the command once in the catalog;
6. decide whether a new diagnostic or exit code is actually required;
7. add positive runtime tests, a missing-value test, an unknown-option test, a generated catalog-order test, and a CLI process test;
8. inspect expansion and confirm that existing commands are unchanged.

Then answer the deletion test: if CommandForge had only this one command, which generation layers would no longer be justified? The answer should change with product scale; metaprogramming is not made correct by permanence.

## Reproducibility and cost

Compile-time generation has cost even when runtime behavior is fast. Record:

- procedural-macro dependencies and compile time;
- expansion size;
- number of generated implementations and items;
- rebuild triggers;
- deterministic inputs and outputs;
- whether errors appear before or after expansion;
- whether ordinary IDE navigation remains usable.

Do not claim a performance improvement without measurement. The primary benefit here is one checked source of truth and causal diagnostics. If generated code becomes larger or harder to inspect than a hand-written table, revisit the mechanism boundary.

## Final architecture defense

Before completing Course 5, answer these without opening the implementation:

1. Which CommandForge facts are declared once, and where?
2. Why is command behavior not generated?
3. Why does the derive add `FromStr` bounds but not `Display` bounds on field values?
4. Which `Option<T>` conclusion is syntactic rather than semantic?
5. Why does the handler attribute reject borrowed arguments?
6. How does the generated wrapper delegate result compatibility to Rust?
7. Why does the catalog own command names instead of the handler attribute?
8. Why is source order part of the catalog contract?
9. Which paths are generated, and how do they resolve inside the runtime crate?
10. Which invalid inputs fail during parsing, validation, name resolution, type checking, build execution, and runtime?
11. Why are process exit codes external data while diagnostic codes use a declarative macro?
12. What security and reproducibility obligations follow from adding a proc-macro or build dependency?
13. Which metaprogramming mechanism could be deleted most easily if the product changed, and what would replace it?
14. Which proposed feature would force the catalog DSL to evolve, and how would you preserve existing syntax?
15. Where would you draw the boundary before turning CommandForge into a reusable public crate?

A strong defense does not praise macros in general. It explains why each mechanism is present, why its grammar is bounded, what it emits, what it refuses to know, and how ordinary Rust remains authoritative wherever generation is unnecessary.

## Completion condition

CommandForge is complete when:

- all four runtime commands behave as specified;
- every generated surface has one source of truth;
- positive and negative tests cover each macro boundary;
- catalog and build output are deterministic;
- no user mistake causes a procedural-macro panic;
- generated paths are deliberate;
- argument expressions and runtime values are not evaluated unexpectedly;
- no build output is written outside `OUT_DIR`;
- the application can be understood from ordinary expanded interfaces;
- you can remove or replace one compile-time layer without rewriting unrelated domain behavior.

That final condition is the architectural test. Good metaprogramming reduces drift without making the entire product depend on macro cleverness.
