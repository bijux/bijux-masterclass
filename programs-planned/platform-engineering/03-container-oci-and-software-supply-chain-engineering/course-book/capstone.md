# Capstone — Atlas Workload Release 1.0

## Starting point

Course 2 exports a cloud-neutral workload contract. Atlas has separate API and worker processes, durable spool/results, an ephemeral runtime directory, runtime-supplied configuration and secrets, port 8080, a non-root identity, workload identity, and a thirty-second shutdown contract. The cloud foundation can replace machines, but the workload package is still entangled with image/bootstrap behavior.

Course 3 changes the release unit from “files installed on a machine” to immutable OCI subjects plus a governed runtime and evidence contract.

## Released products

- `atlas-api` image index for linux/amd64 and linux/arm64;
- `atlas-worker` image index for the same platforms;
- `atlas-probe` verification-only index;
- runtime profiles for API, worker, and probe;
- subject-bound SBOM and provenance referrers for deployable images;
- signed evidence and categorical policy report;
- exact Course 4 contracts for image, process, ports, health, storage, configuration, resources, and trust.

## Capstone invariants

1. Review, policy, promotion, deployment, rollback, and handoff use immutable digests.
2. Every descriptor’s type, size, and digest are verified before parsing.
3. Manifest layer digests and config DiffIDs match the compressed and uncompressed bytes they name.
4. Safe ordered layer application produces the reviewed rootfs; historical layers remain inspectable.
5. Build context excludes secrets and unrelated host state; cache authority is explicit.
6. Every required platform label matches executable identity and has a stated target evidence class.
7. Runtime profiles preserve Course 2 identity, storage, networking, health, and shutdown semantics.
8. SBOM, vulnerability/VEX, provenance, and signature evidence bind to the current image subject.
9. Non-compensable gates cannot be offset by scores or later green checks.
10. The Course 4 handoff contains facts and requirements, not premature Kubernetes design.

## Implementation map

- `capstone/atlas_container/` implements transparent semantic mechanisms;
- `capstone/workload/` contains real Go binaries and Containerfiles;
- `capstone/contracts/` contains Atlas course profiles;
- `capstone/runtime/profiles/` records effective execution requests;
- `capstone/registry/` records registry policy and temporary storage boundary;
- `capstone/sbom/` supplies deterministic inventory/risk fixtures;
- `capstone/security/` documents fixture trust and runtime security profile;
- `capstone/releases/` contains one checked release and categorical negative cases;
- `capstone/planted-defects/` maps defects to proofs;
- `capstone/native/` provides guarded independent-tool lanes;
- `capstone/handoff/` is the only input Course 4 needs.

## Build and evidence flow

The tour compiles each Go binary twice, packages each platform into a deterministic OCI graph, creates indexes, and repeats the API build to compare top-level digests. It publishes API/worker objects to a loopback Distribution subset and attaches SBOM/provenance artifacts by subject. It evaluates policy, executes the probe under the bounded runtime harness, and writes the successor handoff.

The checked release is then regenerated by `make checked-release`. Accepted JSON is not hand-authored independently from the mechanism that produced it.

## What makes the capstone educational

The semantic implementation is intentionally small enough to inspect. You can follow:

- the exact bytes hashed into every digest;
- the distinction between compressed layer identity and DiffID;
- whiteout application;
- platform selection and ELF inspection;
- registry tag/digest/referrer paths;
- runtime identity/mount observation;
- DSSE signing and subject verification;
- release-policy ordering.

A production product usually hides these behind APIs. The course exposes them before later courses automate them.

## What it deliberately does not claim

The capstone is not:

- an OCI conformance-certified runtime or registry;
- a hardened multi-tenant sandbox;
- an operated build service or transparency log;
- a comprehensive arbitrary-ecosystem SBOM/scanner;
- production key custody;
- representative capacity evidence;
- Kubernetes admission or scheduling proof.

Those limits are part of the final release record. “Not executed” is a valid result when the environment is absent.
