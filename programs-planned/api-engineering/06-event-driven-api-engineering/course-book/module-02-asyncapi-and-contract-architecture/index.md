# Module 02 — AsyncAPI, CloudEvents, and Contract Architecture

> **Program stage:** Course 6 of 6 — Extend the promise across asynchronous time.

> **Central question:** How do AsyncAPI, CloudEvents, schemas, channels, operations, bindings, and examples form one governed event contract?

## Where this module fits

Module 01 established which messages deserve a public asynchronous boundary. Those decisions are still
prose until machines can parse the channels, operations, messages, schemas, examples, security schemes,
and server bindings. An informal wiki page cannot support validation, generation, compatibility review,
or consumer discovery.

AsyncAPI is the description format for this course, but learning its object model is not the final goal.
The goal is to express an asynchronous interface without losing semantic ownership. A syntactically valid
document can still be misleading: an operation may use the wrong direction, a message may omit the
partition key, examples may violate schemas, or a NATS subject may be mistaken for the event’s business
identity.

The course combines an AsyncAPI 3.1.0 document with a constrained CloudEvents 1.0 envelope profile. AsyncAPI
describes the interface and transport-facing operations. CloudEvents supplies interoperable event metadata.
JSON Schema describes the `data` payload. The event catalogue records governance facts that are awkward or
inappropriate to encode as transport syntax. Each artifact has a distinct responsibility.

## Core event model

### 1. AsyncAPI describes an interface, not a broker configuration dump

An AsyncAPI document identifies application operations over channels and the messages those operations
exchange. Servers and bindings can describe NATS, Kafka, AMQP, MQTT, WebSocket, or other transport
details, but the document should not be generated by copying broker administration settings.

The contract begins with the application’s perspective. The Analysis command publisher sends
`StartAnalysis` to a command channel. The control plane receives it. The control plane then sends
lifecycle events that consumers receive. An operation’s `action` is interpreted from the described
application, so “send” and “receive” must not be copied mechanically from the remote peer’s viewpoint.

The physical NATS subject is an address. The logical channel is an API element. The event `type` is a
semantic identifier. They may be related, but merging all three makes later transport migration and
catalogue governance harder.

### 2. AsyncAPI 3 operations point to channels

AsyncAPI 3 separates channels from operations. A channel describes the communication location and the
messages permitted there. An operation describes an application action—send or receive—over a channel.
This separation permits several applications to expose different operations over the same shared
channel description without duplicating message definitions.

The capstone uses stable operation IDs such as `sendStartAnalysis` and `receiveAnalysisRunCompleted`.
Operation IDs are code-generation and governance identities; changing one can break consumers even if
the physical subject remains unchanged.

Channel addresses use parameters only when the runtime actually resolves them. A wildcard subscription
used by an operator is not automatically the same as a public parameterized channel.

### 3. CloudEvents supplies envelope vocabulary, not domain meaning

CloudEvents 1.0 defines common attributes including `specversion`, `id`, `source`, `type`, `subject`,
`time`, `datacontenttype`, and `dataschema`. The course adds `tenantid`, `correlationid`,
`causationid`, `partitionkey`, and optional `traceparent` under a documented profile.

The extension attributes are policy, not part of the CloudEvents core specification. The course does
not claim that every CloudEvents consumer understands them automatically. Their names, types, and
semantics are versioned in `event-profile.json`.

Structured JSON encoding is used in deterministic proofs: envelope and payload form one JSON object.
A live NATS adapter may map selected metadata to headers, but that transport mapping cannot change the
canonical semantic envelope used for identity and signatures.

### 4. Envelope and payload require two validation layers

The envelope proves that the message has valid identity, source, type, time, schema reference, tenant,
correlation, causation, partition, and content metadata. The payload schema proves that the event-specific
`data` object has required fields, types, ranges, and additional-property policy.

Validating only the payload allows a forged source or missing tenant. Validating only the envelope allows
an `AnalysisRunCompleted` event with no run ID or a negative duration. The contract proof resolves the
message reference, applies the common envelope profile, then validates `data` against the referenced JSON
Schema.

Business invariants remain a third layer. JSON Schema can require `artifactCount >= 0`; it cannot prove
that the listed artifacts exist in the authoritative database.

### 5. Schema identifiers must survive file movement

A JSON Schema `$id` is an identifier and reference base, not merely a filename. `dataschema` identifies
the payload schema that the producer claims to use. Relative filesystem references are acceptable
inside the source tree, but emitted event metadata should use stable absolute schema URIs.

The capstone uses versioned schema URIs under a course namespace and resolves source files offline during
proof. A bundler may rewrite internal references, yet the public schema identity remains stable.

A schema filename such as `analysis-run-completed.schema.json` is a repository detail. Consumers should
not treat the filename as the compatibility identity unless the catalogue explicitly defines it.

### 6. Examples are executable contract evidence

Each public message has at least one complete example containing both envelope metadata and `data`.
Examples must validate against the same schemas as production messages. They also expose ambiguities that
type definitions alone can hide: timestamp precision, subject format, URI spelling, null handling,
partition keys, and safe error detail.

Examples are not test fixtures by implication. The proof route explicitly loads them, resolves the
message and payload schemas, and verifies the profile. A documentation renderer displaying an example is
not evidence that the example is valid.

Examples should be realistic but contain no live credentials, private dataset content, or sensitive
tenant data.

### 7. Multi-document architecture needs deterministic offline resolution

One monolithic AsyncAPI file becomes difficult to review, while hundreds of tiny fragments create a
reference maze. The capstone keeps the entry document, one message fragment per public type, and one
payload schema per type. Shared envelope rules live in the course profile rather than being copied into
every payload schema.

All references must resolve from a clean checkout without network access. Remote schema identifiers may
name public identities, but local proof maps them to repository-controlled files. The build output must
be deterministic so a release diff represents semantic changes rather than traversal order.

Reference cycles are allowed only where the underlying schema meaning requires recursion. Message
fragments do not use circular ownership.

### 8. Validation evidence has explicit limits

The dependency-light validator checks YAML structure, duplicate keys, AsyncAPI version, channel and
operation references, message references, profile-required fields, schema resolution, examples, and a
course-specific semantic policy. It does not claim to be a complete implementation of every AsyncAPI
rule or every protocol binding.

An optional independent AsyncAPI CLI route validates the description when the pinned toolchain is
available. A live NATS route checks addresses, headers, acknowledgement, and retention behavior. Those
stronger routes are recorded separately rather than being silently marked as passed in an environment
without the tools.

Honest scope is part of contract engineering. A local checker should say what it checked, not announce
“the contract is valid” without qualification.

## Engineering requirements

| Rule | Required behavior | Failure if omitted | Decisive evidence |
|---|---|---|---|
| Operation direction | Every operation action is correct from the described application’s perspective. | Producers and consumers are generated or documented backwards. | Operation/channel map and review |
| Message closure | Every channel permits an explicit set of message references. | Undocumented messages enter a public channel. | Channel message list and broker policy |
| Envelope profile | Every example and runtime message satisfies CloudEvents 1.0 plus event profile 1.0. | Identity, tenant, or partition metadata becomes optional by accident. | Profile validator and shared vectors |
| Payload schema | Every message `data` object validates against its declared JSON Schema. | Type-correct envelopes carry semantically malformed payloads. | Example and schema proof |
| Stable schema URI | Every `dataschema` is an absolute, versioned identity mapped to a controlled file. | File movement or bundling changes public schema identity. | Catalogue and resolver map |
| Offline references | All source references resolve from a clean checkout without network access. | Builds depend on mutable remote content. | Reference-resolution proof |
| Independent validation boundary | Local and external validation results are distinguished. | A partial checker is misrepresented as complete conformance. | Verification report |

## Worked failures

### Case 1 — send and receive were reversed

A consumer application document says it “sends” `AnalysisRunCompleted` because the broker sends the
record to the process. AsyncAPI operations are from the application perspective: the consumer receives
the event. Reverse the operation action and keep broker delivery mechanics in the binding or runtime
documentation.

### Case 2 — NATS subject became event type

The event `type` was set to `analysis.events.completed`, exactly matching the subject. A later subject
hierarchy change would therefore alter semantic identity. Keep the stable reverse-DNS event type in the
envelope and document the physical subject separately in the channel address.

### Case 3 — valid schema, invalid example

The completed example contains `durationMs: "8421"` as a string. The renderer displays it, but generated
consumers infer an integer. Add example validation to the proof and fix the example; documentation
visibility is not schema conformance.

### Case 4 — payload schema accepted private fields

`additionalProperties` was omitted, so a producer included a worker lease token and exception stack.
The payload remained structurally valid. Close public schemas deliberately and use an explicit extension
object only where open content is an actual contract requirement.

## Python implementation

The Python profile validator reads the source description rather than requiring a broker.

```text
capstone/tracks/python-fastapi/src/event_engineering/asyncapi_profile.py
capstone/contracts/asyncapi.yaml
capstone/contracts/examples/
```

`validate_course_profile()` checks the entry version, required top-level identity, channels, operations,
operation actions, message references, and course extensions. The course proof adds reference and example
validation around it.

A focused workflow is:

```python
import yaml
from event_engineering.asyncapi_profile import validate_course_profile

document = yaml.safe_load(open("capstone/contracts/asyncapi.yaml"))
report = validate_course_profile(document)
assert report.operation_count == 3
assert report.channel_count == 3
assert report.message_count == 7
```

Do not embed schema resolution in framework route code. Contract validation is a build and release concern;
runtime message validation consumes the released schema/profile artifacts.

## TypeScript implementation

The TypeScript track treats the AsyncAPI document as an input contract, not as a set of interfaces that
TypeScript alone can guarantee. Generated or authored types provide compile-time help, but runtime messages
still cross an untrusted boundary.

The workshop inspects `asyncapi.yaml`, resolves the same message references, and uses the shared envelope and
payload validators before handler dispatch. Where a generator is used, generated code is checked into a
release artifact or reproducibly regenerated from the pinned contract.

A useful distinction is:

```typescript
type AnalysisRunCompletedData = {
  runId: string;
  durationMs: number;
  artifactCount: number;
};
```

This type does not reject a malformed JSON message at runtime. The schema validator and envelope profile do.

## Cross-language invariant

Both tracks must resolve the same operation IDs, channel addresses, message names, schema URIs, and examples.
They must classify the same invalid envelope or payload as invalid. Differences in YAML libraries, object
property order, or generated type names cannot change public contract meaning.

`make contract-proof` is the language-independent authority; implementation tests prove that each track
enforces the released profile.

## Design review

Review the contract in four passes. First, read only operation names and directions: can the application
perspective be understood? Second, inspect channels and addresses: are logical and physical identities
separated? Third, inspect message metadata and schemas: can every example be validated and traced to an
owner? Fourth, inspect bindings and security: are transport-specific claims accurate and bounded?

A large green validator result does not replace this review. Semantic mistakes are often perfectly valid
YAML.

## End-to-end worked example

`sendStartAnalysis` references the command channel and `StartAnalysis` message. The command envelope uses
CloudEvents metadata because the same identity and correlation discipline is valuable, but the catalogue
classifies it as a command with one logical handler.

The control plane exposes send operations for requested, started, completed, and failed lifecycle facts.
Notification, analytics, and audit application descriptions receive selected events. The event catalogue
records that `AnalysisRunCompleted` is retained for replay, while a progress event has shorter retention and
a different late-consumer expectation.

The NATS binding maps channels to subjects. A deterministic broker proof ignores that binding while
preserving operation, message, envelope, schema, and partition semantics. A live adapter later proves the
binding-specific behavior without changing the contract.

## Failure patterns

- **YAML validity mistaken for API validity.** A parser accepts the document, but operations, examples, or ownership are wrong.
- **Direction reversal.** Actions are written from the broker or peer perspective rather than the described application.
- **Address/type collapse.** A transport subject becomes the event’s semantic type.
- **Envelope-only validation.** A valid CloudEvents shell carries malformed domain data.
- **Type-only validation.** A payload passes while source, tenant, correlation, or partition metadata is forged.
- **Remote reference dependency.** A clean build changes or fails when an external schema host changes.
- **Generated-type overconfidence.** Compile-time TypeScript types are treated as runtime validation.
