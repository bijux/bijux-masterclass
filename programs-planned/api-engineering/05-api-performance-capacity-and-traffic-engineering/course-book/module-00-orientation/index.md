# Orientation — API Performance, Capacity, and Traffic Engineering

> **Program stage:** Course 5 of 10 — Sustain the promise under pressure.

> **Orientation question:** Is the incoming boundary exact, and can you explain why Course 5 owns the next engineering responsibility?

## Why this orientation exists

Course 5 starts from accumulated guarantees rather than an empty repository. Orientation prevents a stale handoff, an unavailable tool, or an accidental version change from contaminating the ten teaching days. The goal is not setup for its own sake; it is to make the first claim of **API Performance, Capacity, and Traffic Engineering** honest.

## Incoming boundary

The Course 4 observable and recoverable API 1.2 service with Security and Reliability Profiles 1.0 and migrations 001–008.

Verify that boundary before editing. Compare the predecessor bytes or entry evidence, inspect the version ledger, and identify which artifacts are historical inputs. A hard implementation problem in Course 5 must be solved at the current layer, not by rewriting an earlier contract or proof.

## Course responsibility

Measure, model, and control latency, throughput, resource use, fairness, and overload behavior with comparable evidence.

The governing question is:

> Where do time and capacity go, what is the first limiting resource, and which measured change improves the system without weakening correctness?

The current version state is:

> API 1.2, Security Profile 1.0, and Reliability Profile 1.0 preserved; Performance Profile 1.0 introduced; migrations 001–009.

## Implementation route

The course strategy is **one primary implementation track plus one comparative reference track**. Record the selected route and the reason it supports your learning goal. Do not switch runtimes in the middle of a failed mechanism; first determine whether the model, the implementation, or the environment is wrong.

## Evidence boundary

List the proof routes available on your machine and classify them as deterministic, local process, live persistence/network, documentation, or independent-tool evidence. The first stronger environment-backed claim is **representative load with resource telemetry**. Until that route actually runs, use narrower wording and record it as `not-executed`.
