# API Platform, Governance, and Developer Experience Engineering

**Course 10 of 10 — Operate APIs as an organizational platform**

## Course promise

Turn the interfaces, evidence, and ownership model from Courses 1–9 into a product-oriented API platform with governed self-service and measurable consumer outcomes.

> **Governing question:** How can an organization make trustworthy API work easier to discover, create, publish, consume, evolve, support, and retire without centralizing domain ownership?

## Place in the program

**Incoming boundary:** The Course 9 handoff containing HTTP, event, RPC, distributed-service, and GraphQL contracts with explicit ownership and release evidence.

**Outgoing boundary:** Analysis API Platform 1.0, a governed catalog and registry, lifecycle and policy engine, golden path, documentation and sandbox, SDK and provenance publication, runtime reconciliation, support model, and a ten-course graduation dossier.

Course 10 treats its incoming handoff as historical evidence, not editable scaffolding. It may add only the operate apis as an organizational platform mechanisms governed here; any public or durable change requires an explicit compatibility and release decision.

## What you will add

- platform product and operating boundaries;
- catalog, ownership graph, immutable contract registry, and governance as code;
- consumer-aware lifecycle, exceptions, templates, and self-service;
- documentation, discovery, sandbox, SDK, SBOM, and provenance workflows;
- runtime reconciliation, product analytics, federated decision rights, and program final defense;

## Course-level learning outcomes

- Define the platform as a product with distinct users.
- Model components, APIs, resources, systems, domains, and groups.
- Distinguish drafts, releases, channels, and promotions.
- Design deterministic policy rules around authoritative evidence.
- Model lifecycle as evidence-gated transitions.
- Design a golden path as a maintained product.
- Organize documentation around tasks and interface choice.
- Design SDKs as supported products rather than raw generated code.
- Reconcile approved releases with runtime routes.
- Design a federated platform operating model.

## Deliberate boundaries

This course does not claim or teach the following as part of its completion:

- a portal as a substitute for authoritative metadata;
- gateway ownership of domain authorization;
- governance by average score or manual theater;
- claiming local fixtures are an operated enterprise platform;

Those boundaries prevent the course from becoming a survey of adjacent tools and make its completion claims defensible.

## How to study

Begin with [Start here](start-here.md).
