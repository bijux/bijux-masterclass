# Course guide

## Ten dense teaching days

| Day | Module | Daily decision |
|---:|---|---|
| 1 | Platform product model | Which repeated organizational problem should the platform own? |
| 2 | Catalog and ownership graph | Which source is authoritative for each metadata fact? |
| 3 | Contract registry | What constitutes a published release across four protocols? |
| 4 | Governance as code | Which decisions can be automated and which require accountable judgment? |
| 5 | Lifecycle | When may an API change, deprecate, or retire? |
| 6 | Golden paths | Which safe defaults reduce work without erasing architecture choices? |
| 7 | Docs and sandbox | Can a new consumer reach first success without private help? |
| 8 | SDK supply chain | Can a consumer verify what contract and build produced an artifact? |
| 9 | Runtime and analytics | Does runtime state match the catalog, and are outcomes improving? |
| 10 | Federated governance | Can the platform scale without becoming a centralized bottleneck? |

## Daily rhythm

1. Retrieval review and predecessor check.
2. Read the complete chapter.
3. Work the exercises without the answer key.
4. Review the Python and TypeScript mechanisms named in the chapter.
5. Perform the laboratory.
6. Interpret the report rather than merely generating it.
7. Satisfy the checkpoint.

## Evidence classes

- **Course-executed:** deterministic checks in this repository.
- **Environment-backed:** requires an external registry, portal, gateway, package
  registry, or hosted build platform.
- **Operational evidence:** collected from a representative live system over
  time. The course teaches its shape but does not fabricate it.

A platform is not mature because it has many integrations. It is mature when its
claims are bounded by evidence and its users can make better decisions with less
unnecessary work.
