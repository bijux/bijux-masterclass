# Standards and Evidence — API Platform, Governance, and Developer Experience Engineering

## How standards are used

Standards settle the protocol and compatibility questions relevant to **API Platform, Governance, and Developer Experience Engineering**; they do not decide the architecture for you. Classify every cited rule as normative requirement, interoperability advice, course profile, observed tool behavior, or architecture decision.

## Reading discipline

Start from the module question, then read only the primary-source clauses needed for operate apis as an organizational platform. Restate the rule, build a counterexample in the Analysis Runs Platform, and name a falsifying oracle; citation alone never proves that the Python or TypeScript runtime conforms.

## Executable profile and frontier

Examples and proofs use the pinned Course 10 profile recorded in `course.json`: All earlier interface and engineering profiles preserved; Analysis API Platform 1.0 and platform-catalog metadata migrations 001–004 introduced. A newer specification or tool does not silently change that profile; advance contracts, fixtures, compatibility rules, and the version ledger together.

## Evidence boundary

The strongest environment-backed claims in Course 10 require an operated catalog/portal, external registries, runtime control plane, identity system, and consumer telemetry. Local parsers, fixtures, unit tests, or simulators remain useful but support narrower claims; [Evidence model](evidence-model.md) names those boundaries.
