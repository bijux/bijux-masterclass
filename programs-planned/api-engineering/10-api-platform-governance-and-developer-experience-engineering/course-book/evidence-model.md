# Evidence Model — API Platform, Governance, and Developer Experience Engineering

## Course-specific proof ladder

| Level | Evidence | Minimum record |
|---:|---|---|
| 1 | catalog and registry integrity | A named claim, version, environment, oracle, and retained artifact |
| 2 | policy evidence and lifecycle decisions | A named claim, version, environment, oracle, and retained artifact |
| 3 | sandbox and artifact publication traces | A named claim, version, environment, oracle, and retained artifact |
| 4 | runtime drift, support routing, and graduation dossier | A named claim, version, environment, oracle, and retained artifact |

## Authority versus diagnosis

For platform claims, immutable releases, accountable ownership, policy evidence, and observed runtime state each answer separate questions; a green portal page cannot substitute for any of them.

## Negative evidence

Every Course 10 lab contains a defect specific to operate apis as an organizational platform. Predict the first failing oracle, retain the raw counterexample, and keep it after repair; a proof that accepts that defect cannot support the checkpoint claim.

## Evidence package

Each checkpoint should retain:

```text
claim and owner
input, workload, or candidate identity
software and contract versions
environment identity
command or procedure
raw result
interpreted decision
known exclusions
cleanup state
```

## Unavailable infrastructure

When an operated catalog/portal, external registries, runtime control plane, identity system, and consumer telemetry is unavailable, run the deterministic evidence that still applies and record the stronger route as `not-executed`. The wording of the claim must shrink with the environment.
