## The proto source is authoritative

The versioned `.proto` files and their imported dependencies define the RPC contract. Handwritten DTOs, framework handlers, generated source, documentation, and reflection must derive from or be checked against them. Editing generated code to fix a behavior is a release defect: the next generation erases the change and other languages remain inconsistent.

Record compiler, plugin, runtime, and option versions. Generation inputs include include paths, package mappings, TypeScript loader options, Editions support, and well-known type versions. A lock file or tool-version policy makes the process reviewable. Generate into a clean temporary directory, compare with checked-in or packaged artifacts, and fail on unexplained drift.

The dependency-light course includes generated-equivalent Python descriptors because `grpcio-tools` may be unavailable. The file says exactly how it was derived and the full proof regenerates it when pinned `protoc` tooling exists.

## protoc and Buf are complementary

`protoc` is the reference compiler and descriptor generator. Language plugins produce stubs and message classes. Buf can lint source, manage modules/dependencies, generate via templates, and compare breaking changes against a baseline. Neither tool proves application semantics.

Use Buf to standardize naming, packages, imports, reservations, and compatibility policy. Use `protoc` descriptors to inventory exact service/method/message definitions. Use language compilers and tests to prove generated APIs integrate with the supported runtimes. Keep a capability matrix because Editions, optional fields, well-known types, and plugin features can differ.

An unavailable tool produces a not-executed record with the command and expected oracle. A local parser does not impersonate Buf or `protoc`.

## Descriptor sets are portable contract evidence

A descriptor set is a serialized schema graph containing files, messages, enums, services, methods, streaming flags, and options. Include imports when the consumer needs a self-contained inventory. Descriptor sets support dynamic tooling, release comparison, documentation, and reflection checks without parsing source text.

The course stores a normalized JSON projection for dependency-light review and optionally the binary descriptor set generated by pinned tools. Normalization sorts declarations and excludes unstable paths or source-info fields according to policy. The digest becomes part of the release record.

Do not mistake a descriptor digest for semantic compatibility. Two descriptors can differ additively or incompatibly; the compatibility engine must classify the change.

## Reflection observes one running instance

Server reflection exposes descriptors for services actually registered in a runtime. It can reveal that the deployment serves an old package, omitted a method, or accidentally exposes an internal diagnostic service. It does not replace source governance because it reflects one process at one moment and may be disabled by policy.

A live proof queries reflection, builds a fully qualified method inventory, and compares it with the release catalogue. Extra or missing methods fail unless explicitly allowed, such as standard health and reflection services. The proof records endpoint identity and server build.

When reflection is disabled, the deployment must still expose a signed or versioned build inventory through an authorized operational path.

## Testing layers answer different questions

**Semantic tests** exercise model adapters, status mapping, retry decisions, stream state machines, authorization policy, and lifecycle without a network. They are fast and deterministic. **In-process service tests** invoke generated handlers with controlled contexts and stores. **Network conformance tests** start a real gRPC server and prove serialization, metadata, deadlines, cancellation, streaming, health, and status over HTTP/2. **Generated-client tests** compile and run each supported language surface. **Environment-backed tests** add TLS, load balancing, PostgreSQL, and external tools.

A mock that returns expected messages cannot prove persistence, concurrency, idempotency, or transport cancellation. A network test cannot exhaust every state-machine schedule. The proof ladder combines them and declares its boundary.

Planted defects are assigned to specific layers. If changing a field number is detected only by an end-to-end test, the generation pipeline is too weak.

## Generated-client compatibility

A provider can compile while consumers fail after regeneration. Maintain a small consumer matrix: Python version/runtime, TypeScript loader or generator, method use, enum policy, JSON use, and supported upgrade window. Generate clients from the candidate schema and build representative consumer programs.

Source compatibility checks include accessor names, optional presence APIs, enum shapes, 64-bit representations, async/sync call forms, and streaming interfaces. Runtime tests execute at least one call for every method shape. A binary-compatible field rename may still fail this gate.

Do not commit enormous generated trees without a policy. Checked-in generated artifacts improve offline learning and reproducibility; generated-at-build artifacts reduce drift. The course documents the chosen boundary and verifies it.

## RPC catalogue and ownership

The catalogue lists every fully qualified method, version, capability owner, state owner, allowed callers, deadline owner, retry policy, idempotency requirement, request and response sizes, streaming shape, status vocabulary, observability signals, and consumers. It is a review index, not a second schema.

Every method appears exactly once. Every contract service has an owner. Every catalogue method exists in the descriptor. Adding a method requires catalogue, policy, tests, and release evidence. Removing a method requires consumer migration and deprecation evidence.

Course 10 uses the catalogue to decide which internal call path can be migrated or rolled back. Course 8 will use it when evaluating service boundaries.

## Documentation generated from contracts needs human meaning

Generated reference pages are useful for field and method inventory, but they cannot explain why an operation is synchronous, what state is authoritative, how ambiguity is reconciled, or when a stream should reconnect. The course book remains the educational product. Generated docs support lookup.

Proto comments should state field semantics, units, identity scope, security sensitivity, ordering, retention, and compatibility constraints. Avoid comments that merely repeat the field name. Link methods to status and deadline policies.

Strict documentation build checks navigation and links; it does not prove that the explanation is correct. Editorial review and exercises provide that layer.

## Release evidence is reproducible

A candidate release records source digest, descriptor digest, generated artifact digests, tool versions, lint and compatibility results, language builds, conformance tests, reflection inventory where available, catalogue match, consumer declarations, and unexecuted capabilities. Reports are deterministic or separate volatile environment data from release identity.

Generate twice from a clean checkout and compare bytes. Extract the course or release package and rerun proofs. Manifests cover source and intentionally checked-in derived artifacts. Temporary compiler output and caches are excluded.

A successful generation command is not release approval. Course 10 combines this evidence with migration, shadow, public HTTP, event, and rollback proof.

## Worked governance review: one source, five observations

The repository contains `analysis.proto`, checked Python generated-equivalent modules, a TypeScript loader profile, a descriptor projection, and a running Python server. These are related but not equal. The proto source is authoritative. Generated modules are derived. The descriptor is compiled contract evidence. The method catalogue adds ownership and operational policy. Reflection observes one runtime instance.

A release begins from a clean source digest. In a fully provisioned environment, pinned `protoc` and plugins generate Python and TypeScript artifacts into temporary directories. Buf lint checks naming, packages, imports, and reservations. Buf breaking compares the candidate with the released baseline. The Python and TypeScript consumer projects compile. Descriptor sets are normalized and compared with the catalogue. The generated bytes are produced twice to detect nondeterminism.

The dependency-light environment cannot pretend to execute missing tools. It imports a checked serialized descriptor into the Python runtime, compiles TypeScript semantic adapters, validates golden bytes and local schema invariants, and reports `protoc`, Buf, grpcurl, and grpc-js network routes as not executed. This is still useful evidence because its scope is explicit.

Now inject drift. A developer edits generated Python code to rename a field accessor. Deterministic regeneration or the manifest catches it. Another developer registers `AdminService/RepairRun` in the server but forgets the catalogue and authorization policy. Reflection comparison detects the extra method when available; source registration/static ownership checks should catch it earlier. A third developer changes a retry option in service config without modifying the proto. Descriptor compatibility passes, but governance and behavioral release tests detect the policy change.

Testing layers are assigned precise jobs. Model tests exercise presence and int64. Golden bytes exercise encoding. In-process tests explore adversarial schedules. Live network tests prove HTTP/2 gRPC metadata, status, deadlines, and streams. Database tests prove idempotency and leases. Generated-client builds prove source compatibility. Reflection proves deployed inventory. No single green suite is allowed to claim all properties.

Documentation also follows the source. Generated reference pages can list fields and methods, but they cannot explain why WatchRun is not the durable Event API or why a live worker stream does not authorize stale completion. The course book remains authoritative for engineering meaning; proto comments preserve field-level semantics; the catalogue links methods to owners and policy.

The release record therefore joins source, descriptor, generated artifacts, consumers, runtime, policy, and proof boundaries. It is reproducible from a clean checkout and honest about unavailable capabilities.

## Failure checklist

- Can generated code be edited without regeneration detecting drift?
- Are compiler, plugin, runtime, and option versions recorded?
- Does a descriptor or lint pass get misrepresented as behavioral proof?
- Can runtime reflection expose methods absent from the release catalogue?
- Do representative generated consumers compile and execute?
- Can an unavailable external tool be silently converted into a pass?
