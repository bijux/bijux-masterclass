# Language Strategy — OpenAPI Contract Engineering

## Strategy

Both providers are primary. Implement the same operations in Python/FastAPI and TypeScript/Fastify, then run one provider-neutral scenario corpus. The point is not stylistic symmetry; it is proof that the contract survives different runtime and type systems.

## What must match

- public messages and documented statuses;
- named state, security, reliability, performance, event, RPC, architecture, graph, or governance decisions owned by this course;
- canonical bytes when signatures, digests, wire compatibility, or cross-language identity depends on them;
- accepted, rejected, and review-required release classifications;
- shared negative vectors and evidence boundaries.
- the Course 1 outcome: A frozen API 1.1 contract, operation ledger, schema fixtures, security decisions, workflow description, compatibility policy, and provider-neutral behavioral scenarios.

## What may differ

FastAPI and Fastify route declarations, validation errors, and OpenAPI generation differ; compare the emitted HTTP contract rather than class names.

## Reading implementation examples

For each example:

1. name the invariant before reading code;
2. identify the owner and state boundary;
3. find the negative test;
4. find cleanup and failure behavior;
5. compare the second track only after you can explain the first;
6. never infer a protocol rule from one framework default.
