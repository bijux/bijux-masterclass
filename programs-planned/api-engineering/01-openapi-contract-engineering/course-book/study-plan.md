# Two-Week Study Plan — OpenAPI Contract Engineering

## Rhythm

Course 1 uses ten teaching days over two weeks. Orientation freezes the incoming boundary before Day 1; each day moves from the specify the public promise model to transfer problems, a controlled experiment, and an evidence defense. The middle weekend is for repairing failed checkpoints, not adding features.

| Day | Module | Required result |
|---:|---|---|
| 1 | [HTTP and OpenAPI Foundations](module-01-http-openapi-foundations/index.md) | Establish health and project operations as raw messages, OpenAPI operations, and equivalent provider behavior. |
| 2 | [Operations, Parameters, and Messages](module-02-operations-parameters-messages/index.md) | Complete project and dataset messages, including pagination inputs, creation responses, and problem representations. |
| 3 | [JSON Schema Contract Modeling](module-03-json-schema-contract-modeling/index.md) | Define precise project, dataset, run, artifact, and problem schemas with a shared valid/invalid fixture corpus. |
| 4 | [References and Multi-Document Architecture](module-04-references-multi-document-architecture/index.md) | Split the contract into owned documents, resolve every reference offline, and produce deterministic bundles. |
| 5 | [Production HTTP API Design](module-05-production-http-api-design/index.md) | Add the analysis-run workflow, idempotency key, status resource, ETags, cancellation, and Problem Details. |
| 6 | [Contract-First and Code-First Runtimes](module-06-contract-first-code-first-runtime/index.md) | Map every operation to both providers and compare generated observations with the canonical contract. |
| 7 | [Mocks, Clients, and Contract Testing](module-07-mocking-clients-contract-testing/index.md) | Build the consumer and contract-test ladder against the mock and both real providers. |
| 8 | [Security in the Public Contract](module-08-security-authentication-authorization/index.md) | Describe API-key and OAuth-style schemes, scopes, anonymous overrides, and documented security failures. |
| 9 | [Evolution, Compatibility, and Audience Views](module-09-evolution-compatibility-overlays-ci/index.md) | Create compatible and rejected release candidates, compatibility gates, and public/partner audience views. |
| 10 | [OpenAPI 3.2, Streaming, Webhooks, and Workflows](module-10-openapi-32-workflows-advanced/index.md) | Publish the OpenAPI 3.2 frontier, streaming and webhook contracts, links, and an Arazzo workflow. |

## Suggested day

```text
08:30  retrieval practice and checkpoint repair
09:00  chapter reading and diagram reconstruction
11:00  worked examples and standards review
13:00  primary-track implementation reading
15:00  exercises before answers
17:00  controlled lab
19:30  evidence package and checkpoint defense
```

The two-week schedule is subordinate to evidence. If the specify the public promise argument becomes unclear, stop at the last green checkpoint, reduce the counterexample, and resume only after the owning mechanism is understood.

## Weekend synthesis

At the Week 1 boundary, reconstruct how Modules 1–5 change the platform while preserving this incoming state: Basic programming ability, command-line familiarity, and no assumed OpenAPI experience. Rerun those checkpoints and postpone every feature that does not serve the Course 1 responsibility.

## Recovery route

When a checkpoint fails:

1. isolate the first broken invariant;
2. restore the predecessor baseline if necessary;
3. reduce the failing case;
4. repair the owning mechanism;
5. retain the case as a regression;
6. update your explanation before continuing.
