# Capstone — OpenAPI Contract Engineering

## Cumulative system

Course 1 continues the Analysis Runs Platform at the point where the previous course stopped. Its capstone exists to specify the public promise while preserving the same projects, datasets, runs, artifacts, identities, and user journeys.

## Inherited state

Basic programming ability, command-line familiarity, and no assumed OpenAPI experience.

The inherited boundary is read-only: Basic programming ability, command-line familiarity, and no assumed OpenAPI experience. A difficult implementation is not permission to rewrite predecessor contracts, migrations, profiles, or evidence; the current course must solve the problem at its own owning layer.

## Course additions

- a canonical multi-document OpenAPI description;
- precise JSON Schema models and examples;
- Python and TypeScript provider parity;
- generated and authored consumer evidence;
- compatibility, security, Overlay, and Arazzo artifacts;

## Increment map

| Module | Mechanism | Cumulative result |
|---:|---|---|
| 1 | HTTP and OpenAPI Foundations | Establish health and project operations as raw messages, OpenAPI operations, and equivalent provider behavior. |
| 2 | Operations, Parameters, and Messages | Complete project and dataset messages, including pagination inputs, creation responses, and problem representations. |
| 3 | JSON Schema Contract Modeling | Define precise project, dataset, run, artifact, and problem schemas with a shared valid/invalid fixture corpus. |
| 4 | References and Multi-Document Architecture | Split the contract into owned documents, resolve every reference offline, and produce deterministic bundles. |
| 5 | Production HTTP API Design | Add the analysis-run workflow, idempotency key, status resource, ETags, cancellation, and Problem Details. |
| 6 | Contract-First and Code-First Runtimes | Map every operation to both providers and compare generated observations with the canonical contract. |
| 7 | Mocks, Clients, and Contract Testing | Build the consumer and contract-test ladder against the mock and both real providers. |
| 8 | Security in the Public Contract | Describe API-key and OAuth-style schemes, scopes, anonymous overrides, and documented security failures. |
| 9 | Evolution, Compatibility, and Audience Views | Create compatible and rejected release candidates, compatibility gates, and public/partner audience views. |
| 10 | OpenAPI 3.2, Streaming, Webhooks, and Workflows | Publish the OpenAPI 3.2 frontier, streaming and webhook contracts, links, and an Arazzo workflow. |

## Implementation route

Build the complete Course 1 increment in one primary track. Use the second track only after the chapter model is clear, then run shared vectors to test whether **specify the public promise** survives an idiomatic implementation in another runtime.

## Final state

A frozen API 1.1 contract, operation ledger, schema fixtures, security decisions, workflow description, compatibility policy, and provider-neutral behavioral scenarios.

## Handoff discipline

The successor receives only the settled result: A frozen API 1.1 contract, operation ledger, schema fixtures, security decisions, workflow description, compatibility policy, and provider-neutral behavioral scenarios. Local caches, secrets, ad-hoc reports, and environment-specific artifacts remain outside the handoff.
