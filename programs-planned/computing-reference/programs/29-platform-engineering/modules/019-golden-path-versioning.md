# Golden-Path Versioning

## One-Page Review

### Governing question

How should a platform evolve a supported golden path across interfaces, templates, runtimes, policies, providers, and consumer-owned projects without turning every improvement into an uncontrolled rollout or every compatibility promise into permanent stagnation?

### Essential definitions

- A **golden path** is a supported end-to-end journey whose interoperable defaults, capabilities, evidence, documentation, and escape routes make a common task reliably easier.
- A **release** is an immutable identified set of path contracts and tested component versions offered with stated support and migration terms.
- A **compatibility contract** defines which existing consumers, data, automation, and behavior continue to work under a change.
- **version skew** is the supported difference among simultaneously interacting client, API, controller, template, runtime, policy, plugin, and provider versions.
- A **stability channel** states change expectations such as experimental, preview, and stable; it is not a quality score or a substitute for support dates.
- A **migration** is a governed transition of consumer state or behavior from one supported contract to another, with preview, verification, recovery, and ownership.
- **deprecation** is advance notice that a supported surface is scheduled to change or be removed; **removal** is the later enforcement event.
- A **consumer inventory** records which projects and operations depend on which path contracts and versions, without assuming generated descendants remain unchanged.

### Central model, mechanism, or theorem

Model golden-path release $G_v=(J,C,I,D,S,U,M,E)$: journey contract $J$, capability/interface versions $C$, implementation bundle $I$, dependency and skew constraints $D$, stability/support policy $S$, upgrade channel $U$, migration/deprecation plan $M$, and verification evidence $E$. Compatibility must be evaluated across source, wire, semantic, operational, data, security, workflow, and evidence dimensions. A higher version means later under a declared scheme; it does not prove safer, compatible, or appropriate for a given consumer.

### Critical invariants

- Every release and referenced component revision is immutable; mutable aliases resolve to an auditable immutable identity.
- Version meaning is defined per surface; semantic versioning is used only where a precise public API and its compatibility rules are declared.
- Stable consumers are not silently moved to preview behavior or forced across an incompatible boundary.
- Compatibility tests include old clients with new servers, stored resources, generated projects, policy, workflows, and observable outcomes.
- Inventory, ownership, support windows, exceptions, and migration evidence precede removal.
- Automated updates produce reviewable plans and preserve consumer-owned changes; conflicts stop rather than overwrite.
- Security or safety urgency may compress a window, but authority, impact, evidence, communication, and compensating support remain explicit.
- Rollback claims account for data, external effects, schema conversion, credentials, and provider irreversibility—not only binary deployment.

### Common failures

Using one version for the entire platform; treating a calendar build as a compatibility promise; moving a tag; calling a behavioral break a patch; adding a response enum without testing exhaustive clients; changing defaults in place; supporting every combination; auto-updating consumer repositories without review; deprecating from download counts alone; removing before locating dependents; promising rollback after irreversible migration; keeping an insecure release indefinitely; and measuring “latest adoption” while ignoring failed migrations and coerced upgrades.

### Compact example

Golden path release 6 pins API `v1`, controller `4.3`, CLI `3.8`, template `2.4`, policy bundle `2026-08-15`, and runtime profile `python-3.14`. The path supports projects generated by template releases 2.2–2.4 and CLI 3.7–3.8. An update service inventories six projects: one is current, two accept an automatic reviewable change, two require owner review because of local customization, and one is outside support. Release evidence exercises old clients, stored resources, generation/update fixtures, first deployment, rollback boundaries, accessibility, and security. Removal of template 2.1 waits for the unsupported project to migrate or accept a governed exception.

## Governing Question

Which contracts are changing, who depends on them, what does the version promise, and how can each consumer move at a safe pace while the platform retires unsustainable or unsafe combinations?

“Version the golden path” sounds like assigning one number. In practice, a path composes API resources, controller behavior, CLI, portal, templates, libraries, runtime, policy, documentation, providers, and consumer code. These surfaces release and persist differently. A useful path release is therefore a tested compatibility bill of materials and support contract, not a claim that all components share one version.

Versioning is communication backed by evidence. Numbers, dates, channels, and labels acquire meaning only through declared compatibility, immutability, support, migration, and enforcement policies.

## Why This Matters

Platform teams need to improve defaults, close vulnerabilities, replace providers, change policies, retire runtimes, and learn from incidents. Consumers need stable automation, predictable maintenance, control over product changes, and time to validate migrations. Without a coherent version model, the platform either breaks teams continuously or freezes obsolete paths indefinitely.

Semantic Versioning 2.0.0 defines `MAJOR.MINOR.PATCH` meaning relative to a declared public API and requires released contents to remain unchanged. This is useful for libraries and bounded contracts. It is not automatically appropriate for a multi-component service, a calendar-versioned policy snapshot, a provider, or an entire user journey. Even SemVer cannot decide whether a semantic behavior change violates reasonable expectations; the platform must define and test its public contract.

Google AIP-180 explicitly distinguishes source, wire, and semantic compatibility and warns about apparently additive changes such as new response enum values or new defaults. AIP-185 demonstrates major API versions and stability channels with coexistence and deprecation. These are reference policies, not universal timelines.

Kubernetes' current deprecation policy illustrates explicit stability levels, round-trip requirements, and minimum lifetimes. Backstage's current policy illustrates another important idea: an umbrella release can be a verified collection of independently versioned packages, with defined skew. A golden-path release can use the same composition principle without inheriting either project's exact rules.

Copier's stable update documentation shows why template versions and recorded lineage matter when generated projects evolve independently. An update computes against old template, new template, and local changes; conflicts require review. The platform cannot infer safe synchronization merely from the original template tag.

## Core Exposition

### Version contracts, not organizational activity

List every consumer-visible contract in the journey: resource schemas, operations, error codes, CLI flags and output, portal workflows, template inputs and ownership, generated files, SDKs, runtime profiles, policy decisions, events, documentation, support, and outcome evidence. Also list implementation dependencies that create skew constraints: controllers, plugins, providers, build images, admission policies, and storage versions.

Decide which changes consumers can observe. A controller refactor with identical behavior may need a deployment revision but no consumer version. A default exposure change is semantically breaking even if no field changes. A new required manual approval breaks workflow automation. Version boundaries follow contracts, not repositories or team ownership.

Do not expose every implementation version. Publish enough identity for reproducibility, support, security, and compatibility while keeping replaceable internals behind stable capabilities.

### Model a golden-path release

Represent release $v$ as

$$
G_v=(J,C,I,D,S,U,M,E),
$$

where $J$ is the end-to-end journey contract, $C$ the capability and interface version set, $I$ an immutable implementation bill of materials, $D$ dependency and skew constraints, $S$ stability and support policy, $U$ update distribution, $M$ migration and deprecation plan, and $E$ verification evidence.

The release manifest identifies immutable digests or revisions, not only mutable tags. It states supported clients, servers, resource versions, templates, runtimes, providers, and policies; known incompatibilities; security posture; rollout state; owner; dates; documentation; and evidence.

An umbrella release can simplify selection by publishing one tested combination. Components still retain their own identities and compatibility policies. A consumer should be able to answer both “which path release am I on?” and “which exact contracts and components produced this outcome?”

### Choose a version scheme deliberately

Use SemVer for a bounded artifact with a precise public API: incompatible changes increment major, backward-compatible functionality minor, and backward-compatible fixes patch. Declare what the public API includes—types, behavior, errors, performance bounds, configuration, output, or only a subset. Version `0.y.z` conveys lower stability under the specification and needs additional support policy.

Use major-only service versions when compatible improvements deploy in place and only incompatible interfaces coexist. Use calendar versions when chronology and support windows matter more than compatibility inference; declare whether the date is build, publication, or contract snapshot. Use immutable revisions or digests for exact implementation identity. Use named channels for stability expectations. Do not ask one identifier to carry all meanings.

Release aliases such as `stable` or `current` may move, but resolution must be recorded. Immutable tags and artifacts never move. Pre-release identifiers do not become stable merely through adoption.

### Analyze compatibility across dimensions

**Source compatibility** asks whether existing consumer code still builds against new libraries or generated clients. **Wire compatibility** asks whether old and new participants serialize, transmit, and interpret messages safely. **Semantic compatibility** asks whether reasonable observable behavior and meaning remain intact.

**Operational compatibility** covers latency, capacity, ordering, retry, error, availability, and control-plane behavior. **Data compatibility** covers stored objects, schema conversion, retention, and rollback. **Security compatibility** covers identity, permissions, trust roots, algorithms, secrets, audit, and threat assumptions.

**Workflow compatibility** covers steps, required decisions, automation, approvals, and recovery. **Evidence compatibility** asks whether success, status, telemetry, and compliance claims retain meaning. A green build proves only a fraction of these dimensions.

Classify each proposed change. Adding an optional request field with old default may be compatible. Adding a response enum can break exhaustive clients. Increasing identifier length can overflow consumer storage. Tightening policy can reject formerly valid intent. Changing “ready” evidence can break dashboards even when bytes match.

### Define stability channels and graduation

An experimental channel optimizes learning and can disappear; restrict consequence, data, and support accordingly. Preview or beta offers broader evaluation with a stated time bound and migration expectation. Stable carries explicit compatibility and support commitments. Critical or long-term support can be separate where the organization can actually sustain it.

State allowed change, data use, availability, support, security, upgrade, and removal rules for every channel. A stable label without an owner and funded support window is misleading. A preview that hosts irreplaceable production state has acquired obligations regardless of its label.

Graduation requires evidence: defined consumer job, stable ownership, contract clarity, security review, operational objectives, migration path, documentation, accessibility, support readiness, and representative adoption. High usage alone does not prove maturity.

### Publish and test a skew matrix

List supported combinations rather than “latest works.” Include CLI/SDK versus API, API versus controller, served versus storage resource version, frontend versus backend plugin, template lineage versus updater, runtime versus build image, policy bundle versus resource schema, and provider API versus adapter.

Choose a bounded window. Test oldest supported consumer with newest server, newest consumer with oldest supported server when promised, every storage conversion path, upgrade order, rollback or forward recovery, mixed-version rolling deployment, and concurrent channels. Reject unsupported combinations early with actionable diagnostics.

Combinatorial coverage grows rapidly. Select combinations by contract boundaries and risk, use pairwise or model-based sampling for lower-risk interactions, and fully test required upgrade paths. Publish what is untested and unsupported.

### Maintain a consumer inventory

Record path release, component versions, template lineage, runtime, resource versions, policy snapshot, owner, environment, risk, update channel, exceptions, and last verified outcome. Discover from authoritative APIs, repositories, artifact provenance, and runtime evidence; do not rely on voluntary surveys alone.

Inventory is uncertain. A project generated from template 2.2 can contain extensive local changes. A repository can be archived while a deployed artifact remains live. Show source and freshness and let owners correct classifications.

### Make upgrades reviewable and observable

An update plan identifies current and target releases, exact changes, compatibility findings, consumer-owned conflicts, policy effects, cost, data transformations, order, downtime, verification, recovery, and point of irreversibility. Bind execution to the reviewed source and target identities.

Use pull requests for project changes when repository ownership and tests are central. Use declarative reconciliation for managed resources. Use dependency updates for libraries. Use service-side rollout for compatible implementation changes. Use explicit migration operations for data or identity transitions. One golden-path update can coordinate several mechanisms without pretending they are atomic.

Progressive delivery begins with internal fixtures, test consumers, opt-in cohorts, low-risk environments, and representative production cohorts. Observe task outcomes and negative evidence. Pause automatically on defined harm; preserve an owner decision for ambiguous trade-offs.

Do not force “latest” when a supported older release meets the consumer's needs. Provide a maintenance route and a planned support boundary. Exceptions name owner, risk, compensating controls, expiry, and migration trigger.

### Treat migration as a product journey

Provide discovery, assessment, preview, prerequisites, automated transformations, manual decisions, execution, status, validation, rollback or forward recovery, completion evidence, and support. Migration documentation alone is not a migration capability.

Preserve consumer-owned changes. Generated updates compute old baseline, new baseline, and local evolution; conflicts stop for review. Schema migrations maintain backups and invariants. Resource conversion preserves round trips across served versions when promised. Credential changes coordinate overlap and revocation.

Migrate behavior as well as bytes. A renamed field with different default, new approval, changed error code, or stricter readiness predicate may require consumer code and operational changes even when data conversion succeeds.

### Deprecate before removal

Deprecation states exact surface, affected versions, reason, safer or supported replacement, migration path, announcement date, removal criteria and earliest date, owner, support, telemetry, and exception process. Emit signals in schemas, build warnings, CLI, portal, docs, and direct owner communication without overwhelming consumers.

Use inventory and observed use, but do not equate absence of telemetry with absence of dependency. Sampling, privacy, offline tools, and uninstrumented clients create blind spots. Confirm high-consequence consumers directly.

Before removal, prove the successor works, supported dependents migrated or received governed exceptions, stored data is readable, rollback/forward plan is current, documentation redirects exist, support is staffed, and monitoring detects harm. Retain historical contracts and provenance where needed.

### Handle urgent security and safety changes

A vulnerability or unsafe behavior can make continued compatibility more harmful than a break. Invoke a documented emergency policy: decision authority, severity, affected inventory, exploit or harm evidence, safe disclosure, remediation, deadline, temporary controls, update mechanism, verification, and support.

Do not disguise the break as compatible. State which promise is overridden and why. Provide the narrowest viable change, test old and new paths, prioritize high-risk consumers, and record exceptions. An emergency is not permission to skip audit or ownership.

Security fixes may require revoking credentials, trust roots, algorithms, images, or provider access. Rollback to the vulnerable state may be forbidden. Forward recovery and compensating controls must be designed in advance.

### Define rollback honestly

Binary rollback is safe only if old code can understand new data, policies, resource versions, and external state. Expand/contract database changes, dual-read/write transitions, served-version conversion, compatible events, and credential overlap can create a rollback window.

Identify irreversible steps: destructive data rewrite, provider replacement, resource deletion, externally consumed event, trust revocation, billing change, or consumer action. Snapshot does not prove restorable recovery. Test restoration and application invariants.

When rollback is unsafe, use forward fix, pause, isolation, traffic shift, compatibility adapter, or restore into a new resource. Feedback must not offer a rollback button unsupported by the evidence.

### Measure versioning outcomes

Track supported-version distribution, inventory coverage and freshness, update availability, migration start and completion, conflict rate, time in each stage, failed and rolled-forward migrations, exception age, deprecation reach, removal incidents, security exposure, task success before/after, consumer satisfaction, support load, and platform maintenance cost.

Latest-version percentage is not a goal by itself. Rapid adoption can reflect coercion; slow adoption can reveal low value, risk, poor tooling, or legitimate stability. Evaluate whether consumers retain safe independent delivery and whether the platform can sustain its promised support matrix.

## Definitions and Notation

$G_v=(J,C,I,D,S,U,M,E)$ models golden-path release $v$ through journey, contracts, implementation bundle, dependencies/skew, stability/support, update channel, migration/deprecation, and evidence.

Let compatibility vector be $\kappa=(\kappa_s,\kappa_w,\kappa_m,\kappa_o,\kappa_d,\kappa_{sec},\kappa_f,\kappa_e)$ for source, wire, semantic, operational, data, security, workflow, and evidence compatibility. Overall compatibility is not proven by one passing component.

Let supported combination set be $\Omega_v$. A deployed tuple outside $\Omega_v$ is unverified or unsupported even when it appears to work.

For consumer $p$, migration state $m_p\in\{\mathrm{unassessed},\mathrm{planned},\mathrm{running},\mathrm{blocked},\mathrm{verified},\mathrm{excepted}\}$. Download or update initiation does not imply verified migration.

## Mechanisms, Invariants, or Proof Structure

Use a release lifecycle: inventory contracts and consumers; define schemes and channels; classify compatibility; assemble immutable manifest; define skew; test old/new and migrations; publish evidence; roll out progressively; observe; prepare reviewable updates; support exceptions; announce deprecation; migrate; prove removal readiness; remove; retain provenance; evaluate outcomes.

The immutability invariant preserves reproducibility. The meaning invariant binds numbers and channels to declared promises. The compatibility invariant spans behavior and data, not syntax alone. The coexistence invariant gives stable consumers a transition window. The ownership invariant prevents silent overwrite. The removal invariant requires inventory and successor evidence.

Adversarial review includes moved tag; compromised release manifest; dependency substitution; old client drops new response field; new enum crashes consumer; default changes exposure; rollback reads incompatible data; policy bundle rejects emergency operation; provider removes API early; project update overwrites local security control; telemetry misses offline consumer; exception never expires; preview holds production data; and security fix forces unsafe downgrade.

## Alternatives and Trade-Offs

**Single umbrella version** simplifies selection and support discussion. It hides independent contracts and can imply compatibility not actually tested.

**Independent component versions** preserve precise ownership and cadence. Consumers face a complex compatibility graph.

**Semantic versioning** communicates compatibility relative to a public API. It requires judgment about public surface and semantic behavior and does not encode support dates.

**Calendar versioning** communicates chronology and helps support windows. It says little about compatibility unless policy adds meaning.

**Automatic latest updates** propagate fixes quickly. They reduce consumer control and amplify defects or local conflicts.

**Consumer-pinned versions** improve predictability. They accumulate security exposure and support burden without update automation and deadlines.

**Long coexistence** reduces migration pressure. It multiplies testing, operations, security, documentation, and provider cost.

**Short support windows** accelerate simplification. They transfer migration work and risk to consumers and can make the path unattractive.

## Failure Modes and Misconceptions

- **“The platform is version 6.”** Consumers need the composed contract and exact component identities behind that label.
- **“SemVer proves compatibility.”** It communicates a promise whose public API and evidence must be defined.
- **“Additive is always safe.”** New enums, defaults, fields, limits, latency, and policy can break reasonable consumers.
- **“Stable means no change.”** Stable means change under a published compatibility and support contract.
- **“Preview means no obligations.”** Production use, durable state, and encouraged adoption create real harm potential.
- **“Latest is best.”** Suitability depends on consumer needs, evidence, and supported risk.
- **“Generated projects can be synchronized.”** Local ownership and conflicts require review.
- **“No observed use means no users.”** Instrumentation and inventory have blind spots.
- **“Rollback is redeploying the old image.”** Data, effects, policy, and trust may prevent it.
- **“Deprecation warning equals migration.”** Consumers need a verified successor journey and time to complete it.

## Worked Examples

### Example 1

A platform calls every monthly bundle `2026.09`. The policy clarifies that the date means publication, not compatibility; an independent stability channel and manifest define supported transitions.

### Example 2

An API adds a response enum in a minor release. Compatibility tests find an exhaustive mobile client crash. The server gates emission until clients are updated and the contract documents open enum handling.

### Example 3

A template tag `2.4.0` is moved after release. Reproducibility fails. The registry rejects tag mutation and binds generations to commit and content digest.

### Example 4

CLI 3.8 works with API `v1`, but portal frontend 6 requires backend 6 or later. The skew matrix and rollout deploy backend before frontend and reject an unsupported reverse order.

### Example 5

A stricter policy changes public exposure from warning to denial. The platform treats this as workflow and semantic impact, inventories affected resources, previews remediation, and stages enforcement rather than calling it a patch.

### Example 6

A generator update cleanly modifies two repositories but conflicts with consumer-owned CI in a third. It opens two pull requests and marks the third `review_required`; it never overwrites the conflict.

### Example 7

Runtime support ends while one critical service cannot migrate. The exception names owner, vulnerability controls, isolated build route, expiry, and funded migration; it does not silently enlarge the normal support matrix.

### Example 8

A database schema expands before new code and contracts only after all old readers retire. The release can roll application code back during the overlap, then records the contraction as irreversible.

### Example 9

Usage telemetry shows zero calls to a deprecated offline CLI feature. Direct inventory finds a quarterly disaster-recovery script. Removal waits for a tested replacement despite apparent zero use.

### Example 10

A compromised signing key forces emergency trust-root rotation. The platform communicates the compatibility break, distributes dual trust where safe, prioritizes exposed consumers, verifies new trust, revokes old trust, and forbids rollback to compromise.

## Answers to the Exercises

### Answer 1

Publish immutable path release identity with the journey's accepted intent, operation states, outcome evidence, API/resource versions, CLI/portal contract, template release and lineage rules, runtime profile, policy snapshot, controller/provider adapter, docs, and support. Pin implementation revisions and signatures. State oldest/newest supported combinations and upgrade order, stable/preview rules, dates, owner, objectives, known limits, and security status. Inventory projects and live resources by owner, risk, source freshness, and exception. Evidence covers old/new clients, storage conversion, generated updates with local changes, rolling deployment, first verified deployment, failure recovery, accessibility, security, and restoration. Offer reviewable updates and explicit migrations. Deprecation names successor and criteria; rollback identifies reversible and irreversible points. Completion means consumer and workload evidence pass, not that component installation finished.

### Answer 2

New response enum is wire-additive but can break source/semantic behavior in exhaustive clients. Tighter identifier length breaks input semantics and stored consumer assumptions. Default exposure change breaks semantic, security, workflow, and possibly operational behavior. Provider upgrade can preserve public semantics yet alter operational, data, error, and evidence compatibility; adapters and tests decide. Required approval breaks workflow and automation. Readiness-evidence change affects semantic, operational, and evidence consumers. Trust-root rotation breaks security and connection compatibility but may be necessary; overlap and inventory govern it. CLI flag removal breaks source-like script and workflow contracts and needs deprecation or a new incompatible surface. None can be classified only by changed bytes.

### Answer 3

First define promised skew and legal upgrade sequences, reducing the theoretical 48 tuples. Test each stable CLI against each served API it promises, oldest CLI/newest API, newest CLI/oldest API if promised, and machine-output/error fixtures. For every controller transition, test mixed old/new replicas against both served and storage versions, round-trip conversion, restart, status generation, and rollback/forward recovery. Pair each policy bundle with the resource schemas it can interpret and include allow, deny, warning-to-enforcement, and emergency cases. Cover each pairwise boundary, all production upgrade paths, highest-risk full combinations, and invalid tuples that must fail early. Publish the omitted combinations as unsupported; production telemetry and canaries supplement but do not replace the matrix.

### Answer 4

Freeze new profile adoption and build inventory from repositories, artifact provenance, runtime APIs, provider records, and owners; label uncertainty. Name the successor and test application, data, security, operational, cost, and regulatory equivalence. The regulated workload receives domain and compliance review rather than a generic deadline. The vulnerability invokes documented emergency authority, temporary isolation or patching, disclosure, and a risk-based compressed window. Consumer-owned templates get reviewable changes with conflict handling. Work backward from the provider deadline with assessment, rehearsal, migration, verification, and contingency dates. Exceptions name owner, controls, expiry, and escalation but cannot extend beyond a hard provider removal without an alternate implementation. Remove only after live and latent dependencies, restoration, docs, support, and audit evidence are reconciled.

### Answer 5

Treat device firmware, pump model, drug-library release, clinical policy, integration protocol, configuration distributor, and audit schema as separate versioned authorities composed into an approved deployment pathway. Patient orders and clinician decisions remain patient-specific clinical truth; the platform never converts them into a generic path version. Define compatibility by device capabilities, dose units and limits, library schema, policy jurisdiction, network protocol, display behavior, alarm semantics, data retention, and evidence. Use laboratory, simulation, clinical, security, accessibility, and biomedical-engineering gates before staged deployment. An urgent safety correction uses named clinical and safety authority, affected-device inventory, narrow remediation, downtime route, direct communication, and verification. Rollback may be unsafe after a corrected limit or firmware security revocation; forward recovery or device isolation may be required. Audit binds exact versions and approvals. Technical installation never proves clinical appropriateness for an individual patient.
