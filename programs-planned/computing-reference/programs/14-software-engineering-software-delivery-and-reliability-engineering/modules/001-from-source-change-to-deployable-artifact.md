# From Source Change to Deployable Artifact

## One-Page Review

### Governing question

How does an accepted source change become an immutable, identifiable, verified, provenance-bearing artifact that a deployment system can consume without rebuilding or guessing what it contains?

### Essential definitions

- A **source revision** is an immutable identity for a complete version-controlled source tree and associated change history—not a mutable branch name.
- A **build** is a controlled transformation from declared source, dependencies, tools, parameters, and environment into outputs plus evidence.
- A **build input** is anything able to influence outputs: source, generated inputs, dependencies, toolchains, configuration, locale/time, network responses, build platform, or nondeterminism.
- An **artifact** is an immutable build output intended for storage, verification, distribution, deployment, or use by another stage.
- A **deployable artifact** has a defined format, target/runtime contract, identity, integrity metadata, required evidence, and installation/startup expectations.
- A **digest** is a cryptographic hash of bytes or a defined content graph; it supports integrity and content identity but does not by itself establish origin, safety, authorization, or correctness.
- **provenance** is verifiable information connecting an artifact to its source, builder, build definition, parameters, dependencies, execution, and outputs.
- A **reproducible build** allows materially equivalent inputs to produce bit-for-bit identical outputs under a documented process; a **hermetic build** isolates the build from undeclared inputs. Neither property implies the other automatically.
- **promotion** advances the same immutable artifact and evidence through environments or release states; rebuilding creates a different candidate.
- A **release** is an authorized artifact/configuration set offered for use; **deployment** installs/activates it in an environment. Build, release, and deployment are distinct decisions.

### Central model, mechanism, or theorem

Model a build invocation as

\[
(A,E)=B(S,D,T,P,X),
\]

where source revision (S), resolved dependency graph (D), toolchain/builder identity (T), parameters/target (P), and declared execution context (X) produce artifact set (A) and evidence (E). For each artifact byte sequence (a), record content identity (h(a)) and bind evidence to that digest. A promotion gate checks

\[
digest(candidate)=digest(verified)=digest(promoted),
\]

plus policy/evidence validity. Source identity alone is insufficient: two builders or dependency resolutions can produce different bytes. A tag alone is insufficient: mutable names can point to different bytes.

### Critical invariants

- Identify exact source revision and dirty/untracked/generated inputs; never claim a local tree from its branch name alone.
- Resolve and record the full transitive dependency/toolchain/build-definition/target inputs that can affect bytes.
- Separate build-time nonsecret configuration from environment runtime configuration and secrets.
- Fail closed on missing, ambiguous, untrusted, expired, incompatible, or unverifiable inputs/evidence.
- Produce artifacts in a clean controlled context; prevent one build from contaminating another.
- Test/scan the exact artifact or input graph that will be promoted; do not rebuild after approval.
- Address artifacts by immutable digest and treat human tags/versions as metadata mappings.
- Publish artifact and required evidence atomically or make incomplete publication unselectable.
- Record provenance, logs, test results, vulnerability/license/SBOM evidence, signatures and approvals as distinct claims.
- Preserve rollback/retention and reproducibility/incident evidence without retaining secrets in artifacts or logs.

### Common failures

Common failures include building from a dirty workstation; resolving floating dependencies; downloading tools at build time without digest verification; embedding current time, path, locale or random ordering accidentally; testing source then packaging different bytes; rebuilding separately for staging and production; overwriting tags; treating checksums as signatures; treating signatures as safety; publishing an artifact before evidence; letting caches cross trust or target boundaries; injecting production secrets into images; assuming container means hermetic; trusting provenance generated by the untrusted build itself; and losing the source-to-runtime link during deployment.

### Compact example

Revision `r42` plus lockfile, compiler digest `c7`, target `linux-amd64`, build definition `b3`, and declared parameters produce package digest `sha256:a9…`. Tests, SBOM, scan and provenance refer to that digest. Staging and production pull `sha256:a9…`; environment-specific endpoint/credential values arrive separately at runtime. If production rebuilds `r42`, it has a new invocation and possibly new dependencies/bytes, so staging evidence does not automatically cover it.

## Governing Question

Which explicit transformations, identities, trust boundaries, and evidence are necessary to turn a source revision into a deployable artifact whose bytes and history remain stable through release and deployment?

“The commit passed CI” is not a complete delivery statement. A deployment consumes packages, images, archives, binaries, manifests, database migrations and configuration—not a conceptual commit. The engineering chain must establish which bytes were built, from which complete inputs, by which builder/process, for which target, with which evidence, and whether deployed bytes are those accepted bytes.

## Why This Matters

Source code can be correct while the shipped artifact is wrong. A packaging script can omit migrations, bundle development credentials, select the wrong architecture, use a compromised dependency, strip required metadata, or publish partial content. A deployment can select a mutable tag that no longer names the tested bytes. These failures occur at seams ignored by code-centric review.

Build infrastructure is privileged. It reads source and credentials, executes generators/compilers/install scripts, downloads dependencies, writes release artifacts, and often emits attestations or signatures. An attacker or configuration error in this chain can alter every downstream environment while leaving source unchanged.

A disciplined artifact chain improves more than security. It makes failures reproducible, rollback exact, audits answerable, cache use safer, incident scope discoverable, releases comparable, and environment promotion meaningful. The goal is not a long pipeline; it is a small, explicit trusted transformation with evidence consumers can verify.

## Prerequisites and Retrieval

Retrieve these concepts:

- version-control revision, tracked/untracked file, branch, tag and merge;
- direct/transitive dependency, version constraint, lockfile and checksum;
- compiler/interpreter, linker, package manager, target platform and ABI;
- process environment, filesystem, clock, locale, randomness, network and cache;
- cryptographic digest, signature, identity, authorization and trust root;
- test suite, static analysis, vulnerability scan and their evidence limits;
- artifact repository/registry, immutable storage and retention;
- runtime configuration, secret, deployment, release, rollback and promotion.

You should be able to explain why a commit ID does not identify downloaded dependencies, why a version tag can be mutable, and why a successful unit-test run on source does not prove that a later container contains the tested binary.

## Core Exposition

### Begin with an accepted source state

A developer’s directory is not automatically a reproducible source input. It may contain uncommitted tracked edits, untracked generated files, ignored configuration, submodule drift, case-collision behavior or symlink targets outside the tree. First define source acquisition: immutable revision, repository identity, submodules/vendor trees, large-file objects, generated-source policy and version-control metadata required by the build.

The change event and source state differ. A pull request describes intent and delta; a merge revision identifies an integrated tree. Testing a feature branch does not automatically cover the merge result when concurrent changes or merge resolution alter it. Merge queues/integration policies belong later, but the artifact must cite the exact integrated revision it consumed.

Source archives should have canonical inclusion rules and integrity identity. Decide whether timestamps, permissions, executable bits, symlinks and line endings are semantic. A content hash has meaning only relative to the serialization/content-graph definition.

### Model the complete input closure

Build functions often appear as `compile(source)`, while actual outputs depend on more:

- resolved direct and transitive packages, native libraries and system headers;
- compiler, linker, interpreter, package manager, plugins and generators;
- build scripts, container/base images and runner image;
- target triple, CPU features, ABI and feature flags;
- environment variables, locale, timezone, working path and user identity;
- filesystem enumeration order, parallel scheduling, random seeds and clock;
- downloaded schemas, code-generation services, license servers and network content;
- caches and previous output directories;
- VCS metadata used for version strings;
- credentials when they influence accessible content.

Classify each input as declared/pinned, declared/variable, intentionally nondeterministic, or accidental. Eliminate accidental inputs. Record variable parameters and acceptable values. Resolve mutable names to immutable identities before execution. A lockfile records a resolution but needs integrity and ecosystem semantics; SDRE-002 handles details.

Secrets should authorize fetching/signing/publishing, not alter application bytes unless that is an explicit exceptional product requirement. Never bake deployment credentials into a general artifact. Secret values must not enter provenance, logs, cache keys exposed to untrusted users, or debug bundles.

### Treat the pipeline as transformations with contracts

A common flow is:

1. receive trusted build request and immutable source identity;
2. acquire/verify source and declared build definition;
3. resolve/verify dependency and toolchain identities;
4. generate derived sources/resources;
5. compile/link/bundle;
6. run static checks and tests at appropriate representations;
7. package target artifact and metadata;
8. inspect/scan/test the packaged artifact;
9. compute digest, provenance and other attestations;
10. publish artifact and evidence atomically;
11. authorize release/promotion by digest;
12. deploy exact digest with separate environment configuration.

The actual graph can branch for targets, debug symbols, source maps, SBOMs or packages. Each node needs inputs, outputs, failure semantics, isolation, retry/idempotency, timeout, logs and ownership. A green orchestration status must not hide a skipped or unavailable required check.

Stage order can change conclusions. Scanning an unpackaged workspace may miss files added by packaging. Integration testing an artifact before signing is fine if signing changes only detached metadata; embedding a signature changes bytes and therefore digest/test binding. Define the final artifact boundary and ensure evidence refers to the correct identity.

### Define the artifact contract

An artifact is not “whatever the build folder contains.” Define:

- media/package format and canonical identity calculation;
- supported target OS/architecture/runtime/ABI and required capabilities;
- entrypoint, files, permissions, ownership and default nonsecret configuration;
- dependencies expected inside versus supplied by runtime;
- schema/migration, debug/source-map and license/documentation companions;
- install/start/health/uninstall behavior and resource assumptions;
- compatibility/version semantics and upgrade/downgrade policy;
- evidence relationships and repository namespace;
- retention, deprecation and deletion policy.

For an OCI image, for example, manifest, optional index, filesystem layers and configuration form a content-addressed graph. A multi-platform index can select distinct manifests by platform. The digest of the index differs from each platform-specific manifest; operators must know which identity a policy or deployment pins.

Archives, language packages, firmware, mobile apps, infrastructure modules and database bundles have different runtime contracts. Do not force every output into a container. “Deployable” means a declared consumer can validate and apply it, not that the artifact type is fashionable.

### Separate names from immutable identities

Version `1.4.0`, channel `stable`, image tag `release`, file name and repository path are human navigation metadata. They can be reassigned unless policy/storage prevents it. A digest identifies content bytes or a defined graph with negligible collision assumption; deploy and evidence policy should ultimately resolve to immutable identity.

Digests provide integrity comparison: expected bytes equal observed bytes under the algorithm/serialization. They do not prove who built bytes or whether bytes are trustworthy. A signature binds a signer/key identity to a statement, but consumer must verify identity, authority, key status, transparency/timestamp policy and statement meaning. A trusted signer can sign vulnerable output.

Promotion records should map a release/environment authorization to digest and evidence set without copying/rebuilding. If repository replication changes representation, prove semantic/content identity or create a traceable new artifact relationship.

### Distinguish evidence types

Evidence claims are orthogonal:

- **test report:** selected behaviors passed for named item/environment;
- **static-analysis report:** named rules found/did not find issues in analyzed inputs;
- **vulnerability scan:** database/policy at scan time matched findings against observed components;
- **SBOM:** component inventory according to generation scope/format;
- **provenance:** claimed source, dependencies, builder, definition, parameters and outputs;
- **signature/attestation:** an identity endorsed a specific statement;
- **reproducibility result:** independent rebuild matched expected bytes under stated inputs;
- **approval:** authorized actor accepted evidence/residual risk for a decision.

No artifact “has passed security” universally. Evidence expires or becomes stale as vulnerability data, keys, policies, dependencies, threats and runtime context change. Bind each claim to digest and record time/schema/tool/policy identity.

Provenance trust depends on how it is generated. Metadata written by the same untrusted script that could alter output is useful for debugging but weak against tampering. Stronger designs have a trusted control plane observe/record source, parameters, builder and output digests with isolation from tenant-controlled steps. SLSA expresses progressively stronger build provenance and isolation requirements; a level is a scoped supply-chain claim, not total software quality.

### Reproducibility and hermeticity solve different problems

A reproducible build yields bit-identical artifacts from materially equivalent inputs. It helps detect undeclared variation or tampering through independent rebuilds and enables artifact verification from source. To achieve it, normalize or eliminate timestamps, absolute paths, locale, random order, filesystem metadata, compression variation and nondeterministic tool behavior.

A hermetic build reads only declared inputs and writes controlled outputs, normally with network/time/environment access restricted. Hermeticity supports caching and reasoning but a hermetic build can be nondeterministic due to parallelism/randomness. A reproducible build can repeatedly fetch an undeclared mutable dependency that happens not to change. Aim for both when risk/economics justify, while documenting exceptions.

Repeatability means same team/setup can repeat a result; reproducibility often expects a meaningfully independent environment. Exact terminology varies by community, so define the claim and comparison procedure. Bit identity also does not prove correctness: a flawed build can be reproducibly flawed.

### Test what you ship and ship what you tested

Testing source-level units remains valuable, but artifact gates must validate packaging and runtime seams. Inspect contents/permissions, start the exact package/image, exercise entrypoint and health, verify target architecture, validate schemas/migrations, check nonroot/least privilege where relevant, and confirm debug/dev/test assets or credentials are absent.

Build once, then promote the digest. Rebuilding per environment lets dependency, compiler, timestamp or script behavior drift and invalidates previous artifact evidence. Runtime configuration supplies environment differences. When compilation genuinely requires environment-specific values, treat each output as a distinct artifact requiring its own evidence; do not call them the same release bytes.

Database migrations and infrastructure declarations may be separate artifacts ordered with application changes. Release manifest can bind a set of digests and compatibility constraints. Atomicity at the set level matters: application may require schema and policy versions together.

### Make caches accelerators, never authorities

Caches return prior outputs based on keys. A correct key represents every semantic input plus build-rule/toolchain/target identity. Missing feature flags, compiler version, environment or transitive dependencies produces false hits. Overbroad keys waste time but remain correct; under-specified keys return wrong artifacts.

Trust boundaries matter. Untrusted contributions must not populate cache entries later consumed by privileged release builds unless entries are independently content-verified and namespaced. Cache outputs should undergo the same artifact verification; a hit is not evidence that generating checks ran in the current context.

Record cache hit/miss/source for diagnosis, but provenance must describe effective inputs/output regardless of acceleration. Be able to bypass/clear caches and reproduce from cold state.

### Publish atomically and fail closed

Partial publication creates artifacts without evidence or aliases pointing to incomplete content. Upload content under digest first, verify readback, publish attestations/metadata, then atomically make a release/channel reference discoverable. If atomic transactions are unavailable, use staged namespaces and a final signed manifest that references complete immutable subjects.

Retries must be idempotent. Publishing identical bytes at same digest is safe; overwriting a version/tag is not. Conflicting content under an immutable version should fail and alert. Validate repository response and retention/replication behavior.

Failure states need evidence: source unavailable, dependency integrity mismatch, test failure, scanner unavailable, policy denial, attestation/signing failure, publication conflict. Do not collapse unavailable into pass. Preserve safe logs and invocation identity for replay/incident response.

### Maintain traceability into runtime

Deployment records should include artifact digest(s), release/config identity, target environment, deployment mechanism, actor/automation identity, time and outcome. Runtime exposes version/digest safely through inventory/telemetry so incidents can answer “where is this artifact running?” and “which source/build produced it?”

Rollback selects a prior known artifact and compatible configuration/data state; it is not `git revert` alone. Database/external side effects may be irreversible. Retain artifacts/evidence long enough for rollback, incident, audit and legal needs, with deletion governance and secret/privacy constraints.

### A small executable canonical-input model

This model creates a canonical manifest from source text and target, then shows that input ordering does not change a pedagogical checksum while a content change does.

<!-- bijux-verify: {"id":"sdre-001-canonical-input","mode":"run","language":"python","toolchain":"python3","expect":{"exit_code":0,"stdout":"manifest=linux-amd64|a.txt=alpha|b.txt=beta\ntoy_checksum=8a242f1a\norder_independent=true\nchange_detected=true\n","stderr":""}} -->
```python
def build_manifest(files, target):
    entries = []
    for path in sorted(files):
        entries.append(path + "=" + files[path])
    manifest = target + "|" + "|".join(entries)
    checksum = 1
    for character in manifest:
        checksum = (checksum * 257 + ord(character)) % 4294967291
    return f"{checksum:08x}", manifest

files = {"b.txt": "beta", "a.txt": "alpha"}
checksum, manifest = build_manifest(files, "linux-amd64")
reordered_checksum, _ = build_manifest(dict(reversed(list(files.items()))), "linux-amd64")
changed_checksum, _ = build_manifest({**files, "a.txt": "alpha!"}, "linux-amd64")

print("manifest=" + manifest)
print("toy_checksum=" + checksum)
print("order_independent=" + str(checksum == reordered_checksum).lower())
print("change_detected=" + str(checksum != changed_checksum).lower())
```

The run verifies one in-memory canonical string definition under Python 3. The checksum is deliberately non-cryptographic and must never identify or secure real artifacts. This is not a package format, secure build, signature, provenance system, collision protection, filesystem capture, trusted builder, or deployability test. Real formats require cryptographic digests and define their own canonical/content-graph semantics.

## Definitions and Notation

Let immutable source identity be (S), resolved dependencies (D), toolchain/builder (T), parameters/target (P), declared context (X), build function (B), artifacts (A), and evidence (E). Invocation identity (I) distinguishes executions even when outputs match. Cryptographic digest (h(a)) identifies artifact bytes under algorithm/format.

Let release record (R=(A,E,C,Q)) bind artifact digests, evidence, compatibility constraints (C), and authorization (Q). Deployment (Deploy(R,Env,Config)) consumes an authorized release plus environment configuration. `tag -> digest` is a mutable or governed mapping; equality of tags does not imply equality of content unless repository policy proves immutability.

Trusted computing base (TCB) contains components/people whose compromise can invalidate the claim. Provenance completeness, authenticity and accuracy are separate properties.

## Mechanisms, Invariants, or Proof Structure

1. Resolve exact integrated source revision and reject/record dirty external inputs.
2. Define build graph, artifact contract, target matrix and required evidence.
3. Enumerate/pin/verify source, dependency, toolchain, builder, parameter and context inputs.
4. Isolate invocation, restrict network/secrets, and namespace caches by complete semantic/trust key.
5. Transform through explicit stages with fail-closed checks and preserved logs.
6. Package final deployable boundary; inspect and execute the exact artifact where applicable.
7. Compute immutable digest and bind tests, scans, SBOM, provenance, signatures and approvals to it.
8. Publish content/evidence atomically, then create governed human-readable release mappings.
9. Promote the same digest across environments; supply secrets/configuration separately.
10. Verify policy, identity, integrity, compatibility and evidence freshness before deployment.
11. Record runtime deployment inventory and preserve rollback/incident traceability.
12. Reproduce/replay independently when required; retire artifacts/evidence under governed retention.

Review each edge for **completeness** (all influencing inputs), **integrity** (bytes/statements unaltered), **authenticity** (claimant identity/authority), **isolation** (untrusted influence constrained), **correspondence** (evidence binds exact subject), and **availability** (required evidence is present, not skipped).

## Alternatives and Trade-Offs

**Local builds** give fast developer feedback and debugging access; workstation drift/credentials weaken release trust. **Central builders** standardize/isolate and attest; they become privileged shared infrastructure and availability bottlenecks.

**Source distribution** lets consumers build/inspect for their platform; reproducibility/toolchain burden shifts downstream. **Binary artifacts** accelerate consistent deployment; producer/build chain must be trusted and supported.

**Container images** bundle filesystem/configuration portably across compatible runtimes; they do not solve kernel, architecture, secret, provenance or orchestration concerns. **Native/language packages** integrate ecosystems efficiently with different dependency/runtime semantics.

**Build per environment** can embed environment specialization; it multiplies candidates/evidence. **Build once/promote** preserves identity and confidence; runtime configuration contract must be designed.

**Hermetic offline resolution** strengthens completeness/isolation; mirroring and update workflows cost effort. **Networked builds** are flexible/current; mutable responses and compromise undermine replay.

**Reproducible builds** support independent verification; normalization/tool discipline costs engineering and may conflict with intentional metadata. **Signed provenance** provides origin/build claims without byte reproducibility; trusted builder remains in TCB. Combine based on risk.

**Aggressive caching** shortens feedback; key/trust errors threaten correctness. **Cold builds** are simpler evidence but expensive. Verify caches and schedule cold/reproducibility checks.

## Failure Modes and Misconceptions

- **“The commit is the artifact.”** It omits dependencies, tools, target, context and package bytes.
- **“CI built it, so it is trusted.”** Builder identity, isolation and provenance guarantees matter.
- **“Container builds are hermetic.”** Build instructions can read network, clock, host and mutable bases.
- **“The lockfile makes it reproducible.”** Toolchain, context and nondeterminism remain.
- **“Same version means same bytes.”** Tags/versions can be remapped or rebuilt.
- **“Same digest means safe.”** Integrity is not origin, correctness or authorization.
- **“Signed means secure.”** It means a verified identity signed a statement under policy.
- **“SBOM proves contents.”** Generation completeness/accuracy and runtime composition matter.
- **“Source tests cover the image.”** Packaging/runtime differences need artifact tests.
- **“Rebuild for production is cleaner.”** It creates a new unverified candidate.
- **“Cache hit means checks passed.”** It means a key returned prior output under cache trust.
- **“Scan unavailable can be ignored.”** Unavailable is an explicit policy state, not pass.
- **“Provenance is a log.”** It is a structured verifiable claim with trust semantics.
- **“Rollback is previous commit.”** Deployable bytes, config, schema and effects determine rollback.
- **“Reproducible means correct.”** Defects can reproduce exactly.

## Worked Examples

### Example 1

**Situation.** Developer builds tag `main` with an untracked `config.py` imported by packaging.

**Reasoning.** Revision does not contain actual input; another builder cannot reconstruct artifact. Reject dirty/untracked influence or declare/hash it as governed input. Tag must resolve to revision.

**Conclusion.** Source identity requires the complete consumed source state.

### Example 2

**Situation.** Dependency constraint `lib>=2` resolves to 2.4 in tests and 2.5 during release.

**Reasoning.** Same source, different graph and behavior. Resolve once, lock/hash, record repository and verify integrity; rebuilding after registry mutation creates another candidate.

**Conclusion.** Dependency resolution is part of artifact identity and evidence.

### Example 3

**Situation.** Generated client code changes although schema is unchanged.

**Reasoning.** Generator version/options/runtime or ordering changed. Pin generator/toolchain and normalize output; store schema and generator identities in provenance. Review whether generated source is committed or produced in build under one authority.

**Conclusion.** Generators are compilers and belong in the trusted input closure.

### Example 4

**Situation.** Two clean builds differ only in archive timestamps and file ordering.

**Reasoning.** Functionality may match, but bit identity/rebuild verification fails. Set canonical timestamps/order/metadata and deterministic compressor, or document intentional fields excluded by format-specific comparison.

**Conclusion.** Reproducibility requires canonicalization of nonsemantic variation.

### Example 5

**Situation.** Staging image is rebuilt with production endpoint and tagged `prod`.

**Reasoning.** Production bytes lack staging evidence and may embed secrets/environment coupling. Promote staging digest; inject validated endpoint/credential separately. If specialization is unavoidable, test/attest distinct artifact.

**Conclusion.** Build once makes promotion a meaningful evidence statement.

### Example 6

**Situation.** Image `app:1.2` was scanned yesterday; tag now points elsewhere.

**Reasoning.** Scan binds old digest, not mutable name. Repository/policy should prevent overwrite; deployment resolves/pins digest and verifies evidence subject.

**Conclusion.** Human names select candidates; immutable identity binds evidence.

### Example 7

**Situation.** Tests pass on compiled binary, then packaging strips a required certificate bundle.

**Reasoning.** Source/binary tests miss final package. Inspect contents and run smoke/integration/recovery checks against packaged artifact in representative runtime.

**Conclusion.** Test the final deployable boundary and its seams.

### Example 8

**Situation.** Untrusted pull request populates release cache with altered generated output.

**Reasoning.** Under-specified key/trust namespace lets privileged build consume attacker output. Separate trust domains, content-verify entries, include all inputs and rerun required artifact checks.

**Conclusion.** Caches are supply-chain inputs, not transparent speedups.

### Example 9

**Situation.** Multi-platform tag contains amd64 and arm64 manifests; only amd64 was tested.

**Reasoning.** Index digest references both, but evidence scope is one subject/target. Build/test/scan each platform and bind an authorized release set; validate runtime selects expected manifest.

**Conclusion.** A multi-target release is a graph of distinct artifacts/evidence.

### Example 10

**Situation.** Firmware artifact controls an implantable cardiac device.

**Reasoning.** Exact source/toolchain/hardware target, generated code, compiler qualification, reproducibility, signing, anti-rollback policy, update interruption, device identity, SBOM, vulnerabilities, tests and traceability require controlled evidence. Artifact authenticity does not validate clinical algorithm or safe deployment.

**Conclusion.** Named cardiologists and biomedical/safety engineers, firmware/hardware/compiler experts, human-factors/accessibility specialists, cybersecurity/privacy experts, manufacturing/operations, quality/regulatory representatives and independent assessors must approve requirements, build system, evidence, residual risk and release. No digest, signature or green pipeline authorizes clinical use.

### Exercise 5

## Answers to the Exercises

### Answer 1

Merge event resolves to immutable source revision and repository; checkout verifies clean complete tree/submodules. Build definition, lockfile and resolved dependency/toolchain/base-image digests plus target/parameters identify inputs. Isolated builder invocation has identity and logs. Generation/compile/test outputs refer to invocation/input graph. Packaging creates OCI layers/config/manifest and final platform manifest digest; inspect/start/test exact image. Generate SBOM, scan, provenance and signatures/attestations whose subject is digest; record tools/policies/times. Publish content and evidence before immutable version/channel mapping. Release authorization binds digest/evidence/compatibility. Deployment resolves digest, verifies policy, injects separate config/secrets and records environment/outcome. Runtime inventory exposes digest. Rollback references prior compatible digest/config/data plan.

### Answer 2

First verify comparison is same artifact format/target and hash bytes; preserve both invocations. Compare source tree including dirty/submodule/LFS/generated inputs; dependency resolutions/checksums/repositories; compiler/linker/package-manager/generator/base/runner versions; parameters/features/target/ABI; environment, locale/timezone/path/user; network responses; timestamps, file permissions/order, compression, random seeds, parallelism; cache hits/keys; VCS-derived metadata and embedded signatures. Diff unpacked structures and binary metadata to localize first divergent stage. Rebuild cold in controlled environment, then vary one suspected input. Classify intentional versus accidental variation, pin/normalize/remove cause, update build definition/provenance, and add reproducibility regression. Matching after normalization supports byte claim; it does not prove artifact correctness.

### Answer 3

Workspace tests do not bind packaged artifact; add final artifact inspection/execution and bind reports to digest. Per-environment rebuilds create distinct candidates; build once and inject environment config/secrets, or treat specialization as separately tested artifacts. Signing a mutable tag authenticates ambiguous mapping; sign/attest digest-bound statements and verify signer authority plus repository immutability. Shared PR cache crosses trust: namespace by trust, include complete semantic key, prevent untrusted writes to privileged cache or independently verify content, and run required checks on release subject. Add trusted provenance observation, atomic publish, fail-closed unavailable checks, cold builds and runtime digest inventory. Each defect is independent; a signature does not repair cache/input or testing gaps.

### Answer 4

Source distribution maximizes inspectability/portability but shifts toolchain/dependency/reproducibility to users. Language package uses ecosystem resolution/install and may be portable if runtime exists, but native extensions/runtime versions matter. Native binaries give fast self-contained execution per OS/architecture/ABI; require separate builds, signing, dependencies and update paths. OCI image bundles runtime filesystem/config and supports registry content graphs; it adds runtime/image size/base maintenance and is awkward for some desktop/local CLI use. For three targets, release manifest can bind per-target native packages and checksums/provenance; offer source for transparency and reproducible rebuilds. Use OCI only if consumers deploy through compatible container runtimes. Test each target artifact, not only index/source, and define install/update/rollback, shell integration, credentials and SBOM/provenance per format.

### Answer 5

Control source/configuration under reviewed immutable revision; pin compiler/linker/generator, hardware board/bootloader/protocol target, dependencies and build definition. Use isolated restricted builder, reproducible independent rebuild where required, static/formal checks for selected critical properties, unit/simulation/hardware-in-loop/fault/interruption tests, exact image layout/size/checksum validation, SBOM/vulnerability/license evidence and trusted provenance. Sign digest-bound release with separated authorized role; verify in boot/update chain with key rotation, anti-rollback compatible with emergency recovery, atomic update, power-loss recovery and device/fleet configuration identity. Publish/retain artifact/evidence atomically and track installed digest per radio; staged field rollout, rollback/manual fallback and incident replay must be exercised.

Named emergency dispatchers and radio operators, communications/RF and embedded hardware/firmware engineers, safety and human-factors/accessibility specialists, cybersecurity/key-management experts, field maintenance and incident-command owners, interoperability/spectrum authorities, quality/configuration managers, regulators and independent assessors review requirements, failure/hazard/threat models, builder/tool qualification, tests, update process, residual risk and operational authorization. A reproducible signed artifact proves neither correct emergency behavior nor authorization to deploy.
