## 0. Orientation

**Precise definition:** Dask builds a **lazy** directed acyclic graph (DAG) of tasks and executes it later using a scheduler. High-level collections (DataFrame/Array/Bag) construct **HighLevelGraph** objects with layered structure that supports optimization and visualization. :contentReference[oaicite:0]{index=0}

You should treat Dask as a *graph compiler + runtime*. If you construct a graph with the wrong granularity or the wrong data movement regime, the runtime will execute it faithfully and you will observe predictable failure signatures (scheduler-bound, shuffle-bound, memory-bound, or serialization-bound).

### 0.1 Unified cost model (use this to predict failures)

> **Total runtime ≈ compute + I/O + shuffle/network + (task_count × overhead_per_task)**

Operationally, every disappointing job is dominated by one term:

1) **Too many tasks** → scheduler overhead dominates.  
2) **Too much data movement** → shuffle/network dominates.  
3) **Peak memory too high** → spilling/pausing/termination dominates.  
4) **Bad payloads** → serialization + unmanaged memory dominates.

**Pre-flight checklist (before you run):**
- **Task count**: how many tasks/futures will the scheduler coordinate?
- **Shuffle**: does any step require global redistribution?
- **Amplification**: what operations multiply memory use (groupby/join/shuffle buffers)?
- **Representation**: are you carrying `object` dtype or Python containers across partitions?

This module teaches you to answer these from reading code and inspecting the graph *without executing*.

# Core 1 — Execution Model: DAGs, Schedulers & Overhead Economics

## 1.1 The contract: build → optimize → execute

### Phase A — Graph construction (client-side, lazy)
- Your code creates a **HighLevelGraph** (HLG): layered operations that symbolically represent many tasks. :contentReference[oaicite:1]{index=1}  
- No data is read; no computation is performed.
- **Task boundaries are chosen implicitly here** (via partitions/chunks/UDF boundaries).

### Phase B — Optimization + lowering (automatic)
- Dask rewrites layers (e.g., projection/fusion where valid) and then lowers the HLG into concrete tasks.

### Phase C — Execution (scheduler-orchestrated)
- Triggered by `compute()` or `persist()`.
- Scheduler tracks dependencies and assigns tasks to workers; workers execute and exchange data.

### Renderable flow diagram (graph-first mental model)

```mermaid
flowchart TD
  A[User code: lazy expressions] --> B[HighLevelGraph layers]
  B --> C[Optimize: projection/fusion/pushdown]
  C --> D[Lower to concrete tasks]
  D --> E[Scheduler: readiness + placement]
  E --> F[Workers: execute tasks]
  F --> G[Materialize: compute() to client / persist() on cluster]
````

## 1.2 Demonstration: the graph exists before execution (and layers matter)

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({
    "key": np.random.randint(0, 200_000, size=200_000),
    "x": np.arange(200_000, dtype=np.int64),
    "y": np.random.randn(200_000),
})
ddf = dd.from_pandas(pdf, npartitions=50)

expr = (
    ddf[["key", "x", "y"]]
      .assign(z=lambda df: df.x * df.y)
      .query("x % 7 == 0")
      .groupby("key").z.mean()
)

# Still lazy: no execution
print(expr)

g = expr.__dask_graph__()
print("Graph type:", type(g))

# HLG diagnostic proxy: number of layers (lower is usually simpler)
if hasattr(g, "layers"):
    print("HLG layers:", len(g.layers))
```

**Interpretation:**

* HLG layers are *not runtime*, but they correlate with graph complexity and the optimizer’s ability to rewrite. ([Dask][1])
* A small output does not imply small work; a single result can require a large DAG.

## 1.3 Local vs Distributed schedulers: same semantics, different physics

The scheduler choice changes dispatch latency, data transfer costs, failure modes, and observability. Dask’s scheduler documentation frames this as “choose the scheduler that matches your workload.” ([Dask][2])

| Dimension        | Local schedulers (threaded/processes) | Distributed (`dask.distributed`) |
| ---------------- | ------------------------------------- | -------------------------------- |
| Coordination     | in-process                            | scheduler + workers              |
| Data transfer    | memory/IPC                            | serialization + network          |
| Failure handling | minimal                               | retries, worker loss handling    |
| Diagnostics      | limited                               | dashboard + reports              |
| Small tasks      | less painful                          | saturates earlier                |

**Correct workflow:**

* Validate correctness locally.
* Validate performance/memory with the distributed scheduler (even on one machine) because it exposes real transfer/coordination behavior.

## 1.4 Overhead economics: why micro-tasks destroy throughput

The distributed scheduler has **~millisecond-scale overhead per task/future**, and if tasks run faster than ~100ms you may see little or no speedup. ([Dask Distributed][3])
Therefore: **task granularity is a first-class design parameter**.

### Lab: micro-task pathology with `delayed`

```python
from dask import delayed

@delayed
def square(i: int) -> int:
    return i * i

N = 200_000
micro = [square(i) for i in range(N)]
total = delayed(sum)(micro)

# Run under distributed + dashboard to see scheduler-bound behavior.
result = total.compute()
print(result)
```

**Expected signature (Task Stream):**

* huge count of ultra-short tasks,
* visible scheduler backlog,
* low sustained worker efficiency.

### Fix: batch work into fewer, larger tasks

```python
from dask import delayed

@delayed
def square_batch(start: int, stop: int) -> int:
    s = 0
    for i in range(start, stop):
        s += i * i
    return s

N = 200_000
batch = 20_000

macro = [square_batch(i, min(i + batch, N)) for i in range(0, N, batch)]
total = delayed(sum)(macro)

result = total.compute()
print(result)
```

**Quantitative anchor (how to sanity-check your design):**

* If you are creating *hundreds of thousands to millions* of tiny tasks, you are likely scheduler-bound.
* If each task processes “real bytes” (tens–hundreds of MiB after projection), you are usually in a healthier regime—*then* you tune by measurement. ([Dask Distributed][3])

# Core 2 — Picking the Right Abstraction: `delayed`, `bag`, `array`, `dataframe`

## 2.1 What each abstraction is optimized for

| Collection | Best for                                | Semantics Dask can assume         | What this unlocks             | Common failure mode                      |
| ---------- | --------------------------------------- | --------------------------------- | ----------------------------- | ---------------------------------------- |
| DataFrame  | tabular analytics (groupby/join)        | stable schema, partitioned pandas | projection + planned shuffles | accidental shuffles, dtype drift         |
| Array      | dense numeric grids                     | chunked ndarray semantics         | blockwise fusion + reductions | tiny chunks → task explosion             |
| Bag        | semi-structured logs/JSON, text streams | partitions of Python objects      | schema-free map/filter/fold   | heavy serialization, slow relational ops |
| Delayed    | custom orchestration / irregular DAGs   | none                              | arbitrary DAGs                | microtasks, uncontrolled graph growth    |

## 2.2 Boundary hygiene: avoid accidental execution

Safe inspections that avoid full compute:

* `ddf.dtypes`, `ddf.columns`, `ddf.npartitions`, `ddf._meta`

Prefer bounded execution:

* `ddf.partitions[0].compute()` (one partition)
* `ddf.head()` (bounded but still executes; treat as a read)

Avoid as default debugging:

* `len(ddf)` (can trigger full scan)
* converting whole collections to pandas/NumPy “just to look”

### Example: disciplined partition inspection (and what `deep=True` means)

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({"x": np.arange(100_000), "s": ["a"] * 100_000})
ddf = dd.from_pandas(pdf, npartitions=20)

p0 = ddf.partitions[0].compute()

# deep=True accounts for Python object memory (e.g., strings/object dtype)
mib = p0.memory_usage(deep=True).sum() / 1_048_576
print("Partition 0 size (MiB):", round(mib, 2))
print(p0.dtypes)
```

## 2.3 Anti-pattern: forcing semi-structured data into DataFrame too early

**Mechanism:** DataFrame enforces schema and dtypes; semi-structured data violates schema early. That pushes expensive parsing and dtype inference across the full dataset *before* you shrink it.

Correct shape:

1. Bag parse/filter/extract stable fields,
2. Convert to DataFrame after volume reduction,
3. Store as Parquet for repeatable reads.

```python
import json
import dask.bag as db

raw = db.read_text("logs/*.jsonl").map(json.loads)

filtered = raw.filter(lambda r: r.get("event") in {"purchase", "refund"})
flat = filtered.map(lambda r: {
    "user": r.get("user_id"),
    "event": r.get("event"),
    "amount": float(r.get("amount", 0.0)),
})

# Convert only after stabilization (requires meta in many real cases)
# df = flat.to_dataframe(meta={"user": "i8", "event": "object", "amount": "f8"})
```

# Core 3 — Dask DataFrame Reality: Partitions, Index, Divisions, Unknown Divisions

## 3.1 Partitions are units of parallelism *and* memory pressure

A partition is the atomic unit for scheduling, memory residency, and shuffle exchange. Treat partition sizing as a *survivability* constraint, not “performance tuning.”

### Empirical starting point (calibrate; do not treat as a law)

Start around **50–200 MiB per partition after projection** and calibrate using dashboard peak memory during representative operations (e.g., groupby/join amplification). (This is a starting point, not a guarantee.)

### Measure partition size correctly

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({
    "key": np.random.randint(0, 10_000, size=1_000_000),
    "value": np.random.randn(1_000_000),
})
ddf = dd.from_pandas(pdf, npartitions=100)

p0 = ddf.partitions[0].compute()
mib = p0.memory_usage(deep=True).sum() / 1_048_576
print("npartitions:", ddf.npartitions)
print("partition0 (MiB):", round(mib, 2))
```

## 3.2 Divisions: precise definition and why they gate fast paths

`divisions` is a tuple of length `npartitions + 1` describing ascending index bounds per partition, enabling Dask to know which partition contains a given index value and speeding up `.loc` and other operations. ([Dask][4])
`known_divisions` indicates whether these bounds are known. ([Dask][5])

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({"x": np.arange(100_000), "v": np.random.randn(100_000)}).set_index("x")
ddf = dd.from_pandas(pdf, npartitions=20)

print("known_divisions:", ddf.known_divisions)
print("divisions (first 5):", ddf.divisions[:5])
```

## 3.3 Unknown divisions: how you get them and what breaks

Divisions become unknown when Dask cannot prove partition index bounds after transformations (commonly filtering, many UDF boundaries, or reading unsorted sources).

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({"x": np.arange(100_000), "v": np.random.randn(100_000)}).set_index("x")
ddf = dd.from_pandas(pdf, npartitions=20)

filtered = ddf[ddf["v"] > 0]
print("known_divisions after filter:", filtered.known_divisions)
```

**Operational consequence:** Dask often cannot prune partitions for index-based selection, so operations like `.loc` may degrade to scanning many partitions.

**Important correction:** `reset_index()` changes the index values; it does not “restore divisions” in the performance sense you want. Divisions are about provable partition bounds, not cosmetic index resets.

## 3.4 `repartition` vs `set_index`: two fundamentally different costs

### `repartition` by size/count: granularity tuning

Used to coalesce/split partitions to manage task count and memory.

```python
balanced = ddf.repartition(partition_size="128MiB")
```

### `set_index`: key-based redistribution (often a shuffle)

Usually requires global data movement. Treat it as a major architectural decision.

```python
indexed = ddf.reset_index().set_index("v")  # example: new index likely requires shuffle
print(indexed.known_divisions)
```

Use `set_index` when you will amortize the cost across many downstream index-based operations; otherwise avoid it.

# Core 4 — Laziness Control: `compute`, `persist` & Graph Optimization

## 4.1 Correct use cases

### `compute()` → return concrete result to the client

Use only for small terminal results.

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({"x": np.arange(1_000_000), "v": np.random.randn(1_000_000)})
ddf = dd.from_pandas(pdf, npartitions=100)

m = ddf.v.mean().compute()
print(m)
```

### `persist()` → materialize on the cluster and keep distributed

Use to create a reusable stage boundary (avoid recomputation across branches).

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({
    "key": np.random.randint(0, 200_000, size=2_000_000),
    "v": np.random.randn(2_000_000),
})
ddf = dd.from_pandas(pdf, npartitions=200)

stage = ddf[["key", "v"]][ddf["v"] > 0].repartition(partition_size="128MiB")
stagep = stage.persist()

a = stagep.groupby("key").v.mean()
b = stagep.groupby("key").v.std()

ra, rb = a.compute(), b.compute()
print(ra.head(), rb.head())
```

### Stay lazy → maximize optimization scope

Use for linear pipelines where you want projection/fusion/pushdown across the full chain.

## 4.2 Graph blow-ups: how they happen, how to prevent them

Blow-ups come from:

* deep non-fusible UDF chains,
* Python loops generating tasks,
* branching without persistence.

### Anti-pattern + fix (explicit)

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

def bump(pdf: pd.DataFrame) -> pd.DataFrame:
    pdf = pdf.copy()
    pdf["v"] = pdf["v"] + 1
    return pdf

pdf = pd.DataFrame({"v": np.random.randn(1_000_000)})
ddf = dd.from_pandas(pdf, npartitions=100)

layered = ddf
for _ in range(40):
    layered = layered.map_partitions(bump, meta=ddf._meta)

# Branching without persist forces repeated upstream work
mean_v = layered.v.mean()
std_v = layered.v.std()

# Fix: persist once at the reuse boundary
layered_p = layered.persist()
mean_v = layered_p.v.mean()
std_v = layered_p.v.std()
print(mean_v.compute(), std_v.compute())
```

## 4.3 Purity discipline: determinism + restart-safe I/O

Tasks may run more than once (retries, worker loss). Therefore:

* task functions must be deterministic,
* writes must be idempotent or transactional.

### Concrete safe-write pattern (partitioned outputs)

```python
import os
import pandas as pd
import dask.dataframe as dd

def write_partition(pdf: pd.DataFrame, out_dir: str, part_id: int) -> str:
    # Unique temp file per partition
    tmp = os.path.join(out_dir, f"part-{part_id}.tmp.parquet")
    final = os.path.join(out_dir, f"part-{part_id}.parquet")

    pdf.to_parquet(tmp, index=False)

    # Atomic replace on most filesystems
    os.replace(tmp, final)
    return final

# Usage sketch:
# parts = ddf.to_delayed()
# futures = [client.submit(write_partition, p, "out/", i) for i, p in enumerate(parts)]
```

This pattern prevents corruption under retries: a partition always ends in one canonical file.

# Core 5 — I/O at Scale: Dataset Layout as a Performance Primitive

## 5.1 Parquet-first: what matters operationally

For tabular analytics, Parquet enables:

* **projection** (read fewer columns),
* **predicate pushdown** (skip row groups),
* **partition pruning** (skip directories/files via hive partitioning).

These are storage-level “skip work” mechanisms; they often dominate performance more than compute tuning.

## 5.2 What gets skipped (and what does *not*)

### Projection

```python
import dask.dataframe as dd
ddf = dd.read_parquet("dataset/", columns=["key", "value", "date"])
```

### Predicate pushdown

```python
import dask.dataframe as dd
ddf = dd.read_parquet("dataset/", filters=[("value", ">", 0)])
```

### Partition pruning (layout dependent)

Hive layout example:

```
dataset/date=2025-12-01/region=EU/part-*.parquet
```

```python
import dask.dataframe as dd
ddf = dd.read_parquet("dataset/", filters=[("date", "==", "2025-12-01"), ("region", "==", "EU")])
```

**Clarification:** DataFrame divisions are in-memory index metadata; they do not control Parquet partition pruning.

## 5.3 Writing strategy: avoid small files and schema drift

Small files create persistent overhead (metadata reads, too many tasks). A controlled pattern:

```python
import numpy as np
import pandas as pd
import dask.dataframe as dd

pdf = pd.DataFrame({
    "date": pd.to_datetime("2025-12-01") + pd.to_timedelta(np.random.randint(0, 30, size=2_000_000), unit="D"),
    "region": np.random.choice(["EU", "US", "APAC"], size=2_000_000),
    "key": np.random.randint(0, 200_000, size=2_000_000),
    "value": np.random.randn(2_000_000),
})
ddf = dd.from_pandas(pdf, npartitions=200)

prepared = ddf[["date", "region", "key", "value"]].repartition(partition_size="256MiB")

prepared.to_parquet(
    "processed/",
    partition_on=["date", "region"],     # choose low/moderate cardinality keys
    write_metadata_file=True,
    compression="snappy",
)
```

Partition key criteria:

* low/moderate cardinality (avoid directory explosion),
* common filter predicates,
* not severely skewed.

## Appendix B — Debugging Playbook: what you see → what it means

| Observation                | Dominant term in cost model | Primary cause                                     | First fixes (in order)                                                  |
| -------------------------- | --------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------- |
| Many tiny tasks (<~50ms)   | task_count × overhead       | too-fine partitions/chunks, micro-delayed         | coalesce/repartition larger → fuse ops → batch                          |
| Shuffle dominates runtime  | shuffle/network             | wide data, high volume, poor key choice           | project/filter early → pre-aggregate → mitigate skew                    |
| Memory spikes, spill/pause | peak memory amplification   | shuffle buffers, join/groupby state, object dtype | narrow columns → tune partitions → remove object dtype                  |
| “Stuck near 99%”           | stragglers                  | skew/hot keys, uneven partitions                  | detect skew → salt/two-phase reduce → adjust partitioning               |
| High network, low CPU      | serialization/transfer      | object-heavy payloads, fragmented partitions      | consolidate partitions → pass references not objects → simplify payload |

## Appendix C — Exercises

1. **Granularity sweep (evidence-based):**
   Run the same groupby with `npartitions` in {50, 200, 2000}. Record:

   * wall time, task count proxy (graph size), shuffle bytes, peak memory (dashboard).
     Explain which cost term dominates in each run.

2. **Width impact (quantify shuffle):**
   Add 3–5 unused columns (including one `object` column). Compare:

   * groupby with early projection vs without projection.
     Quantify shuffle bytes and runtime.

3. **Skew stress test (straggler diagnosis):**
   Force 40% of rows to share one `key`. Compare baseline groupby vs salted two-phase aggregation.
   Explain the “stuck near end” signature and how it changes.

   Build a 40-layer `map_partitions` chain, branch into two downstream computations, and:

   * observe recomputation without `persist`,
   * fix with one `persist` at the reuse boundary,
   * report the change in task stream and wall time.
